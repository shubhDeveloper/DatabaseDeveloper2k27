# PART II: DATABASE FUNDAMENTALS REFRESHER (F1-F30)
##########################################################################
Senior interviewers still ask fundamentals - but expect precise, nuanced
answers with real examples.

F1. What are ACID properties and how do real engines implement them?
A.  Atomicity (undo/rollback or MVCC aborted xid), Consistency (constraints,
triggers, application invariants), Isolation (locking/MVCC snapshots),
Durability (write-ahead log flushed at commit: Oracle redo, PostgreSQL WAL).
Durability trade-offs exist: asynchronous commit (COMMIT WRITE NOWAIT /
synchronous_commit=off) trades the last few commits for speed.

F2. Explain the relational model, keys and integrity types.
A.  Relations (tables), tuples, attributes. Keys: super, candidate, primary,
alternate, foreign, surrogate vs natural. Integrity: entity (PK not null/
unique), referential (FK), domain (types/CHECK), business rules
(triggers/application). Prefer constraints in the database: they protect
every application and feed the optimizer.

F3. Normal forms and when to denormalize.
A.  1NF atomic values; 2NF no partial dependency on part of a composite key;
3NF no transitive dependency; BCNF every determinant is a candidate key;
4NF/5NF multi-valued/join dependencies. OLTP: 3NF/BCNF. Reporting: star
schema, summary tables, materialized views. Denormalize with measurement
and a consistency plan.

F4. Join types and algorithms.
A.  Logical: INNER, LEFT/RIGHT/FULL OUTER, CROSS, SEMI (EXISTS/IN), ANTI
(NOT EXISTS), LATERAL/APPLY, SELF, NATURAL (avoid). Physical: nested loop,
hash, sort-merge (Oracle and PostgreSQL). Choose by input sizes, indexes,
sortedness and memory.

F5. Transaction isolation levels and anomalies.
A.  Anomalies: dirty read, non-repeatable read, phantom read, lost update,
write skew. SQL levels: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ,
SERIALIZABLE.
  - Oracle: READ COMMITTED (default), SERIALIZABLE (snapshot), READ ONLY.
    No dirty reads. 
  - PostgreSQL: READ COMMITTED (default), REPEATABLE READ (snapshot),
    SERIALIZABLE (SSI, prevents write skew). READ UNCOMMITTED = READ COMMITTED.
  Write skew example: two doctors both go off-call because each saw the
  other still on-call; fix with SERIALIZABLE, locking, or constraints.

F6. Pessimistic vs optimistic concurrency control; MVCC vs locking.
A.  Locking engines block readers vs writers; MVCC keeps versions so readers
don't block writers. Optimistic: version columns/timestamps, retry on
conflict. Pessimistic: SELECT FOR UPDATE. Oracle MVCC via undo; PostgreSQL via
tuple versions in heap.

F7. What is a deadlock and how do you prevent it?
A.  Cycle of lock waits. Both engines detect it and abort one statement/
transaction (Oracle ORA-00060, PG 40P01). Prevent: consistent lock order,
short transactions, index FKs, avoid user interaction inside transactions,
retry logic.

F8. Explain two-phase commit and distributed transactions.
A.  Coordinator asks participants to PREPARE (durable promise), then COMMIT.
Oracle: DB links with automatic 2PC (RECO resolves in-doubt). PostgreSQL:
PREPARE TRANSACTION / COMMIT PREPARED (needs max_prepared_transactions); beware
orphaned prepared transactions blocking vacuum. Prefer sagas/outbox patterns
for microservices.

F9. What is write-ahead logging (WAL) and why does it matter?
A.  Log first, data later: changes are durable once the log record is flushed,
while data pages are written lazily. Enables fast commits, crash recovery,
PITR, replication. Both Oracle redo and PostgreSQL WAL follow this rule.

F10. Explain NULL and three-valued logic.
A.  Comparisons with NULL are UNKNOWN; WHERE keeps only TRUE. NOT IN with
NULL returns nothing; aggregates ignore NULL (not count(*)); Oracle treats ''
as NULL, PostgreSQL does not; use IS DISTINCT FROM (PG) or LNNVL/DECODE
tricks (Oracle) for null-safe compare. UNIQUE allows multiple NULLs in both
(PG15+ NULLS NOT DISTINCT option).

F11. Logical order of SQL execution.
A.  FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> window functions -> SELECT
-> DISTINCT -> ORDER BY -> LIMIT/FETCH. Explains why aliases can't be used in
WHERE (but can in ORDER BY; Oracle 23ai and PostgreSQL allow GROUP BY alias).

F12. WHERE vs HAVING; aggregate pitfalls.
A.  WHERE filters rows before grouping; HAVING filters groups after aggregation.
Push row filters into WHERE for performance. Joining before aggregating can
multiply rows (fan-out) and inflate sums - aggregate first or use semi-joins.

F13. Views vs materialized views vs temp tables vs CTEs.
A.  View: stored query (no data). Materialized view: stored result, refreshed.
Temp table: session/transaction scoped data with own statistics.
CTE: query-scoped, may be inlined or materialized. Use temp tables for
multi-step transformations needing statistics/indexes; CTEs for readability.

F14. Clustered vs non-clustered index concepts. How do Oracle and PG map?
A.  SQL Server style "clustered index" means table data stored in index order.
Oracle: index-organized table (IOT) or table clusters; normal tables are heaps.
PostgreSQL: all tables are heaps; CLUSTER reorders once; indexes are all
secondary. Row location = ROWID (Oracle) / ctid (PG).

F15. What is a covering index?
A.  An index containing all columns a query needs, avoiding table access.
Oracle: composite index (index-only access via INDEX FAST FULL SCAN/RANGE).
PostgreSQL: INCLUDE columns (PG11+) + index-only scan (needs visibility map).

F16. Cardinality and selectivity - why they matter.
A.  Selectivity = fraction of rows matched; cardinality = estimated rows.
Optimizers use them to pick access paths and join orders. Misestimates are
the most common cause of poor plans; fix with statistics, histograms,
extended statistics, query rewrite.

F17. What is a transaction log vs undo log vs binary log?
A.  Oracle: redo (forward changes) + undo (before-images in segments).
PostgreSQL: WAL (redo-only); no undo, old versions in heap. MySQL: binlog
(replication) + InnoDB redo/undo. Know which engine you're talking about.

F18. Surrogate vs natural keys; UUID vs sequence.
A.  Surrogate keys decouple identity from business attributes; sequences/
identity give compact, ordered keys (good index locality); random UUIDs (v4)
cause index fragmentation and cache misses; time-ordered UUIDs (v7; native in
PG18) combine uniqueness with locality. Keep natural keys as unique
constraints.

F19. Data types: choosing correctly.
A.  Use exact numerics for money (NUMBER/numeric, not float), timestamps with
time zone for events, smallest suitable integer, text vs varchar (PG: same
performance), CLOB/BLOB vs text/bytea, JSON(B) for semi-structured data,
enums/lookup tables for domains. Datatype mismatches cause implicit
conversions that kill index use.

F20. Referential actions: CASCADE, SET NULL, RESTRICT, NO ACTION.
A.  Oracle supports ON DELETE CASCADE/SET NULL (no ON UPDATE). PostgreSQL
supports ON DELETE/UPDATE with all actions, DEFERRABLE constraints, MATCH
options. Always index FK child columns.

F21. Temporary data structures.
A.  Oracle: global temporary tables (persistent definition, private data),
private temporary tables (18c+). PostgreSQL: TEMP tables (per session),
UNLOGGED tables (no WAL, not crash-safe). Statistics on temp tables need
gathering/ANALYZE.

F22. Sequences vs identity vs auto-increment.
A.  Sequences are independent objects; identity columns (Oracle 12c, PG10)
use them internally. Neither is gap-free or rollback-safe. Cache improves
speed, causes gaps on restart; RAC/replicas add ordering considerations.

F23. Set-based thinking vs procedural loops.
A.  Declarative SQL lets the optimizer choose algorithms; row-by-row loops
("slow-by-slow") force one plan per row and pay context switch/round-trip
costs. Convert loops to INSERT...SELECT, MERGE, UPDATE...FROM, window
functions; where loops are unavoidable, batch with bulk operations.

F24. OLTP vs OLAP vs HTAP design differences.
A.  OLTP: normalized, short transactions, B-tree indexes, high concurrency.
OLAP: star schemas, large scans, partitioning, bitmap/BRIN, compression,
parallelism, summary tables. HTAP: mixed workloads; use replicas, in-memory
column stores (Oracle In-Memory), or extensions; isolate resources.

F25. What is database normalization's impact on performance?
A.  More joins but smaller rows and less redundancy; good indexes and FK
design make joins cheap. Over-normalization hurts reads; under-normalization
hurts write integrity and size. Measure.

F26. Explain cardinality of relationships and how to model many-to-many.
A.  One-to-one, one-to-many, many-to-many via an associative (junction)
table with composite PK/unique and two FKs; add attributes of the
relationship there. Index both FK directions according to access paths.

F27. Define referential integrity vs application-enforced integrity.
A.  DB-enforced constraints are the source of truth: atomic, concurrent-safe,
visible to the optimizer. Application checks have race conditions. Use both
for UX and safety.

F28. Explain checkpointing conceptually (engine neutral).
A.  Periodically force dirty pages to disk and record a recovery start
point so crash recovery replays only recent log. Trade-off: frequency vs I/O
spikes vs recovery time.

F29. What is a database cursor? Client vs server side?
A.  Cursor = handle to iterate a result set. Server-side cursors keep state in
the DB (Oracle open cursors; PG portals/named cursors) and fetch in
batches; client-side loads all rows to the client. Large result sets
need streaming/server-side cursors with fetch size.

F30. How do you decide between SQL and application logic?
A.  Put data-intensive set operations, integrity rules and security-sensitive
logic near the data; keep UI/workflow/external integrations in the app.
Avoid chatty round-trips and duplicated rules; version and test both
sides. Document ownership of each rule.

==========================================================================
 3.1 THE BIG PICTURE (BEGINNER VIEW)
==========================================================================
An Oracle server has two halves:

  DATABASE  = files on disk (data, redo, control, archive).
  INSTANCE  = memory (SGA) + background processes that operate the database.

One instance opens one database (single instance). In RAC, many instances
on many servers open the SAME database on shared storage.

 Client app
    |  (Oracle Net / TCP 1521)
    v
 +----------+     spawns / hands off      +----------------------------------+
 | Listener | --------------------------> | INSTANCE                         |
 +----------+                             |  SGA (shared memory)             |
                                          |   - Database Buffer Cache        |
 User Process --> Server Process (+PGA) <-|   - Shared Pool (library cache,  |
                                          |     dictionary cache, result     |
                                          |     cache)                       |
                                          |   - Redo Log Buffer              |
                                          |   - Large / Java / Streams pools |
                                          |  Background processes:           |
                                          |   PMON SMON DBWn LGWR CKPT ARCn  |
                                          |   MMON MMNL RECO LREG CJQ0 ...   |
                                          +----------------+-----------------+
                                                           |
                      +------------------+-----------------+-------------+
                      |                  |                 |             |
                 Data files         Online redo logs   Control files  Archived
                 (tables, indexes,  (groups/members)   (metadata,     redo logs
                  UNDO, TEMP)                           SCN, files)

==========================================================================
 3.2 MEMORY STRUCTURES
==========================================================================
SGA (System Global Area) - shared by all processes:

 a) Database Buffer Cache
    - Caches data blocks (default 8 KB) read from datafiles.
    - Managed with a touch-count modified LRU. Dirty buffers sit on a
      checkpoint queue and are written by DBWn.
    - Pools: DEFAULT, KEEP, RECYCLE, plus non-standard block-size caches.
    - Access is protected by "cache buffers chains" latches. Hot blocks
      cause "latch: cache buffers chains" or "buffer busy waits".

 b) Shared Pool
    - Library cache: parsed SQL (cursors), PL/SQL, execution plans.
      Parent cursor (SQL text) + child cursors (plan per environment).
    - Dictionary (row) cache: data dictionary metadata (tables, columns,
      privileges).
    - Result cache: SQL/PL/SQL function results.
    - Errors: ORA-04031 (cannot allocate shared memory) - usually literal
      SQL (no binds) causing fragmentation.

 c) Redo Log Buffer
    - Circular buffer where change vectors are written first.
    - LGWR flushes it to online redo logs.

 d) Large Pool: shared-server session memory (UGA), RMAN buffers,
    parallel execution message buffers.
 e) Java Pool, Streams Pool, In-Memory Column Store (option).

PGA (Program Global Area) - private to each server process:
    - Sort area, hash area, bitmap merge area (work areas).
    - Session information (UGA) and private SQL area.
    - Controlled by PGA_AGGREGATE_TARGET (soft) and PGA_AGGREGATE_LIMIT
      (hard). Spills go to TEMP tablespace.

Memory management modes: AMM (MEMORY_TARGET), ASMM (SGA_TARGET +
PGA_AGGREGATE_TARGET) - most production DBs use ASMM (AMM doesn't work
with HugePages on Linux).

==========================================================================
 3.3 BACKGROUND PROCESSES
==========================================================================
 PMON/CLMN : cleans up failed user processes, releases locks/resources.
 LREG      : (12c+) registers services with the listener.
 SMON      : instance recovery at startup, cleans temp segments, coalesces
             free space, recovers dead transactions.
 DBWn      : writes dirty buffers to datafiles (database writers).
 LGWR      : writes redo buffer to online redo logs. Commit waits on it.
 CKPT      : signals checkpoints, updates control/datafile headers.
 ARCn      : copies filled online redo logs to archive destination.
 MMON/MMNL : AWR snapshots, metrics, alerts (hourly AWR by default).
 RECO      : resolves in-doubt distributed transactions.
 CJQ0/Jnnn : scheduler job coordinator and job slaves.
 DBRM, VKTM, DIAG, PSP0, MMAN, SMCO, Wnnn : resource manager, timer,
             diagnostics, process spawner, memory manager, space mgmt.
 RAC only  : LMON, LMD, LMS (cache fusion), LCK, GCR.

==========================================================================
 3.4 PHYSICAL STRUCTURES (FILES)
==========================================================================
 Datafiles     : actual data for tablespaces (SYSTEM, SYSAUX, UNDO, TEMP,
                 USERS...). Tempfiles for TEMP.
 Online redo   : at least 2 groups, each with 1+ members (multiplex).
                 LGWR writes circularly; log switch moves to next group.
 Archived redo : copies of filled redo logs when in ARCHIVELOG mode
                 (needed for point-in-time recovery, Data Guard).
 Control files : database name, datafile/redo locations, checkpoint info,
                 SCN, RMAN metadata. Multiplexed. Losing all = recovery.
 SPFILE/PFILE  : startup parameters.
 Password file, alert log, trace files (ADR - Automatic Diagnostic
 Repository), wallet (TDE).

==========================================================================
 3.5 LOGICAL STRUCTURES
==========================================================================
 Database > Tablespace > Segment > Extent > Data Block

 - Block: smallest I/O unit (2K-32K, commonly 8K).
 - Extent: contiguous blocks. Segment: all extents of one object (table,
   index, partition, LOB, undo, temp).
 - Locally Managed Tablespaces with ASSM (bitmap-based free space) are the
   norm. High-Water Mark (HWM) separates formatted from unformatted blocks;
   full scans read up to HWM.
 - ROWID = data object# + file# + block# + row slot#.

Data block layout:
   [ Header (ITL slots) | Table dir | Row dir | ... free space ... | Rows ]
 ITL = Interested Transaction List: one slot per concurrent transaction
 touching the block (INITRANS/MAXTRANS). Each row has a lock byte pointing
 to the ITL slot - Oracle stores row locks in the block, not in a lock table.

==========================================================================
 3.6 HOW A SQL STATEMENT RUNS (END TO END)
==========================================================================
 1) Client connects: listener -> dedicated server process (or dispatcher
    for shared server, or DRCP pooled server). PGA is allocated.
 2) PARSE: syntax check -> semantic check (privileges, objects) ->
    library-cache lookup by SQL text hash (SQL_ID).
      - Found = SOFT parse (reuse).
      - Not found = HARD parse: optimizer transformations + plan costing.
 3) BIND/DEFINE: bind values supplied (bind peeking may influence plan).
 4) EXECUTE: row-source tree runs. Blocks fetched from buffer cache; if
    absent, physical read into cache (db file sequential/scattered read).
 5) FETCH: rows returned to client in array-size batches.

 For DML:
 a) Server process finds block in buffer cache (reads if needed).
 b) Allocates undo (undo segment transaction table slot), writes undo
    record (old values) into undo block (also a buffer, also logged).
 c) Generates redo for BOTH the data change and the undo change into the
    redo log buffer.
 d) Changes the data block in cache (now dirty), sets row lock byte/ITL.
 e) COMMIT: assigns commit SCN, LGWR writes redo (incl. commit record) to
    disk -> "log file sync" -> user told committed. Dirty data blocks are
    NOT written at commit (no-force policy). Locks released; block cleanout
    may be delayed.
 f) DBWn lazily writes dirty blocks later (no-steal is NOT enforced:
    uncommitted changes may reach disk; undo + redo handle recovery).
 Write-ahead rule: redo must be on disk before the corresponding dirty data
 block is written.

==========================================================================
 3.7 READ CONSISTENCY, UNDO AND SCN
==========================================================================
 - SCN (System Change Number): global logical clock. Each statement/
   transaction starts with an SCN; queries see data "as of" that SCN.
 - If a reader finds a block changed after its SCN (or with uncommitted
   data), Oracle clones the block and applies UNDO to roll it back -
   a consistent-read (CR) block. Readers never block writers.
 - ORA-01555: undo needed for CR was overwritten (undo too small, long
   query, fetch across commits).
 - Undo serves 3 roles: rollback, read consistency, flashback/recovery.
 - UNDO_RETENTION: target seconds to keep committed undo ("unexpired").
 - Delayed block cleanout: after commit, blocks are not immediately cleaned
   of transaction info; next reader cleans them (can cause redo on SELECT).

==========================================================================
 3.8 CHECKPOINTS, REDO AND RECOVERY
==========================================================================
 - Checkpoint = advance of the point from which recovery must start:
   all changes before it are on disk in datafiles. Types: full (shutdown),
   incremental (continuous; driven by FAST_START_MTTR_TARGET), log switch,
   tablespace/datafile (offline, begin backup).
 - Instance recovery after crash (automatic, by SMON at open):
     ROLL FORWARD: apply redo from checkpoint position to end of redo
     (repeating history, including uncommitted).
     ROLL BACK: undo uncommitted transactions (can be done after the DB
     opens, on demand, in background).
 - Media recovery: restore datafile from backup (RMAN) + apply archived and
   online redo (to latest, or to time/SCN/cancel).
 - Redo log groups states: CURRENT, ACTIVE (needed for crash recovery,
   checkpoint not yet complete), INACTIVE, UNUSED.

==========================================================================
 3.9 CONCURRENCY CONTROL: LOCKS, LATCHES, MUTEXES
==========================================================================
 - Enqueues (locks): TX (transaction/row), TM (table DML), UL (user),
   others. Queue-based, deadlock detection, visible in V$LOCK.
 - Row locking: lock byte + ITL; no lock escalation, no memory per row lock.
 - Latches: low-level, short, spin-then-sleep (e.g. cache buffers chains,
   redo allocation). Mutexes: lightweight for library cache objects.
 - Pins/buffer busy waits for same-block contention.
 - Isolation: READ COMMITTED (default), SERIALIZABLE, READ ONLY. No dirty
   reads; writers don't block readers.

==========================================================================
 3.10 STARTUP, SHUTDOWN, MULTITENANT, RAC, DATA GUARD
==========================================================================
 Startup stages:
   NOMOUNT : read SPFILE, create SGA/processes (instance only)
   MOUNT   : read control file
   OPEN    : open datafiles/redo, instance recovery if needed
 Shutdown: NORMAL (wait for sessions), TRANSACTIONAL, IMMEDIATE (rollback and
   close; standard), ABORT (like a crash; instance recovery at next start).

 Multitenant (12c+): CDB (root + seed + PDBs). One instance/SGA/background
   processes shared; each PDB has its own datafiles/schemas. Fast clone,
   unplug/plug, resource isolation. 21c+ is multitenant only.

 RAC: multiple instances, one shared database (ASM/shared storage). Cache
   Fusion ships blocks over a private interconnect (GCS/GES), SCAN listener,
   voting disks/OCR in Clusterware. Gives HA + scalability for suitable
   workloads; needs attention to hot blocks and sequences (CACHE, NOORDER).

 Data Guard: standby databases fed with redo (physical = block-identical
   redo apply; logical = SQL apply). Protection modes: Maximum Performance
   (async), Availability, Protection (sync). Active Data Guard: read-only
   standby while applying.

 ASM: Oracle's volume manager/filesystem for database files (striping,
   mirroring, rebalance).

==========================================================================
 3.11 OPTIMIZER, STATISTICS AND DICTIONARY
==========================================================================
 - Cost-Based Optimizer: uses stats (num rows, blocks, NDV, histograms,
   clustering factor, system stats) to choose among plans.
 - Query transformations: view merging, subquery unnesting, predicate
   pushing, join predicate pushdown, OR expansion, star transformation.
 - Adaptive features (12c+): adaptive plans, dynamic statistics, SQL plan
   directives, automatic reoptimization (cardinality feedback). SQL Plan
   Management for stability.
 - Data dictionary: base tables owned by SYS (never touched manually),
   exposed through DBA_/ALL_/USER_ views. V$/GV$ views expose live memory
   structures. AWR/ASH store history in SYSAUX.
 - Automated maintenance windows: statistics gathering, segment advisor,
   SQL tuning advisor.

# PART IV: ORACLE ARCHITECTURE & INTERNALS QUESTIONS (O1-O55)
##########################################################################

---------------------------- A. BASICS TO CORE ---------------------------

O1. What is the difference between an Oracle instance and a database?
A.  Instance = SGA + background processes (volatile, in memory). Database =
physical files (datafiles, redo, control). An instance opens exactly one
database (RAC: many instances, one database). You can start an instance
without a database (NOMOUNT). Instance failure loses memory only; the
database is recovered from redo.
REAL-WORLD: During a server reboot I explained to app teams that data is
safe because committed redo was on disk; instance recovery was automatic.

O2. Explain the SGA components and which ones you tune most.
A.  Buffer cache, shared pool (library cache, dictionary cache, result
cache), redo log buffer, large pool, Java pool, streams pool, in-memory area.
Most tuning attention: buffer cache hit patterns and hot blocks, shared pool
(literals -> ORA-04031 / mutex waits; use binds, size properly), redo log
buffer (rarely > 100 MB), and large pool for shared server/parallel/RMAN.
Use V$SGA_TARGET_ADVICE and AWR advisories, but confirm with wait events.
REAL-WORLD: High library cache mutex waits were solved by fixing literal SQL
and setting a sensible shared pool floor, not by blindly enlarging memory.

O3. PGA vs UGA vs SGA - what is where?
A.  PGA is private per server process: work areas (sort/hash), cursor state,
variables. UGA (session state: package variables, cursors) lives in the PGA
for dedicated server connections but in the SGA (large pool) for shared
server. Large sorts/hash joins that exceed their work area spill to TEMP
("multi-pass"). Control with PGA_AGGREGATE_TARGET/LIMIT.
REAL-WORLD: Unbounded BULK COLLECT in PL/SQL ballooned PGA until ORA-04030;
fixed using LIMIT.

O4. List the important background processes and what happens if each dies.
A.  DBWn, LGWR, CKPT, SMON, PMON are mandatory - if any dies the instance
terminates (crashes) and recovers on restart. ARCn death isn't fatal but redo
logs can't be archived (database may hang with ORA-00257 when logs fill).
MMON failure stops AWR/alerts only.
REAL-WORLD: Archiver stuck on a full archive destination hung the database;
I freed space, took RMAN backup deleting archives, and added alerts.

O5. What happens when a client connects to Oracle?
A.  Client resolves service name -> contacts listener -> listener
hands off to (or spawns) a dedicated server process (or dispatcher for
shared server, or DRCP pooled server) -> authentication -> session and PGA
created -> logon triggers -> session in V$SESSION. With RAC, SCAN/VIP and
connection load balancing pick an instance.
REAL-WORLD: Slow logins traced to DNS reverse lookups and a logon trigger;
fixed both.

O6. Dedicated server vs shared server vs DRCP?
A.  Dedicated: one server process per session (best for OLTP/long
transactions, default). Shared server: dispatchers route requests to a pool
of shared servers (saves processes, bad for long-running work, UGA in
SGA/large pool). DRCP: pool of server processes for short-lived connections
from stateless apps (e.g. PHP), reducing connect cost.
REAL-WORLD: Used application-side pooling (UCP/HikariCP) with dedicated
servers rather than shared server for predictable performance.

O7. Describe the lifecycle of a SQL statement.
A.  Parse (syntax, semantic, shared pool lookup; soft vs hard parse) ->
bind -> execute (row source tree, consistent gets/physical reads) -> fetch.
Hard parse includes transformations and cost-based plan generation and takes
latches/mutexes; soft parse avoids optimizer work. Cursor sharing depends on
SQL text, bind metadata and optimizer environment.
REAL-WORLD: Reduced hard parses/sec from 800 to 20 by enforcing bind
variables in the data access layer.

O8. Library cache internals: parent/child cursors, version count, mutexes?
A.  Parent cursor = SQL text hash. Child cursors = distinct plan/environment
variants (different NLS, bind length buckets, optimizer settings, Adaptive
Cursor Sharing). High VERSION_COUNT (hundreds) causes "cursor: mutex S/X"
waits. Check V$SQL_SHARED_CURSOR for reason codes. Fix root cause (bind
mismatches, NLS differences, literals) rather than flush.
REAL-WORLD: A single SQL had 3,000 children because of varying bind sizes in
a legacy driver; upgraded driver and normalized binds.

O9. How is the buffer cache managed? What are hot blocks?
A.  Hash buckets of buffer headers protected by cache-buffers-chains latches;
touch-count-based replacement (modified LRU); dirty buffers tracked on the
checkpoint queue. Full table scans of large tables use direct path reads
(bypass cache) or recycle-style handling. Hot blocks (e.g. a tiny lookup
table or right-edge index leaf on a sequence key) cause latch/buffer busy
contention. Fixes: reverse key/hash partition indexes, spread data
(PCTFREE), cache in app, reduce logical IO.
REAL-WORLD: A sequence-based PK index right-edge contention was eased with
hash-partitioned global index.

---------------------- B. TRANSACTIONS, REDO AND UNDO --------------------

O10. Walk through what happens on UPDATE then COMMIT.
A.  Block read into cache -> undo segment slot + undo record created ->
redo generated for undo and data changes -> block modified, row lock byte/ITL
set -> COMMIT: commit record in redo buffer, LGWR flushes ("log file sync"),
SCN assigned, locks released; dirty blocks stay in cache and DBWn writes
later. Delayed block cleanout may finish transaction info on next access.
REAL-WORLD: Answering this precisely helped me diagnose "log file sync"
spikes: row-by-row commits were the cause.

O11. What triggers LGWR to write?
A.  Commit/rollback, redo buffer 1/3 full, 1 MB of redo accumulated, every 3
seconds, before DBWn writes a block whose redo isn't yet on disk (write-ahead
logging), and on checkpoints/log switch. LGWR can use slaves (LGnn) in newer
versions. Group commit batches multiple sessions' commits in one write.
REAL-WORLD: Moved redo logs to low-latency storage and sized groups so
switches happened about every 15-20 minutes.

O12. What triggers DBWn to write?
A.  Checkpoint progress (incremental via FAST_START_MTTR_TARGET), buffer cache
needs free buffers (scan depth), tablespace offline/ read-only/backup begin,
dirty buffer threshold, every 3 seconds timeout. DBWn doesn't write on
commit. "free buffer waits" indicate DBWn can't keep up.
REAL-WORLD: Added DBWn processes and improved I/O after seeing free buffer
waits and write complete waits.

O13. Redo vs undo - differences and why both?
A.  Redo = forward-looking log to re-apply changes (recovery, standby).
Undo = backward-looking old values for rollback, read consistency and
flashback. Redo is also generated for undo blocks (undo is itself protected
by redo). Redo is sequential files; undo lives in undo tablespace segments
cached in the buffer cache.
REAL-WORLD: Used this to explain why a huge UPDATE generates redo about
2x the data change (data + undo).

O14. Explain checkpoint types and why they matter.
A.  Full checkpoint (shutdown/immediate), incremental checkpoint (continuous
via checkpoint queue; target set by FAST_START_MTTR_TARGET), thread
checkpoint (log switch), object checkpoint (drop/truncate, offline).
Checkpoint position is stored in control file and datafile headers and
defines where crash recovery starts. Too-frequent checkpoints add I/O;
too infrequent lengthen recovery.
REAL-WORLD: Set MTTR target to 120s balancing recovery time vs write load.

O15. Explain instance recovery step by step.
A.  Startup detects unclean shutdown (control file/header SCN mismatch) ->
SMON rolls forward by applying redo from last checkpoint to end (including
changes of uncommitted transactions), opens database, then rolls back
uncommitted transactions using undo (in background/on demand). Time depends
on checkpoint distance. No archived logs normally needed.
REAL-WORLD: Crash recovery of a 2 TB DB took ~4 minutes because MTTR was
tuned; I documented RTO based on this.

O16. What is SCN and how is it used?
A.  A monotonically increasing logical timestamp. Used for read consistency,
commit ordering, recovery, flashback, Data Guard, GoldenGate and
distributed transactions. Visible via CURRENT_SCN, SCN_TO_TIMESTAMP. The
control file stores checkpoint SCNs. SCN headroom concerns (2012-2019)
were fixed with patches; keep patched.
REAL-WORLD: Used flashback query AS OF SCN to compare data before/after a
faulty batch.

O17. How does read consistency work, and what is ORA-01555?
A.  Query SCN fixed at start. For blocks changed later, Oracle builds a CR
copy by applying undo. If needed undo is overwritten (expired and reused),
ORA-01555. Causes: undersized undo, long queries, commits inside fetch loops,
delayed block cleanout. Fix: size undo / UNDO_RETENTION, RETENTION GUARANTEE
(careful: can fail DML), fix commit-in-loop, shorten queries.
REAL-WORLD: Month-end report hit 01555 after undo autotune shrank; we set
retention and fixed the loop.

O18. What is delayed block cleanout?
A.  After commit, Oracle doesn't revisit every changed block to clear
transaction info (ITL/lock bytes); the next session touching it cleans it
(may generate redo even for a SELECT, and requires checking undo
transaction table). Large transactions with many blocks flushed before
commit are the typical case ("commit SCN stored lazily").
REAL-WORLD: Explained unexpected redo from a SELECT after a huge batch load.

O19. Explain block structure, ITL, PCTFREE, chaining and migration.
A.  Block = header (with ITL), table directory, row directory, free space,
row data. INITRANS reserves ITL slots; ITL waits (enq: TX - allocate ITL)
happen when many sessions modify one block and no free ITL space exists.
PCTFREE reserves space for updates. Row migration: updated row no longer fits
-> moved, leaving forwarding pointer (rowid retained). Row chaining: row
larger than one block.
REAL-WORLD: Fixed ITL waits on a hot status table by increasing INITRANS
and rebuilding.

O20. Segments, extents, HWM, ASSM - explain and why it matters.
A.  Segments contain extents of blocks. ASSM uses bitmaps for free space
within segments (no freelists), good for concurrency. HWM marks the top of
used blocks; full scans read to HWM even if empty; lowered by TRUNCATE,
SHRINK SPACE, MOVE. Direct-path inserts load above HWM.
REAL-WORLD: Shrinking a work-queue table reduced a 2 s full scan to 20 ms.

O21. What is a ROWID and why is it not a stable key?
A.  Physical address: object number, relative file#, block#, row slot.
Changes if row moves (partition key update with ROW MOVEMENT, MOVE/SHRINK,
export/import). Fine inside one statement/session logic; never store as a
permanent key.
REAL-WORLD: Fixed a job that cached ROWIDs across a table move.

O22. Tablespaces, datafiles, temp, bigfile - what do you design?
A.  Separate tablespaces by purpose (data, index, LOB, partition ranges) for
manageability and backup/recovery granularity; locally managed + ASSM;
TEMP tablespace groups for parallel; UNDO sized for longest transaction;
bigfile tablespaces to simplify admin in ASM. Avoid autoextend surprises.
REAL-WORLD: Partitions in dedicated tablespaces allowed moving cold data to
cheaper storage and making older partitions read-only.

O23. What is in the control file and what if you lose it?
A.  DB name/DBID, datafile & redo locations, checkpoint SCNs, archived log
history, RMAN metadata, tablespace info. Always multiplex. If all copies
are lost: restore from autobackup or recreate (CREATE CONTROLFILE), then
recover with redo.
REAL-WORLD: Practiced control-file restore in DR drills.

O24. ARCHIVELOG vs NOARCHIVELOG; log switch and ORA-00257?
A.  ARCHIVELOG: filled redo logs are copied by ARCn so you can do online
backups, PITR and Data Guard. If the archive destination is full, log switches
block (ORA-00257) and the DB appears hung. Monitor FRA usage, backup and
delete archives (RMAN DELETE ... BACKED UP).
REAL-WORLD: Added alert at 70% FRA and an automated RMAN archive backup.

O25. Redo log sizing and "log file switch (checkpoint incomplete)"?
A.  Logs too small -> frequent switches; DBWn can't finish checkpointing
before LGWR needs the log again -> checkpoint incomplete/ archiving needed
waits. Size so switches occur ~every 15-30 min at peak; add groups; fast
storage for redo; check archiver throughput.
REAL-WORLD: Increased 200 MB logs to 4 GB and added groups; waits vanished.

----------------------- C. LOCKING AND CONCURRENCY -----------------------

O26. Locks vs latches vs mutexes vs enqueues?
A.  Enqueues are queued, deadlock-detected locks for logical resources
(TX, TM). Latches protect memory structures (spin then sleep, no queue).
Mutexes are finer-grained, cheaper latch replacements for cursors/objects.
Buffer pins protect a buffer during access. Latch/mutex waits imply CPU/
contention issues; enqueue waits imply application locking.
REAL-WORLD: Distinguished "enq: TX - row lock contention" (app design)
from "latch: shared pool" (parsing) in AWR to route issues correctly.

O27. How does Oracle implement row-level locking?
A.  A transaction gets an ITL slot in the block and sets the row's lock
byte to that ITL index; the TX enqueue is held on the transaction's undo
slot. Other sessions requesting the row wait on the TX enqueue until commit/
rollback. No lock table in memory, hence no escalation. TM locks protect
tables from DDL during DML.
REAL-WORLD: Explained why Oracle scales with millions of row locks.

O28. Unindexed foreign keys - what's the problem?
A.  Deleting/updating parent keys requires a lock on the child table (TM
share lock in older versions, or row-level scans on child) causing
blocking and deadlocks. Index FK columns when parents are modified or
joins are common.
REAL-WORLD: Deadlocks disappeared after indexing child FK columns.

O29. Enqueue deadlock detection and ORA-00060?
A.  Oracle detects cycles in waits (every few seconds), rolls back the
statement of one session (not whole transaction) and raises ORA-00060; the
trace file in ADR shows both sessions' SQL. App must handle by retry or
fix lock ordering.
REAL-WORLD: Analyzed deadlock trace to find two procedures locking in
opposite order.

--------------------------- D. OPTIMIZER AND SQL -------------------------

O30. How does the Oracle optimizer work?
A.  Parse tree -> transformation phase (heuristic and cost-based rewrites:
view merging, subquery unnesting, predicate pushdown, OR-expansion,
star transformation) -> plan generation (access paths, join methods/orders,
costs using statistics, system stats) -> best plan chosen and stored in
shared pool. Adaptive plans can switch join methods at runtime; SQL Plan
Management baselines can stabilize plans.
REAL-WORLD: Used 10053 trace to see why join order changed after stats
gathering.

O31. Statistics and histograms - types and pitfalls?
A.  Table/column/index stats, NDV, density, nulls, histograms (frequency,
top-frequency, hybrid, height-balanced legacy). Bad histograms on bind-
dependent columns cause plan instability; use METHOD_OPT carefully. Extended
stats for column groups/expressions. Gather with DBMS_STATS, AUTO sample,
incremental for partitions, lock stats on volatile tables.
REAL-WORLD: Removed a histogram on a skewed status column causing flip-flop
plans with bind peeking, and used SQL baseline.

O32. Adaptive Cursor Sharing, bind peeking, cursor_sharing?
A.  Bind peeking uses the first bind at hard parse. ACS (11g+) marks cursors
bind-sensitive and creates multiple children when bind values produce very
different row counts. CURSOR_SHARING=FORCE rewrites literals but is a
workaround.
REAL-WORLD: Diagnosed using V$SQL.IS_BIND_SENSITIVE/AWARE.

O33. Direct path vs conventional path reads/writes?
A.  Conventional: through buffer cache, SGA latches, undo/redo generated.
Direct path: bypasses cache (parallel full scans, large serial scans, sort
spills, APPEND inserts, SQL*Loader direct). Direct path reads are good for
large scans but mean repeated scans don't get cached.
REAL-WORLD: Switched a heavily scanned table to be cached via KEEP pool and
smaller serial direct read threshold tuning after profiling.

O34. Parallel execution architecture?
A.  Query Coordinator (QC) plus PX server processes (producer/consumer sets)
exchanging rows via table queues. DOP controlled by hints, table/index
degree, PARALLEL_DEGREE_POLICY (auto), Resource Manager. Parallel DML needs
enabling and commit before reading. Skew and too many PX servers hurt other
workloads.
REAL-WORLD: Capped DOP using consumer groups for the batch role.

O35. Partitioning internals and global index maintenance?
A.  Partitions are separate segments; partition pruning at parse/execution.
Local indexes align with partitions (easy maintenance); global indexes span
partitions, becoming UNUSABLE on partition ops unless UPDATE INDEXES
(asynchronous maintenance in 12c for DROP/TRUNCATE). Interval partitioning
auto-creates partitions; exchange partition is a dictionary-only swap.
REAL-WORLD: Monthly purge was converted into DROP PARTITION ... UPDATE
GLOBAL INDEXES.

O36. B-tree index internals?
A.  Root, branch, leaf blocks; leaf entries (key + rowid) doubly linked;
50/50 splits for random inserts and 90/10 for right-edge inserts. Deleted
entries are reused, so regular rebuilds are mostly a myth; rebuild only
with clear evidence. Bitmap indexes lock ranges of rows (bad for OLTP).
Index compression and invisible indexes help testing.
REAL-WORLD: Stopped a weekly index-rebuild job after measuring no benefit;
saved IO and locking.

---------------- E. HA, BACKUP, MULTITENANT, OPERATIONS ------------------

O37. RMAN architecture and backup strategy?
A.  RMAN uses server sessions to read datafiles, writes backup pieces/sets or
image copies, tracks metadata in control file/catalog. Block change tracking
makes incrementals fast. Strategy: weekly level 0 + daily level 1 (cumulative
or differential) + archivelog backups; validate (RESTORE VALIDATE); test
restores; define RPO/RTO. Recovery scenarios: restore datafile, PITR,
tablespace PITR, block media recovery, PDB recovery.
REAL-WORLD: Ran quarterly restore tests that exposed a missing archive log
range and fixed policy.

O38. RAC architecture and common issues?
A.  Multiple instances, shared storage, Clusterware (CRS), ASM, voting disks,
OCR, private interconnect, Cache Fusion (GCS/GES) transfers blocks between
instances (gc cr/current block waits). Issues: hot blocks, sequences
(use CACHE/NOORDER), interconnect latency, application affinity, split-
brain avoided by voting. Services and load balancing route sessions.
REAL-WORLD: Partitioned workloads by service to cut gc waits 60%.

O39. Data Guard: types, modes and failover vs switchover?
A.  Physical standby (redo apply, block identical, can be Active Data Guard
read-only), logical standby (SQL apply), snapshot standby. Protection modes:
Max Performance (ASYNC), Max Availability (SYNC with fallback), Max
Protection (SYNC no fallback). Switchover = planned role swap, no data loss;
failover = unplanned, may lose data in async. Use Data Guard Broker/Fast-Start
Failover.
REAL-WORLD: Performed switchover drills for patching with ~2 min downtime.

O40. ASM overview?
A.  Disk groups with striping and mirroring (normal/high/external
redundancy), automatic rebalance on disk add/remove, instance of its own
(+ASM), files named by ASM (OMF). Removes need for filesystem/LVM; used by
RAC and standalone.
REAL-WORLD: Added disks online and rebalanced without downtime.

O41. Flashback technologies - what's available?
A.  Flashback Query/Version Query/Transaction Query (undo-based), Flashback
Table (undo + row movement), Flashback Drop (recycle bin), Flashback
Database (flashback logs, rewinds the DB), Flashback Data Archive (long
history). Not a replacement for backups.
REAL-WORLD: Used Flashback Table to recover after a bad deployment script
in a lower environment in seconds.

O42. AWR, ASH and ADDM - how do they work?
A.  MMON takes AWR snapshots (default hourly, retained 8 days) of V$ stats
into SYSAUX; ASH samples active sessions every second in memory (flushing
1 in 10 samples to AWR). ADDM analyzes snapshots and recommends. Use ASH for
short spikes, AWR for trends, SQL Monitor for long ops. Diagnostics Pack
licensing applies.
REAL-WORLD: Used ASH for a 5-minute outage that AWR hourly average hid.

O43. Startup and shutdown modes - what do you use in production and why?
A.  STARTUP NOMOUNT/MOUNT/OPEN stages; SHUTDOWN IMMEDIATE normally (rolls back
active transactions, no instance recovery needed). ABORT only when hung or
for crash testing; TRANSACTIONAL waits for transactions. Always check alert
log after.
REAL-WORLD: A hung immediate shutdown was due to a long rollback; waited
using v$transaction rather than aborting.

O44. Multitenant architecture - benefits and gotchas?
A.  One CDB instance with PDBs: consolidation, quick provisioning (clone),
patch once, resource management per PDB, plug/unplug. Gotchas: common vs
local users, per-PDB parameters, shared undo (12.2+ local undo option),
connect via service names, backups at CDB or PDB level.
REAL-WORLD: Consolidated 12 non-CDB dev databases into one CDB.

O45. Resource Manager and Scheduler internals?
A.  Resource Manager (DBRM) plans consumer groups with CPU/parallel/IO/
session limits. Scheduler: CJQ0 coordinates, Jnnn run jobs, supports chains,
windows, events, remote jobs. Use for protecting OLTP from batch.
REAL-WORLD: Gave OLTP group 70% CPU priority during business hours.

O46. Security architecture overview?
A.  Users/roles/profiles, system and object privileges, definer/invoker
rights, VPD (DBMS_RLS), Fine-Grained Auditing/Unified Audit, TDE (wallet,
tablespace/column), Database Vault, Data Redaction, network encryption.
Least privilege + auditing + encryption in transit/rest.
REAL-WORLD: Implemented VPD policies for regional data access.

O47. Oracle Net: listener, services, tnsnames, SCAN?
A.  Listener (LISTENER, port 1521) maps service names to instances (dynamic
registration via LREG). Clients use EZConnect or tnsnames.ora (service_name,
failover, load balance). RAC SCAN gives single access name with 3 IPs.
Troubleshoot using lsnrctl status/services, tnsping, listener logs.
REAL-WORLD: Fixed intermittent ORA-12514 by correcting service registration.

------------------------ F. TROUBLESHOOTING SCENARIOS --------------------

O48. The database appears hung. What do you do?
A.  1) Can you connect (sqlplus -prelim / oradebug hanganalyze)? 2) Check
alert log, archiver/FRA full (ORA-00257), disk space, 3) ASH/V$SESSION:
blockers, wait classes (Concurrency, Configuration, Commit), 4) latch/
mutex storms, library cache pin, 5) undo/temp full, 6) kill blocker
only after identifying root cause, 7) capture diagnostics before
bounce. Post-incident: RCA and monitors.
REAL-WORLD: A hang from FRA full: freed archives, resumed in 10 min.

O49. Many sessions waiting on "log file sync". Approach?
A.  Check average commit latency: LGWR "log file parallel write" time. If
LGWR write is slow: storage latency, redo on busy disks, too many
members/sync. If LGWR write is fast but sync is slow: CPU starvation or
excessive commits. Fix: batch commits, faster redo storage, reduce redo,
correct Data Guard SYNC latency.
REAL-WORLD: App committed per row; moving to batches reduced waits 90%.

O50. ORA-04031 appears intermittently. Approach?
A.  Check which pool (shared pool/large pool/streams); literal SQL leading to
fragmentation, large PL/SQL objects (pin large packages), too small
pool, many versions. Use V$SHARED_POOL_RESERVED, V$SQL for literal
duplicates (FORCE_MATCHING_SIGNATURE), fix with binds; avoid flush as a
routine.
REAL-WORLD: Found 1.2M near-identical literal statements; app fix removed
04031.

O51. Instance recovery takes too long. Why?
A.  Large checkpoint gap (huge redo logs, high MTTR target, many dirty
buffers), slow redo read I/O, parallel recovery not enabled, long
transactions needing rollback. Tune FAST_START_MTTR_TARGET, check
V$INSTANCE_RECOVERY, parallel recovery, avoid giant transactions.
REAL-WORLD: Reduced crash recovery from 20 to 4 minutes with MTTR tuning.

O52. Temp tablespace is full - what do you check?
A.  V$TEMPSEG_USAGE/V$SORT_USAGE for sessions, SQL causing hash/sort spills,
missing join predicates (cartesian), large GROUP BY/ORDER BY, parallel
operations, global temporary tables, LOB temp. Add tempfile as relief; fix
SQL and PGA settings.
REAL-WORLD: Cartesian join from a missed predicate consumed 400 GB temp.

O53. Segment/table growth: how do you reclaim space?
A.  ALTER TABLE ... SHRINK SPACE (online, requires row movement), MOVE (online
in 12.2+), DBMS_REDEFINITION, drop/purge old partitions, compress. Rebuild
dependent indexes if unusable; check HWM and segment advisor.
REAL-WORLD: Reclaimed 300 GB via partition drop and online move.

O54. Statistics job and maintenance windows: how do you manage them?
A.  Auto optimizer stats collection runs in maintenance windows (stale >10%
changes). For volatile or partitioned tables set custom prefs
(INCREMENTAL, STALE_PERCENT), lock stats, gather after ETL, monitor job
history (DBA_SCHEDULER_JOB_RUN_DETAILS / DBA_OPTSTAT_OPERATIONS).
REAL-WORLD: Locked stats on staging tables and gathered explicitly post-load.

O55. How would you explain Oracle architecture in 2 minutes?
A.  "An instance - SGA plus background processes - serves sessions through
server processes with private PGA. Data blocks are cached in the buffer
cache; changes generate redo and undo; commit just forces redo to disk via
LGWR, while DBWn writes data blocks later using checkpoints. Undo gives
rollback and read consistency; SCN orders everything. Crash recovery is
roll-forward with redo then rollback with undo. Archive logs, RMAN,
Data Guard and RAC give recovery and HA."

==========================================================================
 5.1 THE BIG PICTURE (BEGINNER VIEW)
==========================================================================
PostgreSQL uses a PROCESS-PER-CONNECTION model. A "cluster" is one
PostgreSQL server instance managing a data directory (PGDATA) that contains
multiple databases.

 Client app
    |  (TCP 5432 / Unix socket)
    v
 +-----------+  fork()   +-------------------+
 | postmaster| --------> | Backend process   |  one per connection
 | (parent)  |           | (local memory:    |
 +-----+-----+           |  work_mem, etc.)  |
       |                 +---------+---------+
       | forks                     |
       v                           v
 Background processes      +--------------------------------------------+
  checkpointer             | SHARED MEMORY                              |
  background writer        |  shared_buffers (page cache)               |
  WAL writer               |  WAL buffers                               |
  autovacuum launcher/     |  clog/SLRU buffers, lock tables, proc array|
    workers                |  pg_stat shared stats (PG15+)              |
  archiver, WAL sender/    +----------------------+---------------------+
    receiver, logical      |                      |
    replication workers    v                      v
  (PG18: I/O workers)   Data files (base/)    WAL (pg_wal/)
                         + OS page cache      + archive (optional)

==========================================================================
 5.2 MEMORY STRUCTURES
==========================================================================
SHARED (allocated at startup, shared by all processes):
 - shared_buffers: PostgreSQL's page cache (8 KB pages). Typical start
   ~25% of RAM. PostgreSQL ALSO relies on the OS page cache
   ("double buffering"), so effective_cache_size tells the planner how much
   total cache (shared_buffers + OS) is likely available.
   Replacement: clock-sweep with usage counts; large seq scans, VACUUM and
   bulk writes use small ring buffers so they don't evict the whole cache.
 - WAL buffers (wal_buffers): WAL records before flush to disk.
 - SLRU buffers: pg_xact (commit status), subtrans, multixact, notify,
   serializable (PG17 made these configurable).
 - Lock manager tables, ProcArray (list of running transactions), shared
   cumulative statistics (since PG15 - old stats collector process removed).

PER-BACKEND (private, allocated on demand):
 - work_mem: per sort/hash node (a query can use many multiples); hash nodes
   can use work_mem x hash_mem_multiplier.
 - maintenance_work_mem: VACUUM, CREATE INDEX, ALTER TABLE ADD FK.
 - temp_buffers: temp table pages. Plus catalog caches (relcache, catcache),
   plan caches for prepared statements/PL/pgSQL.
 Because memory is per process, thousands of connections can exhaust RAM:
 use a pooler (PgBouncer, pgcat, RDS Proxy).

==========================================================================
 5.3 PROCESSES
==========================================================================
 postmaster       : supervisor; listens for connections; forks backends and
                    background workers; restarts them after crashes
                    (a backend crash triggers a cluster-wide restart/
                    recovery as shared memory may be corrupted).
 backend          : serves one client connection (parse, plan, execute).
 checkpointer     : performs checkpoints: flush all dirty buffers, write
                    checkpoint WAL record, recycle old WAL.
 background writer: trickles dirty buffers to disk to keep free buffers
                    available and smooth checkpoint I/O.
 WAL writer       : flushes WAL buffers periodically (wal_writer_delay,
                    200 ms) - also helps asynchronous commit.
 autovacuum launcher + workers: run VACUUM/ANALYZE based on thresholds.
 archiver         : copies completed WAL segments to archive (if enabled).
 WAL sender / receiver : streaming replication (primary / standby).
 startup process  : performs crash recovery and WAL replay on standbys.
 logical replication launcher/apply workers; parallel workers;
 walsummarizer (PG17 incremental backup); I/O workers (PG18, io_method=worker
 for asynchronous I/O; io_uring option on Linux).
 Stats collector: existed before PG15, replaced by shared-memory stats.
 View all with: SELECT pid, backend_type FROM pg_stat_activity;

==========================================================================
 5.4 PHYSICAL STRUCTURES ($PGDATA)
==========================================================================
  base/<db_oid>/<relfilenode>  : table & index files (1 GB segments).
  global/                      : cluster-wide catalogs (pg_database, roles).
  pg_wal/                      : WAL segments (16 MB default each).
  pg_xact/                     : commit/abort status of transactions
                                 (2 bits per xid; formerly pg_clog).
  pg_multixact/, pg_subtrans/, pg_commit_ts/, pg_notify/, pg_serial/ : SLRU data.
  pg_tblspc/                   : symlinks to tablespaces.
  postgresql.conf, postgresql.auto.conf (ALTER SYSTEM), pg_hba.conf (auth),
  pg_ident.conf, PG_VERSION, postmaster.pid.

 Each relation has "forks": main (data), _fsm (free space map), _vm
 (visibility map: all-visible/all-frozen bits), and init (unlogged tables).

 Page (8 KB) layout:
   [PageHeader | ItemId array (line pointers) -> grows down ...
    ... free space ... <- tuples grow up | special space (indexes)]
 TID/ctid = (block number, line pointer index). Index entries point to TIDs.
 Tuple header (~23 bytes): xmin, xmax, cmin/cmax (command id), ctid
 (next version link), infomask (hint bits), null bitmap.
 TOAST: values > ~2 KB are compressed (pglz/lz4) and/or moved to a TOAST
 table in chunks; transparent to SQL.

==========================================================================
 5.5 MVCC: HOW PostgreSQL STORES VERSIONS
==========================================================================
 - UPDATE = mark old tuple dead (set xmax) + insert NEW tuple version
   (new xmin) in the same table (heap). No separate undo.
 - DELETE = set xmax. INSERT = new tuple with xmin.
 - A snapshot (xmin, xmax, active xid list) decides visibility:
   tuple visible if creator xid committed & before snapshot and not deleted
   by a visible committed xid. Commit status read from pg_xact; result is
   cached in tuple hint bits to avoid repeated clog lookups
   (a SELECT can dirty pages by setting hint bits).
 - HOT (Heap-Only Tuple) updates: if no indexed column changes and the new
   version fits in the same page, no new index entries are needed; old
   versions are pruned in-page ("page pruning").
 - VACUUM: finds dead tuples not visible to any snapshot, removes index
   entries, marks space reusable (free space map), updates visibility map,
   freezes old xids. VACUUM FULL rewrites the table (exclusive lock).
 - Transaction ID wraparound: xids are 32-bit; freezing protects old tuples.
   Autovacuum runs anti-wraparound vacuums; if not possible the DB stops
   accepting writes near the limit.
 - Consequence: table bloat if vacuum is blocked (long transactions,
   replication slots, prepared transactions, idle in transaction).

==========================================================================
 5.6 WAL, CHECKPOINTS AND RECOVERY
==========================================================================
 - Write-Ahead Logging: every change is first described in WAL (LSN =
   position). Commit = WAL record flushed to disk (synchronous_commit=on).
   Data pages are written later by bgwriter/checkpointer/backends.
 - full_page_writes: first modification of a page after a checkpoint logs the
   whole page (protects against torn pages) - increases WAL after each
   checkpoint, which is why checkpoint tuning matters.
 - Checkpoints triggered by checkpoint_timeout (5 min), max_wal_size (1 GB
   default), or manually. checkpoint_completion_target spreads writes.
 - Crash recovery: startup process replays WAL from the last checkpoint's
   redo point to the end. There is NO "rollback phase": uncommitted
   transactions' tuples remain invisible (xid not committed) and vacuum
   cleans them later.
 - wal_level: minimal, replica (default), logical (for logical decoding).
 - Timelines: new timeline created after promotion/PITR to separate histories.

==========================================================================
 5.7 QUERY PROCESSING PIPELINE
==========================================================================
   SQL text
     -> PARSER      (raw parse tree; syntax)
     -> ANALYZER    (semantic analysis, catalog lookups -> query tree)
     -> REWRITER    (rules, views are expanded here)
     -> PLANNER/OPTIMIZER (generates paths, costs them, chooses cheapest)
     -> EXECUTOR    (pull-based "Volcano" tree of plan nodes)
 - Cost model: seq_page_cost=1, random_page_cost=4 (use ~1.1 on SSD),
   cpu_tuple_cost=0.01, cpu_index_tuple_cost=0.005, cpu_operator_cost=0.0025.
 - Join ordering by dynamic programming; GEQO (genetic) beyond
   geqo_threshold (12) relations.
 - Plans are NOT shared across sessions (no global shared plan cache);
   each backend caches plans for prepared statements and PL/pgSQL
   (generic vs custom plans).
 - Statistics: pg_statistic/pg_stats from ANALYZE (MCV, histogram,
   n_distinct, correlation); CREATE STATISTICS for multi-column.
 - Parallel query: leader + parallel workers (dynamic background workers)
   communicating via shared memory queues; Gather/Gather Merge nodes.
 - JIT (LLVM) can compile expressions for big analytic queries.

==========================================================================
 5.8 LOCKING AND CONCURRENCY
==========================================================================
 Four layers:
  1) Spinlocks      - tiny critical sections in shared memory.
  2) LWLocks        - lightweight locks for shared structures (buffer
                      mapping, WAL insert); show as "LWLock:*" wait events.
  3) Heavyweight locks - table/row/transaction/advisory locks, deadlock
                      detection (deadlock_timeout 1 s). Row locks are stored
                      in the tuple (xmax + infomask) and multixacts.
  4) Predicate locks - for SERIALIZABLE (SSI) to detect rw-dependencies.
 Isolation: READ COMMITTED (default), REPEATABLE READ (snapshot isolation),
 SERIALIZABLE (SSI). No dirty reads.

==========================================================================
 5.9 REPLICATION, BACKUP, HA
==========================================================================
 - Streaming (physical) replication: WAL stream to standbys; hot standby
   allows read queries; async or sync (synchronous_standby_names);
   replication slots retain WAL until consumed (watch disk usage!).
 - Logical replication: publish/subscribe of row changes using logical
   decoding (wal_level=logical). Selective tables, cross-version, used for
   zero-downtime upgrades; DDL not replicated.
 - Backups: pg_dump/pg_dumpall (logical), pg_basebackup / pgBackRest /
   Barman (physical) + WAL archiving for PITR; PG17 incremental backup.
 - HA: no built-in failover manager; use Patroni (etcd/Consul), repmgr,
   pg_auto_failover, or managed services. pg_rewind resyncs old primary.
 - Upgrades: pg_upgrade (in-place, --link fast), logical replication.

==========================================================================
 5.10 CATALOG, EXTENSIBILITY, CONFIGURATION
==========================================================================
 - System catalogs (pg_class, pg_attribute, pg_index, pg_proc, pg_stats...)
   are ordinary tables in each database; objects identified by OID.
 - Extensibility is a core design goal: extensions, custom types/operators,
   index access methods (GiST/GIN/BRIN...), table access methods, FDWs,
   procedural languages, hooks (e.g. pg_stat_statements, auto_explain).
 - Config precedence: compile defaults < postgresql.conf <
   postgresql.auto.conf < ALTER DATABASE/ROLE SET < session SET.
   Parameter "context": postmaster (restart), sighup (reload), superuser/
   user (session). Check pg_settings.
 - Startup/shutdown (pg_ctl): smart (wait for sessions), fast (default;
   abort sessions, clean checkpoint), immediate (like crash - recovery on
   next start).

# PART VI: POSTGRESQL ARCHITECTURE & INTERNALS QUESTIONS (P1-P55)
##########################################################################

---------------------------- A. BASICS TO CORE ---------------------------

P1. Explain PostgreSQL architecture in simple terms.
A.  A cluster (one server instance on one PGDATA) is managed by the
postmaster, which forks one backend process per client connection. Backends
share shared_buffers, WAL buffers and lock tables in shared memory. Background
processes (checkpointer, bgwriter, WAL writer, autovacuum, archiver, WAL
senders) do maintenance. Data is in 8 KB pages in heap files; changes go
to WAL first; MVCC keeps old row versions in the table until VACUUM cleans
them.
REAL-WORLD: I use this description to explain why connection counts and
long-running transactions directly affect memory and bloat.

P2. Why does PostgreSQL use process-per-connection? What are the trade-offs?
A.  Historically simpler and more robust (isolation of crashes per backend,
portability, no thread-safety concerns). Costs: connection start-up is
expensive (fork + catalog cache warm-up), each backend uses memory
(relcache, work_mem), context switching grows with thousands of connections,
and process overhead limits max_connections practically to hundreds without
pooling. Mitigate with PgBouncer and sensible pool sizes.
REAL-WORLD: Reduced 3,000 app connections to 150 server connections with
PgBouncer; CPU and memory dropped markedly.

P3. What are the main background processes and what does each do?
A.  checkpointer (periodic flush, checkpoints), background writer (smooth
dirty page writing), WAL writer (flush WAL buffers), autovacuum launcher/
workers, archiver, WAL sender/receiver (replication), startup (recovery),
logical replication workers, stats/IO workers depending on version.
If a backend crashes, the postmaster restarts all backends and runs crash
recovery. See pg_stat_activity.backend_type.
REAL-WORLD: An extension segfault in one backend restarted the whole
cluster; I moved that extension out of the hot path and patched it.

P4. What memory areas exist and how do you size them?
A.  Shared: shared_buffers (~25% RAM start), wal_buffers (auto-sized, up to
16 MB), SLRU buffers. Local: work_mem (per sort/hash node), maintenance_work_
mem, temp_buffers. Planner hint: effective_cache_size (~50-75% RAM).
Total potential = shared + (connections x work_mem x nodes) + maintenance.
Size from workload; monitor temp files (log_temp_files) and cache hit ratios
per relation, not just global.
REAL-WORLD: Right-sized work_mem by role (OLTP 4 MB, reporting 128 MB) after
seeing OOM kills.

P5. How does shared_buffers differ from Oracle's buffer cache? Double buffering?
A.  PostgreSQL buffers pages in shared_buffers AND the OS page cache holds
copies (double buffering) because PG uses buffered I/O. Hence shared_buffers
is not set to most of RAM. Replacement is clock-sweep with usage counts;
large scans/VACUUM use ring buffers. Oracle typically bypasses the OS cache
(direct I/O) and manages most memory itself. PG18 adds asynchronous I/O to
improve read throughput.
REAL-WORLD: pg_buffercache showed hot tables fitting; further increasing
shared_buffers didn't help while OS cache did the work.

P6. Describe the lifecycle of a query.
A.  Parse -> analyze (catalog lookup) -> rewrite (views/rules) -> plan
(path generation + cost) -> execute (Volcano-style iterator tree; each node
returns tuples on demand) -> results to client. Simple Query vs Extended
Query protocol (parse/bind/execute) for prepared statements. Plans are cached
per session for prepared statements/PL/pgSQL, not globally.
REAL-WORLD: Explained why many short connections hurt: each re-parses and
re-plans with no shared plan cache.

P7. How does the planner choose a plan?
A.  Generates access paths (seq, index, bitmap, index-only) and join paths
(nested loop, hash, merge) with cost estimates from statistics and cost
constants (seq_page_cost, random_page_cost, cpu_*). Dynamic programming over
join orders (GEQO for many tables). Costs are "arbitrary units" that
correlate to page fetches. Wrong estimates, not wrong cost constants,
usually cause bad plans.
REAL-WORLD: Tuned random_page_cost to 1.1 after moving to NVMe; several
index scans were chosen correctly.

P8. Walk through what happens on INSERT, UPDATE, DELETE.
A.  INSERT: backend finds a page with space (FSM), writes tuple (xmin=txid),
logs WAL record, marks buffer dirty, updates indexes (each with WAL).
UPDATE: sets xmax on old tuple, inserts new tuple (HOT if possible), updates
indexes only if needed. DELETE: sets xmax. No data is removed physically
until VACUUM. WAL flush at commit; data page writes later.
REAL-WORLD: Used this to explain why UPDATE-heavy tables need vacuum tuning
and fillfactor.

P9. What happens on COMMIT?
A.  Commit WAL record is generated and flushed (fsync) according to
synchronous_commit; transaction status in pg_xact set to committed;
ProcArray updated (snapshot visibility). Locks released. Data pages stay
dirty and are flushed by bgwriter/checkpointer. With synchronous
replication, commit also waits for standby ack (synchronous_commit levels).
REAL-WORLD: Reduced commit latency for non-critical audit logging using
synchronous_commit=off at the transaction level.

P10. Describe a heap page and tuple header.
A.  Page header, array of line pointers (ItemIds) at the front, tuples
growing from the end, free space in the middle. Tuple header holds xmin,
xmax, command id, ctid, infomask (hint bits, locked flags), null bitmap,
then column data. Index entries point to (block, offset). Wide row
overhead ~24 bytes/tuple + 4-byte line pointer.
REAL-WORLD: Estimated table size correctly for 1B-row table including
tuple overhead and alignment padding (column order matters!).

P11. What is TOAST?
A.  The Oversized-Attribute Storage Technique: values bigger than ~2 KB are
compressed (pglz or lz4) and/or stored out-of-line in a per-table TOAST
table in chunks, with a pointer in the main tuple. Storage strategies:
PLAIN, EXTENDED, EXTERNAL, MAIN. Implication: SELECT * on wide
columns costs I/O; updates of other columns don't rewrite TOASTed values.
REAL-WORLD: Splitting big JSONB blobs into a separate table sped up
scans of the hot narrow table.

---------------------------- B. MVCC AND VACUUM --------------------------

P12. Explain MVCC visibility rules and snapshots.
A.  A snapshot records xmin (oldest active), xmax (next xid) and active xid
list. A tuple version is visible if xmin committed and visible to the
snapshot, and xmax is invalid/aborted/not yet visible. READ COMMITTED takes
a new snapshot per statement; REPEATABLE READ per transaction. Commit status
comes from pg_xact, cached as hint bits.
REAL-WORLD: Used txid_current_snapshot()/pg_current_snapshot() to debug
why a long transaction blocked cleanup.

P13. What are hint bits and why can a SELECT write?
A.  First reader to check a tuple's xmin/xmax commit status in pg_xact sets
hint bits (committed/aborted) in the tuple header to avoid future lookups.
That dirties the page; if checksums/wal_log_hints are on, may also WAL-log it.
So SELECT after a large load can cause writes (and why teams run VACUUM
after bulk loads).
REAL-WORLD: Explained unexpected write I/O after a bulk COPY; a post-load
VACUUM (FREEZE) fixed it.

P14. What does VACUUM do, phase by phase? VACUUM vs VACUUM FULL?
A.  Plain VACUUM: scans heap (using visibility map to skip), collects dead
TIDs (limited by maintenance_work_mem; PG17 improved memory use), vacuums
indexes, removes dead tuples from heap, updates FSM/VM, freezes old xids,
may truncate empty trailing pages. Doesn't block normal DML. VACUUM FULL
rewrites the table and indexes into new files with ACCESS EXCLUSIVE lock -
returns space to OS but blocks everything. pg_repack achieves it online.
REAL-WORLD: Replaced a weekly VACUUM FULL with autovacuum tuning plus
pg_repack for rare cases.

P15. How does autovacuum decide to run? How do you tune it?
A.  Vacuum when dead tuples > autovacuum_vacuum_threshold (50) +
autovacuum_vacuum_scale_factor (0.2) x reltuples; analyze similarly (0.1);
insert-driven vacuum since PG13 (for freezing/vm). Throttled by cost-based
delay (autovacuum_vacuum_cost_limit/delay), max workers (3) shared. For big
hot tables set per-table: scale_factor 0.01-0.05, higher cost limit,
more workers. Watch for autovacuum not finishing due to locks or old
snapshots.
REAL-WORLD: A 2B-row table with scale 0.2 waited for 400M dead rows; per-
table 0.01 fixed bloat.

P16. What blocks vacuum from cleaning dead tuples?
A.  The "xmin horizon": oldest of (long-running transactions/snapshots,
idle in transaction sessions, prepared transactions, replication slots'
xmin / catalog_xmin, standbys with hot_standby_feedback). Find with
pg_stat_activity (xact_start, backend_xmin), pg_replication_slots,
pg_prepared_xacts. Fix the culprit; set
idle_in_transaction_session_timeout.
REAL-WORLD: A forgotten logical replication slot held xmin and bloated
catalog tables by 80 GB.

P17. What are the free space map and visibility map?
A.  FSM tracks free space per page so inserts reuse space. VM stores two bits
per page: all-visible (index-only scans can skip heap; vacuum can skip) and
all-frozen (anti-wraparound vacuum can skip). Poor vacuuming means index-only
scans do heap fetches.
REAL-WORLD: Raised vacuum frequency on a table to restore index-only scans.

P18. Explain HOT updates and page pruning.
A.  HOT: if the update touches no indexed column and the new tuple fits in the
same page, the new version is chained from the old one and no index entry is
added. Page pruning (opportunistic, during reads/writes when the page is
near full) removes dead HOT chains without VACUUM. Maximize with
fillfactor 70-90 and avoid indexing frequently updated columns.
REAL-WORLD: Dropped an unused index on an updated column: HOT ratio rose
from 10% to 85% (pg_stat_user_tables.n_tup_hot_upd).

P19. Explain transaction ID wraparound and multixacts.
A.  32-bit xids compared circularly; a tuple older than ~2 billion would
look "in the future". Freezing marks tuples as frozen (visible to all).
Autovacuum forces vacuum when age(relfrozenxid) > autovacuum_freeze_max_age
(200M). Multixact IDs track multiple lockers of the same row (FOR SHARE, FK
checks) and have their own wraparound handling. If limits are neared,
PostgreSQL refuses new xid allocations until vacuum completes.
REAL-WORLD: Built alerts on age(datfrozenxid) > 1B and per-table
age(relfrozenxid).

------------------------ C. WAL, CHECKPOINT, RECOVERY --------------------

P20. Explain WAL structure and LSN.
A.  WAL is a sequence of records (insert/update/commit/checkpoint, per
resource manager) stored in 16 MB segment files (pg_wal). LSN is a 64-bit
byte position in the WAL stream (e.g. 0/16B3748). Used by recovery,
replication (sent/flush/replay LSN), and page LSN for ordering. Names encode
timeline + segment.
REAL-WORLD: Computed replica lag in bytes with pg_wal_lsn_diff.

P21. How do checkpoints work and why do they cause I/O spikes?
A.  At checkpoint, all dirty shared buffers are flushed, a checkpoint record
is written, and older WAL can be recycled. Triggered by checkpoint_timeout or
reaching max_wal_size. After a checkpoint, first change to each page writes a
full page image (full_page_writes), increasing WAL volume. Tuning: larger
max_wal_size, checkpoint_timeout 15-30 min, checkpoint_completion_target 0.9.
REAL-WORLD: Latency spikes every 5 min matched checkpoints; larger
max_wal_size and spread writes removed them.

P22. Explain crash recovery. How is it different from Oracle?
A.  After unclean shutdown, the startup process reads pg_control for the
last checkpoint and replays WAL from the redo location to the end. It's
redo-only: uncommitted transactions don't need rollback because their tuple
versions are simply invisible (xid not committed) and cleaned later by
vacuum. Oracle must roll forward and then roll back using undo.
REAL-WORLD: Used it to explain why PostgreSQL restarts come up quickly
even after a long-running batch crash.

P23. bgwriter vs checkpointer vs backend writes?
A.  checkpointer: writes all dirty buffers at checkpoints. bgwriter: writes
some dirty buffers continuously ahead of the clock sweep so backends find
clean buffers. Backends write buffers themselves only when forced (a bad
sign: many "buffers_backend" in pg_stat_bgwriter / pg_stat_io). PG16+ pg_stat_io
gives detailed breakdown.
REAL-WORLD: High backend writes pointed to undersized shared_buffers and
aggressive bulk loads; tuned bgwriter_lru_maxpages.

P24. wal_level, synchronous_commit, fsync - what are the effects?
A.  wal_level: minimal (no replication), replica (physical replication/
archiving), logical (adds info for logical decoding). synchronous_commit:
off (async, risk losing recent commits but no corruption), local, remote_
write, on, remote_apply. fsync/full_page_writes off risk corruption -
never in production.
REAL-WORLD: Per-transaction synchronous_commit=off for telemetry inserts.

------------------------ D. LOCKING AND CONCURRENCY ----------------------

P25. Explain the PostgreSQL lock hierarchy.
A.  Spinlocks (shared-memory primitives), LWLocks (buffer mapping, WAL
insert, etc.; LWLock waits in pg_stat_activity), heavyweight locks (relation
locks in 8 modes, tuple/transactionid/advisory, deadlock detection), and
predicate locks for SSI. Row locks live in tuples (xmax + infomask) with
multixacts for shared locks, so no in-memory lock table for rows.
REAL-WORLD: Distinguished Lock:transactionid waits (app contention) from
LWLock:WALInsert (write contention) while triaging.

P26. How is SERIALIZABLE implemented?
A.  Serializable Snapshot Isolation (SSI): snapshot isolation plus
predicate locks tracking read-write dependencies; if a dangerous structure
(two consecutive rw-antidependencies forming a cycle) is detected, a
transaction aborts with 40001. Needs retry logic; has memory overhead
(max_pred_locks_per_transaction).
REAL-WORLD: Used SERIALIZABLE for a funds allocation procedure with retry
wrapper; no need for explicit locks.

P27. Why can ALTER TABLE cause an outage even if it's quick?
A.  It needs ACCESS EXCLUSIVE lock. If a long query holds a conflicting
lock, ALTER waits - and all later queries queue behind the ALTER. Use
lock_timeout, retry loop, avoid DDL during long transactions, and consider
operations that need weaker locks (CREATE INDEX CONCURRENTLY, ADD
CONSTRAINT NOT VALID).
REAL-WORLD: Introduced a migration runner that sets lock_timeout=2s and
retries with backoff.

P28. Subtransactions: where do they come from and what is the problem?
A.  SAVEPOINTs and PL/pgSQL EXCEPTION blocks create subtransactions with own
xids (allocated lazily when they write). Each backend caches up to 64
subxids in the proc array; beyond that, snapshots are marked "suboverflowed"
and visibility checks hit pg_subtrans (SLRU) heavily, causing contention
(LWLock:SubtransSLRU) and slowdowns, especially on replicas.
REAL-WORLD: Removed per-row EXCEPTION blocks in a loop and ORM savepoints;
latency stabilized.

---------------------------- E. INDEXES AND STORAGE ----------------------

P29. B-tree internals in PostgreSQL?
A.  Lehman-Yao style B+-tree; leaf pages hold (key, TID), linked siblings;
page splits when full; deduplication of equal keys (PG13), bottom-up
deletion to reduce version churn (PG14). Indexes are unversioned: each
index entry points to a heap TID, so update of an indexed column inserts
new entries; dead entries removed by vacuum. Bloat appears from deleted
rows and splits - REINDEX CONCURRENTLY fixes.
REAL-WORLD: Rebuilt a 120 GB bloated index concurrently, cutting it to 40 GB
and reducing IO.

P30. GIN, GiST, SP-GiST, BRIN - how do they work internally?
A.  GIN: inverted index key -> posting list/tree of TIDs; fastupdate pending
list for writes. GiST: balanced tree with generalizable predicates (ranges,
geometry, KNN, exclusion constraints). SP-GiST: space-partitioned (tries,
quadtrees). BRIN: stores min/max (or other summary) per range of pages;
tiny but only effective if physical order correlates with values.
REAL-WORLD: Tuned gin_pending_list_limit and fastupdate for a high-write
JSONB table.

P31. How are system catalogs and OIDs organized?
A.  Catalogs are normal tables (pg_class: relations; pg_attribute: columns;
pg_index; pg_proc; pg_type; pg_namespace; pg_stats view). Files are named by
relfilenode (changes on rewrite like VACUUM FULL, TRUNCATE, some ALTERs).
pg_relation_filepath() shows path. Template databases (template0/template1)
are used to create new DBs.
REAL-WORLD: Used catalog queries to find missing FK indexes and unused
indexes.

P32. How do tablespaces, databases, schemas and roles relate?
A.  Cluster -> databases (isolated; cross-database queries not possible without
FDW/dblink) -> schemas (namespaces) -> objects. Roles are cluster-wide
(users and groups are both roles). Tablespaces are directories mapped to
filesystems for placing tables/indexes. Oracle's "schema = user" model
differs: PG schemas are separate from roles.
REAL-WORLD: Used schema-per-tenant for 200 tenants with a shared role model.

P33. Partitioning internals?
A.  Declarative partitions are separate tables attached to a partitioned
parent (no data in parent). Planner prunes at plan and execution time.
Each partition has its own indexes, vacuum, statistics (analyze the parent for
the global view too). No global indexes; unique keys must include partition
key. Too many partitions increase planning/memory.
REAL-WORLD: 400 daily partitions worked; 20,000 did not - moved to weekly.

P34. How does parallel query work?
A.  The leader process plans a Gather node; the postmaster launches parallel
workers (dynamic background workers; limits: max_parallel_workers_per_
gather, max_parallel_workers, max_worker_processes) that run the same plan
subtree on a share of work (parallel seq scan splits blocks; parallel hash
join shares a hash table), returning tuples through shared-memory queues.
Writes (except some utility commands like CREATE INDEX) aren't parallel.
REAL-WORLD: Parallel index build cut a 6-hour index creation to 1.5 hours.

P35. Extensibility architecture: extensions, hooks, FDW, access methods?
A.  Extensions package SQL objects + shared libraries (CREATE EXTENSION).
Hooks allow intercepting planner/executor (pg_stat_statements, auto_explain).
FDWs access external sources (postgres_fdw, oracle_fdw, file_fdw). Pluggable
index AMs and (since PG12) table access methods; procedural languages.
This is a key reason PostgreSQL powers many forks and specialized
databases.
REAL-WORLD: Used postgres_fdw with pushdown for cross-database reports and
pg_partman for partition maintenance.

P36. What is async I/O in newer PostgreSQL (PG18)?
A.  PG18 introduced an asynchronous I/O subsystem (io_method = worker, io_uring
or sync) so backends can issue multiple reads concurrently for scans,
bitmap heap scans and vacuum, improving throughput on cloud/network storage.
Know your version: earlier releases relied on OS readahead and
effective_io_concurrency prefetch hints.
REAL-WORLD: Benchmarked seq scans on EBS-like storage before/after enabling
async I/O in a test cluster.

------------------------- F. REPLICATION, BACKUP, HA ---------------------

P37. Streaming replication internals?
A.  Standby's WAL receiver connects to primary's WAL sender, streams WAL;
startup process replays. Hot standby allows reads; replay can conflict with
queries (vacuum cleanup removing rows needed by standby queries) -> query
cancellation unless max_standby_streaming_delay/hot_standby_feedback are
set (feedback may cause primary bloat). Sync replication via
synchronous_standby_names with quorum options.
REAL-WORLD: Long reporting queries on replica were cancelled; used a
dedicated replica with larger delay.

P38. Replication slots - benefits and dangers?
A.  Slots ensure the primary retains WAL (and catalog xmin for logical) until
the consumer confirms. Dangers: abandoned/lagging slot fills pg_wal and
disk, and holds back vacuum. Monitor pg_replication_slots (restart_lsn,
wal_status), set max_slot_wal_keep_size, drop unused slots.
REAL-WORLD: Disk hit 100% from a dead logical slot; dropped it and added
alerting.

P39. Logical decoding and logical replication?
A.  WAL with wal_level=logical is decoded by an output plugin (pgoutput,
wal2json) into row changes per transaction, delivered via slots. Logical
replication publishes tables; subscribers apply changes. Needs replica
identity (PK) for UPDATE/DELETE; DDL, sequences and large objects aren't
replicated automatically. Used for upgrades, CDC (Debezium), selective sync.
REAL-WORLD: Upgraded PG13 to PG16 with logical replication and a
5-minute cutover.

P40. Backup strategies and PITR?
A.  Logical: pg_dump (consistent snapshot, portable, slower for restore).
Physical: pg_basebackup/pgBackRest/Barman + WAL archiving => PITR to a
timestamp/LSN/named restore point (recovery_target_time + recovery signal
files). PG17+ supports incremental base backups. Always test restores and
measure RTO; verify with pg_verifybackup; encrypt and store off-site.
REAL-WORLD: Restored a PITR clone to just before an accidental DELETE and
copied rows back.

P41. HA and failover: how does Patroni work and what is split-brain?
A.  Patroni uses a distributed consensus store (etcd/Consul/ZooKeeper) to
elect a leader and holds a leader key with TTL. If the leader can't renew,
a replica promotes; old primary is demoted or rewound (pg_rewind).
Fencing and synchronous replication settings reduce split-brain/data
loss. Applications reach the leader via HAProxy/virtual IP/DNS/
pgbouncer.
REAL-WORLD: Practiced switchover and failover drills and tuned TTL and
loop_wait to avoid flapping.

P42. Upgrade options?
A.  pg_upgrade (in-place; --link for seconds-to-minutes downtime; then ANALYZE
or rely on carried-over stats in newer versions), dump/restore (simple but
slow), logical replication (near-zero downtime). Test extensions
compatibility, check release notes, collations (glibc changes can corrupt
indexes), and have a rollback.
REAL-WORLD: Upgraded a 5 TB database with pg_upgrade --link in under 15
minutes of downtime.

----------------------- G. OPERATIONS AND TROUBLESHOOTING ----------------

P43. Configuration files and parameter contexts?
A.  postgresql.conf, postgresql.auto.conf (ALTER SYSTEM), pg_hba.conf (host/
user/db/method rules, top-down first match), pg_ident.conf. Contexts
(pg_settings.context): postmaster (restart), sighup (reload), superuser/
user. Overrides: ALTER ROLE/DATABASE SET, SET LOCAL.
REAL-WORLD: Changed shared_buffers in a maintenance window since it needs
restart; others via pg_reload_conf().

P44. Startup and shutdown modes?
A.  Start via pg_ctl/systemd: reads config, creates shared memory,
startup process does recovery, then accepts connections. Shutdown: smart
(waits for clients), fast (default: disconnect clients, rollback, clean
checkpoint), immediate (abort-like, requires crash recovery on next
start).
REAL-WORLD: Ran CHECKPOINT before a fast shutdown to shorten it.

P45. What does pg_stat_statements track and how?
A.  Per normalized query (queryid): calls, total/mean time, rows, shared/
local/temp blocks hit/read/written, WAL, plan time (if enabled). Stored in
shared memory hash table loaded via shared_preload_libraries. Reset
periodically; capture snapshots externally for trending (no AWR built in).
REAL-WORLD: Exported pg_stat_statements snapshots hourly to build AWR-like
history.

P46. Cumulative statistics system (PG15 change)?
A.  Before PG15 a stats collector process received UDP-like messages and
wrote stats files; from PG15 stats live in shared memory (faster, no
collector, flushed at shutdown/checkpoints). Views: pg_stat_database, user_
tables/indexes, io (PG16), wal, bgwriter, replication, progress views.
REAL-WORLD: Used n_dead_tup and last_autovacuum to monitor vacuum health.

P47. Authentication and security architecture?
A.  pg_hba.conf selects method (scram-sha-256, cert, gss/ldap, peer).
Roles with attributes and inheritance, GRANT on objects/columns, default
privileges, RLS, SECURITY DEFINER functions, TLS, pgaudit, pgcrypto, TDE
isn't in core (use disk/volume encryption or vendor builds).
REAL-WORLD: Replaced md5 with scram-sha-256 and disabled trust rules.

P48. Sequences and identity internals?
A.  A sequence is a special one-row relation; nextval is non-transactional and
logs to WAL in advance (every 32 values) so after crash it may skip
numbers. CACHE per session leaves gaps. Identity columns use an owned
sequence.
REAL-WORLD: Explained gaps to auditors and used a counter table for
legally gap-free numbers.

P49. Temp files, spills and temp tables?
A.  Sorts/hashes exceeding work_mem spill to base/pgsql_tmp (log_temp_files,
EXPLAIN shows Disk usage); temp tables live in temp_buffers/local files per
session, not WAL-logged, dropped at session end (vacuum doesn't auto-
vacuum them - run ANALYZE manually). temp_file_limit protects disk.
REAL-WORLD: Set temp_file_limit for ad hoc users after one query filled disk.

P50. Prepared transactions (2PC)?
A.  PREPARE TRANSACTION persists transaction state until COMMIT PREPARED;
needs max_prepared_transactions > 0. Orphaned prepared transactions hold
locks and block vacuum/freezing - monitor pg_prepared_xacts.
REAL-WORLD: A forgotten prepared transaction stalled autovacuum for weeks.

--------------------------- H. SCENARIO QUESTIONS ------------------------

P51. Database is slow suddenly. What is your approach?
A.  1) pg_stat_activity: active vs idle in transaction, wait events, longest
queries. 2) Locks: pg_blocking_pids. 3) System: CPU, IO wait, memory/swap,
disk latency. 4) pg_stat_statements top queries and plan changes. 5)
Checkpoint/WAL (pg_stat_bgwriter/io, logs). 6) Autovacuum activity or
bloat. 7) Connection storm/pooler saturation. Mitigate (cancel offender,
kill blockers) then RCA.
REAL-WORLD: A connection storm after a deploy exhausted max_connections;
pooler limits and backoff fixed it.

P52. pg_wal is filling the disk. Causes?
A.  Inactive/lagging replication slot, archiver failing (archive_command
errors), standby down with wal_keep_size, long checkpoint settings
(max_wal_size too large relative to disk), heavy write burst. Check
pg_replication_slots, pg_stat_archiver, logs. Never delete WAL files
manually; fix the cause (drop slot, repair archive).
REAL-WORLD: Fixed a broken archive_command permission and ran pg_switch_wal;
WAL drained.

P53. Autovacuum can't keep up and bloat grows. What do you do?
A.  Identify blockers (xmin horizon), check cost throttling, per-table
thresholds, worker count, long transactions, high update churn without HOT,
maintenance_work_mem. Lower scale factors, increase cost limit, raise
fillfactor headroom, schedule manual VACUUM, use pg_repack for existing
bloat. Check I/O capacity.
REAL-WORLD: Reduced table bloat from 70% to 10% in two weeks with tuning
plus one-time repack.

P54. Backend killed by the OOM killer. What next?
A.  Check dmesg/journal, sum potential memory: connections x work_mem x
hash/sort nodes, maintenance_work_mem x autovacuum workers, parallel workers
each using work_mem, shared_buffers + huge pages. Fix: pooling, lower
work_mem globally and raise per-session, vm.overcommit_memory=2 with
sensible overcommit_ratio, use huge_pages, container memory limits.
REAL-WORLD: OOM events stopped after capping work_mem at 16 MB and
using pooling.

P55. How would you explain PostgreSQL architecture in 2 minutes?
A.  "The postmaster forks a backend per connection. Backends share
shared_buffers and WAL buffers. Every change is WAL-logged before data pages
are written; commit is a WAL flush. MVCC stores row versions in the heap
(xmin/xmax), so updates create new tuples and VACUUM cleans old ones; that
makes long transactions and replication slots the main sources of bloat.
Crash recovery is WAL replay only. The planner is cost-based per session,
no shared plan cache. Replication ships WAL (physical) or decoded changes
(logical); HA uses external tools like Patroni; extensibility is a core
strength."

# PART VII: ORACLE vs POSTGRESQL - ARCHITECTURE & PROCESS DIFFERENCES

==========================================================================
 7.1 ONE-PAGE MENTAL MODEL
==========================================================================
 ORACLE                                  POSTGRESQL
 ------                                  ----------
 Instance + Database                     Cluster (postmaster + PGDATA)
 Dedicated server proc per session       Backend process per connection
 (threaded model optional in 12c+)       (forked from postmaster)
 SGA (buffer cache, shared pool,         shared_buffers + WAL buffers +
   redo buffer) + PGA                      local work_mem per backend
 Shared SQL/plan cache (library cache)   No shared plan cache (per-session)
 Undo segments hold OLD versions         Heap holds OLD versions (dead tuples)
 Rollback via undo                       Rollback = just mark xid aborted
 Redo log (circular, groups)             WAL (segments, recycled/archived)
 Commit = LGWR flush                     Commit = WAL flush (+ pg_xact bit)
 Crash recovery: roll forward + back     Crash recovery: WAL replay only
 DBWn + CKPT                             bgwriter + checkpointer
 SMON/PMON housekeeping                  autovacuum + postmaster/startup
 ORA-01555 (undo too small)              Bloat / vacuum blocked
 Data dictionary (SYS), V$ views         System catalogs (pg_*), pg_stat_* views
 AWR/ASH/ADDM (licensed)                 pg_stat_statements, logs, extensions
 RAC (shared-everything)                 Streaming replicas (shared-nothing)
 Data Guard                              Streaming/logical replication + Patroni
 RMAN                                    pg_basebackup/pgBackRest/Barman + WAL

==========================================================================
 7.2 SIDE-BY-SIDE DETAIL
==========================================================================

[1] PROCESS MODEL
 Oracle     : Listener hands connections to dedicated server processes (or
              shared server/DRCP). Many fixed background processes per
              instance (DBWn, LGWR, CKPT, SMON, PMON, ...). On Linux a
              multithreaded model (THREADED_EXECUTION) is available in 12c+.
 PostgreSQL : postmaster forks one backend per connection; a small set of
              background processes. Crash of a backend restarts all.
 Impact     : PG needs a pooler earlier; Oracle copes with many sessions
              better but also benefits from pooling.

[2] MEMORY
 Oracle     : SGA shared (buffer cache, shared pool, redo buffer, etc.),
              PGA private with automatic work-area management against a
              global target (PGA_AGGREGATE_TARGET/LIMIT).
 PostgreSQL : shared_buffers (smaller share of RAM; relies on OS cache),
              per-node work_mem with no global cap - you must reason about
              multiplication yourself.
 Impact     : Oracle memory is globally governed; PG memory can overshoot
              if connections x work_mem are not controlled.

[3] CACHING AND I/O
 Oracle     : Manages most caching itself (direct I/O/ASM typical), multiple
              pools, direct path reads for large scans, Smart Flash Cache.
 PostgreSQL : Buffered I/O (double buffering with OS cache), ring buffers for
              big scans/vacuum. PG18 adds async I/O.
 Impact     : PG performance depends heavily on OS tuning (page cache,
              readahead, huge pages, dirty ratios).

[4] ROW VERSIONING (MOST IMPORTANT DIFFERENCE)
 Oracle     : Current row version in table block; older versions rebuilt
              from UNDO on demand (consistent read). Updates are in-place.
 PostgreSQL : Each UPDATE writes a NEW tuple in the heap; old tuples remain
              until VACUUM. Visibility by xmin/xmax + snapshots.
 Impact     :
   - Oracle: tables don't bloat from updates; risk is ORA-01555 and undo
     sizing; rollback of large transactions is slow (applies undo).
   - PG: ROLLBACK is instant; but updates cost more space/WAL (index
     entries too unless HOT) and VACUUM is a core operational duty;
     long transactions cause bloat.

[5] REDO vs WAL
 Oracle     : Redo logs = change vectors for data AND undo blocks; circular
              groups; archived in ARCHIVELOG mode; used by Data Guard.
 PostgreSQL : WAL = record of page changes (plus full page images after
              checkpoint); segments are archived/recycled; used for
              recovery, PITR, streaming and logical replication.
 Impact     : PG full-page writes increase WAL after checkpoints; Oracle
              logs undo too, increasing redo for updates.

[6] COMMIT, CHECKPOINT, CRASH RECOVERY
 Oracle     : LGWR flush on commit; incremental checkpointing with MTTR
              target; recovery = roll forward (redo) then roll back (undo).
 PostgreSQL : WAL flush on commit; periodic spread checkpoints; recovery =
              WAL replay only (no undo phase).
 Impact     : PG recovery time is bounded by checkpoint distance; Oracle
              additionally may need rollback time for big in-flight txns.

[7] READ CONSISTENCY
 Oracle     : Statement-level (RC) or transaction-level (serializable/
              read-only) via SCN + undo. "Snapshot too old" possible.
 PostgreSQL : Snapshot per statement (RC) or per transaction (RR/SERIAL.).
              Never "snapshot too old" in core (the old_snapshot_threshold
              feature was removed), but vacuum may be blocked by old snapshots.

[8] LOCKING AND ISOLATION
 Oracle     : Row lock info in block (ITL + lock byte), no escalation;
              TM/TX enqueues; latches/mutexes. Isolation: RC, SERIALIZABLE
              (snapshot-based, ORA-08177), READ ONLY.
 PostgreSQL : Row locks in tuple header (xmax/infomask) + multixact; table
              lock modes (8 levels); advisory locks; SSI for SERIALIZABLE
              with 40001 retries; RR = snapshot isolation.
 Impact     : Both: readers don't block writers. Gotchas: PG DDL lock
              queues (lock_timeout), Oracle unindexed FK locks/ITL waits.

[9] SQL PARSING AND PLAN CACHE
 Oracle     : Shared pool library cache - plans shared across sessions,
              hard/soft parse, bind peeking, ACS, SQL plan baselines.
 PostgreSQL : No global plan cache; each backend plans per statement unless
              prepared; generic vs custom plans; poolers affect reuse.
 Impact     : Oracle needs binds to avoid shared-pool pressure; PG planning
              cost matters for very short queries (use prepared statements).

[10] OPTIMIZER AND HINTS
 Oracle     : Rich CBO with adaptive features, SQL profiles, baselines,
              hints widely used, dynamic sampling.
 PostgreSQL : Cost-based, no native hints (pg_hint_plan extension), no plan
              baselines; fixes via stats, indexes, SQL rewrite, settings.
 Impact     : PG tuning = better stats/SQL; Oracle tuning may use hints/SPM.

[11] STATISTICS AND DIAGNOSTICS
 Oracle     : AWR/ASH/ADDM/SQL Monitor/10046 trace (Diagnostics Pack
              licenses), V$ views.
 PostgreSQL : pg_stat_statements, pg_stat_*, auto_explain, logs/pgBadger,
              EXPLAIN (ANALYZE, BUFFERS); history needs external tooling.

[12] SPACE MANAGEMENT
 Oracle     : Segments/extents, ASSM, HWM, SHRINK/MOVE, undo/temp tablespaces,
              rebuild online. Row migration/chaining.
 PostgreSQL : Heap files + FSM/VM, VACUUM, bloat, pg_repack, fillfactor,
              TOAST, HOT. No HWM concept for deletes except trailing page
              truncation.

[13] INDEXING
 Oracle     : B-tree, bitmap, function-based, reverse key, IOT, cluster,
              domain indexes, global/local partitioned indexes, index
              compression. Does not index all-NULL keys in B-tree.
 PostgreSQL : B-tree, hash, GIN, GiST, SP-GiST, BRIN, partial, expression,
              covering (INCLUDE); indexes store NULLs; no bitmap persistent
              index (bitmap scans are runtime), no IOT (CLUSTER is one-time).
              Index entries carry no visibility info -> heap checks (VM helps).

[14] PARTITIONING
 Oracle     : Range/list/hash/composite/interval/reference/auto-list; global
              indexes supported incl. global partitioned; online ops; option
              license needed (Enterprise Edition + Partitioning option).
 PostgreSQL : Range/list/hash declarative; no global indexes; unique keys must
              include partition key; free and built-in.

[15] PROCEDURAL CODE
 Oracle     : PL/SQL with packages (state, init blocks), autonomous
              transactions, BULK COLLECT/FORALL, compile-time dependency
              checking, pipelined functions, wrapped code.
 PostgreSQL : PL/pgSQL (+ PL/Python, etc.), schemas/extensions instead of
              packages, no autonomous transactions, late binding (runtime
              errors), procedures with COMMIT (PG11+), RETURN QUERY.

[16] USERS, SCHEMAS, DATABASES
 Oracle     : Schema = user. One database (or CDB with PDBs) per instance;
              multitenant option for consolidation.
 PostgreSQL : Many databases per cluster; schemas separate from roles; roles
              are cluster-wide; no cross-database queries without FDW.

[17] HIGH AVAILABILITY / SCALING
 Oracle     : RAC (active-active shared storage), Data Guard, GoldenGate,
              ASM, Application Continuity.
 PostgreSQL : Streaming/logical replication, Patroni/repmgr, read replicas;
              sharding via Citus/partitioning/FDW; no built-in active-active
              multi-writer for one database.

[18] BACKUP AND RECOVERY
 Oracle     : RMAN (block-level incremental via change tracking), Flashback
              (Query/Table/Database), Data Guard.
 PostgreSQL : pg_dump + physical backups + WAL PITR (pgBackRest/Barman);
              PG17 incremental; no flashback (use PITR clone or logical
              backups/temporal design).

[19] PARALLELISM
 Oracle     : PX servers with QC, parallel DML/DDL, auto DOP, Resource Manager.
 PostgreSQL : parallel workers for reads/joins/aggregates/index builds;
              parallel DML limited (not for general writes).

[20] SCHEDULING / JOBS
 Oracle     : DBMS_SCHEDULER built in (CJQ0/Jnnn).
 PostgreSQL : external or extension (pg_cron, pgAgent).

[21] SECURITY
 Oracle     : TDE, Database Vault, VPD, Unified Audit, Data Redaction,
              Label Security (options licensed).
 PostgreSQL : RLS, pgaudit, SCRAM, TLS; TDE not in community core
              (OS/volume encryption or vendor builds).

[22] UPGRADES, PATCHING, LICENSING
 Oracle     : RU/PSU patches, AutoUpgrade, rolling patching with RAC/ASM,
              license by core/feature (cost).
 PostgreSQL : Minor releases are binary swaps; major upgrades via pg_upgrade
              or logical replication; open source (cost is people/support).

[23] DATA TYPES AND SQL DIALECT
 Oracle     : '' = NULL, DATE has time, VARCHAR2/NUMBER, ROWNUM, (+) joins,
              CONNECT BY, sequences with NEXTVAL, DUAL, MERGE (old).
 PostgreSQL : '' <> NULL, DATE no time, text/varchar/numeric/timestamptz,
              LIMIT/FETCH, ANSI joins, WITH RECURSIVE, no DUAL, arrays/
              JSONB/range/enum types, ON CONFLICT, MERGE since PG15.

[24] CONNECTION POOLING
 Oracle     : UCP/DRCP/shared server, Proxy Authentication.
 PostgreSQL : PgBouncer/pgcat/Odyssey; transaction-mode pooling needs
              session-stateless apps.

==========================================================================
 7.3 WHAT HAPPENS ON UPDATE + COMMIT - DIRECT COMPARISON
==========================================================================
 ORACLE
   1. Read block into buffer cache; lock row (ITL + lock byte).
   2. Write old value to UNDO; generate redo for undo+data.
   3. Modify row IN PLACE in the block.
   4. COMMIT: LGWR writes redo; locks released; done.
   5. ROLLBACK: apply undo (time proportional to work done).
   6. Readers needing old version: build CR block from undo.

 POSTGRESQL
   1. Read page into shared_buffers; check row visibility; lock row (xmax).
   2. Insert NEW tuple version (same page if HOT possible); set old xmax.
   3. WAL records for heap change (+ index inserts if needed).
   4. COMMIT: WAL flush; pg_xact marked committed.
   5. ROLLBACK: pg_xact marked aborted (instant); dead tuples cleaned by
      VACUUM.
   6. Readers just use snapshot to pick the visible tuple version.

==========================================================================
 7.4 WHAT HAPPENS AT CRASH - DIRECT COMPARISON
==========================================================================
 ORACLE     : SMON roll-forward (redo) -> open -> roll-back using undo.
 POSTGRESQL : Startup process WAL replay from last checkpoint -> open.
              Uncommitted work is simply invisible.

==========================================================================
 7.5 COMPARISON INTERVIEW QUESTIONS (C1-C25)
==========================================================================

C1. Biggest architectural difference between Oracle and PostgreSQL?
A.  Row version storage and concurrency control. Oracle updates in place and
keeps old versions in undo (rebuilt on demand); PostgreSQL appends new tuple
versions in the heap and uses VACUUM. This drives everything else: bloat vs
ORA-01555, rollback speed, WAL/redo volume, index maintenance, HOT, and ops
practices.
REAL-WORLD: I explained it to a team migrating from Oracle so they planned
vacuum monitoring on day one.

C2. Why is rollback instant in PostgreSQL but slow in Oracle?
A.  PG rollback marks the xid aborted; its tuples remain invisible (cleanup
later). Oracle must apply undo records to restore blocks, so a 1-hour
transaction can take comparable time to roll back (and recovery needs it).
REAL-WORLD: Killing a huge Oracle batch took 40 minutes to roll back; the
PG equivalent returned immediately but vacuum cleaned afterwards.

C3. Why does PostgreSQL need VACUUM and Oracle doesn't?
A.  Dead tuple versions live in the PG heap/indexes; they must be reclaimed
and xids frozen. Oracle's old versions live in undo, which is self-managed
(overwritten after retention). Oracle has analogous housekeeping
(shrink, stats, cleanout) but not table-level vacuum.

C4. Compare ORA-01555 with PostgreSQL's equivalents.
A.  Oracle: snapshot too old when undo overwritten. PostgreSQL: query
conflicts on standbys (canceling due to conflict with recovery), vacuum
removing rows needed by old snapshots is prevented by horizon; bloat is
the price. PG's removed old_snapshot_threshold feature mimicked 01555.

C5. How do commits compare (log file sync vs WAL flush)?
A.  Both require sequential log flush before acknowledging. Oracle
"log file sync" with LGWR group commit; PG WAL fsync with group commit via
commit_delay/siblings and WALWriter. Both can use asynchronous commit
(COMMIT WRITE NOWAIT / synchronous_commit=off). Diagnose via wait events
(Oracle: log file sync/parallel write; PG: IO:WALSync/WALWrite).

C6. Compare memory management philosophy.
A.  Oracle manages a large SGA and PGA globally with auto-tuning; PG keeps
moderate shared_buffers and trusts the OS cache, with per-operation work_mem.
Oracle DBA mindset: size SGA/PGA. PG: size shared_buffers modestly, control
connections and work_mem, tune OS.

C7. Plan caching: how do the two differ and what does it mean for developers?
A.  Oracle shares cursors across sessions (bind variables vital to avoid
hard parse storms). PG has per-session plan caching only for prepared
statements/PL/pgSQL; every new connection re-plans, so use pooling +
prepared statements. Bind peeking (Oracle) vs custom/generic plans (PG)
are the analogous plan-stability issues.

C8. How do hints and plan stability differ?
A.  Oracle: hints, SQL profiles, SQL plan baselines, outlines. PG: no hints
in core, rely on stats/extended stats/index/SQL rewrite, config flags,
pg_hint_plan, or application-level query shape. PG teams invest more in
statistics quality and schema design.

C9. How do transaction isolation levels compare?
A.  Both default to READ COMMITTED without dirty reads. Oracle SERIALIZABLE
is snapshot isolation (write skew possible) and errors ORA-08177. PG
REPEATABLE READ is snapshot isolation; PG SERIALIZABLE is true SSI preventing
write skew (with 40001 retries). Oracle has READ ONLY transactions.

C10. Locking: how do large row-lock counts behave in each?
A.  Oracle stores lock state in blocks (no memory cost, no escalation).
PG stores row locks in tuples; locking many rows writes to heap pages
(dirtying them, generating WAL) - SELECT FOR UPDATE on millions of rows is
expensive. Multixacts add cost for shared locks.

C11. Compare index behavior on UPDATE.
A.  Oracle updates in place; index entries change only if the indexed
column changes (delete+insert in index). PG creates a new heap tuple, so
every index needs a new entry unless HOT applies (no indexed column change +
space in page). This is why index count and fillfactor matter more in PG
write-heavy workloads.

C12. Compare how each handles large deletes/purges.
A.  Both: avoid giant DELETEs; use partition drop. Oracle: undo and redo
heavy, rollback slow; HWM remains until shrink. PG: dead tuples + vacuum,
WAL heavy; space reuse after vacuum, not returned to OS (unless trailing
pages or VACUUM FULL/repack). Partition DROP/DETACH is best in both.

C13. Backup/recovery comparison - RMAN vs PG tools?
A.  RMAN: integrated, block-level incrementals, validation, catalog, block
media recovery, Flashback. PG: pg_basebackup/pgBackRest/Barman, WAL
archiving, PITR, pg_dump for logical; PG17 incremental; no flashback.
Both require tested restores and defined RPO/RTO.

C14. HA: RAC vs PostgreSQL clustering?
A.  RAC provides active-active access to one database with Cache Fusion on
shared storage (scale-out for some workloads, HA with fast failover).
PostgreSQL uses a single primary with replicas (shared-nothing) and
failover managers; scale reads with replicas, writes with sharding/
partitioning/Citus or by scaling up. Different failure and scaling models.

C15. Data Guard vs streaming replication?
A.  Both ship redo/WAL to standbys. Data Guard adds Broker, protection modes,
Fast-Start Failover, logical standby and Active Data Guard licensing.
PG streaming replication is built in; failover automation needs Patroni/
repmgr; sync replication is configurable via synchronous_standby_names.

C16. Procedural language differences important in migration?
A.  Packages (spec/body, state) vs schemas/extensions; autonomous
transactions; BULK COLLECT/FORALL vs set-based/unnest; exception handling
semantic (PG subtransaction cost); %TYPE/%ROWTYPE exist in both; cursors
and ref cursors differ; PL/SQL compile-time checks vs PG runtime;
DBMS_* packages (DBMS_OUTPUT, UTL_FILE, DBMS_SCHEDULER, DBMS_LOCK) need
replacements (RAISE NOTICE, COPY/file_fdw, pg_cron, advisory locks).

C17. How do temp tables differ?
A.  Oracle global temporary tables: permanent definition, session/transaction-
private data (private temp tables in 18c+). PG temp tables: created per session
and dropped at session end; no global definition; need ANALYZE manually.

C18. Sequences and identity differences?
A.  Oracle sequences (CACHE, ORDER for RAC, NEXTVAL pseudo-column);
12c identity. PG sequences are relations; nextval function; identity (PG10);
no sequence reset on rollback in both; PG logs 32 values ahead.

C19. Statistics and monitoring: AWR vs PG?
A.  AWR keeps history automatically (licensed); PG keeps cumulative counters
only; you build history via pg_stat_statements snapshots, Prometheus/
Grafana, pgBadger, or commercial tools (pganalyze, pgwatch). Wait-event
interface exists in both (V$ACTIVE_SESSION_HISTORY vs pg_stat_activity
sampling by extensions such as pg_wait_sampling).

C20. Space and storage: tablespaces, datafiles vs PG files?
A.  Oracle: tablespaces of datafiles holding segments, with undo and temp as
special tablespaces and ASM option. PG: one file (1 GB segments) per
relation fork in a directory per database; tablespaces map to directories;
temp in per-DB pgsql_tmp; no undo space.

C21. Multitenancy comparison?
A.  Oracle CDB/PDB (option) shares one instance with isolated PDBs. PG:
multiple databases per cluster (shared processes/WAL, separate catalogs) or
schema-per-tenant/RLS or separate clusters; cross-DB queries not native.

C22. When would you pick Oracle vs PostgreSQL (honest answer)?
A.  Oracle: need RAC active-active, advanced partitioning/global indexes,
mature enterprise features (Data Guard, flashback, Exadata), existing
PL/SQL investment, strict vendor support. PostgreSQL: cost, flexibility,
extensions (PostGIS, TimescaleDB, pgvector), cloud-native, open standards,
strong JSON/SQL features, avoiding licensing lock-in. Decide with
workload, team skills, compliance and TCO.

C23. Key risks when migrating Oracle -> PostgreSQL?
A.  Empty string/NULL semantics, DATE/timestamp, sequences, packages,
autonomous transactions, hierarchical queries, optimizer hints, ROWNUM/
ROWID logic, outer join (+), date arithmetic, case sensitivity of
identifiers, locking/isolation behavior differences, operational shift
(vacuum, pooling), data type mapping (NUMBER -> numeric/int/bigint),
performance regressions from untuned plans. Mitigate with assessment tools
(ora2pg, AWS SCT), phased cutover, parallel run, performance baselines.

C24. Oracle DBA habit that doesn't transfer to PostgreSQL (and vice versa)?
A.  Oracle -> PG: "just throw a hint", "set SGA to 80% RAM", "ignore bloat",
"unlimited sessions". PG -> Oracle: "ignore parse overhead / literals",
"expect instant rollback", "no need for undo sizing", "avoid packages",
"ignore license implications of features/options".

C25. Explain, in one minute, how a transaction flows in both systems.
A.  "Oracle: block in buffer cache, undo + redo generated, in-place change,
commit flushes redo via LGWR, DBWn writes blocks later; readers rebuild old
versions from undo. PostgreSQL: new tuple version inserted in heap, WAL
logged, commit flushes WAL and flips the pg_xact bit; readers use snapshots
to ignore invisible versions; VACUUM cleans dead versions later. Oracle
pays at rollback/read time (undo), PostgreSQL pays at cleanup time
(vacuum/bloat)."

 SECTION A (Oracle SQL/PLSQL): ADVANCED SQL
==========================================================================

OQ1. Difference between ROW_NUMBER, RANK and DENSE_RANK? Where have you used each?
OA1. ROW_NUMBER gives a unique sequence even for ties. RANK leaves gaps after
ties (1,1,3). DENSE_RANK has no gaps (1,1,2).
  - Dedup: ROW_NUMBER() OVER (PARTITION BY key ORDER BY load_ts DESC) = 1
  - "Top 3 salaries including ties": DENSE_RANK <= 3
REAL-WORLD: I used ROW_NUMBER to pick the latest record per business key in
a 200M-row staging table, instead of a self-join with MAX(), which cut run
time significantly because it needed a single pass.

OQ2. Explain window frames: ROWS vs RANGE. Give a running total example.
OA2. ROWS counts physical rows; RANGE groups rows with equal ORDER BY values
(logical). Default frame with ORDER BY is RANGE UNBOUNDED PRECEDING TO CURRENT
ROW, which treats ties together and is slower than ROWS.
  SUM(amt) OVER (PARTITION BY acct ORDER BY txn_dt, txn_id
                 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
REAL-WORLD: Explicit ROWS + a unique tiebreaker column gives deterministic
running balances; the default RANGE gave wrong-looking balances for
same-timestamp transactions in a ledger report.

OQ3. How do you solve "gaps and islands" problems?
OA3. Use the row-number-difference technique:
  SELECT MIN(d) start_d, MAX(d) end_d
  FROM (SELECT d, d - ROW_NUMBER() OVER (ORDER BY d) grp FROM t)
  GROUP BY grp;
Consecutive values share the same grp. LAG/LEAD can also detect gaps
(next_value - value > 1).
REAL-WORLD: Used for finding continuous employee coverage periods and missing
batch-date sequences in a data warehouse load audit.

OQ4. Hierarchical queries: CONNECT BY vs recursive CTE. Which do you prefer?
OA4. CONNECT BY is Oracle-specific, with LEVEL, PRIOR, SYS_CONNECT_BY_PATH,
CONNECT_BY_ISLEAF, CONNECT_BY_ROOT and NOCYCLE. Recursive WITH (11gR2+) is
ANSI, portable, and supports CYCLE clause and SEARCH DEPTH/BREADTH FIRST.
I use recursive CTE for portable code and complex joins, CONNECT BY for quick
Oracle-only tree work.
REAL-WORLD: For BOM (bill of materials) explosion, I used a recursive CTE
with a CYCLE clause to protect against bad data creating infinite loops.

OQ5. Explain MERGE. What are its common pitfalls?
OA5. MERGE does upsert in one statement (WHEN MATCHED UPDATE / WHEN NOT
MATCHED INSERT, optional DELETE WHERE inside matched branch).
Pitfalls:
  - ORA-30926: source returns multiple rows for one target row; dedupe the
    source first.
  - You cannot update columns used in the ON clause.
  - Trigger/row-level behavior and performance with huge sources; make sure
    the join column is indexed or use hash join.
REAL-WORLD: I replaced a row-by-row "try update, if no rows then insert"
loop with MERGE + FORALL staging, reducing a 3-hour load to ~10 minutes.

OQ6. IN vs EXISTS vs JOIN. What is the NOT IN NULL trap?
OA6. The optimizer often transforms IN/EXISTS to semi-joins, so performance is
usually equal on modern versions. Semantic difference matters with NOT IN:
if the subquery returns even one NULL, NOT IN returns no rows (three-valued
logic). NOT EXISTS is NULL-safe. Use NOT EXISTS or anti-join.
REAL-WORLD: A "missing customers" report returned zero rows in production
because one NULL customer_id existed in the subquery. Switching to NOT
EXISTS fixed it, and I added NOT NULL constraints upstream.

OQ7. How do you delete duplicate rows from a huge table safely?
OA7. Options:
  1) DELETE WHERE ROWID IN (SELECT rid FROM (SELECT ROWID rid, ROW_NUMBER()
     OVER (PARTITION BY k ORDER BY ROWID) rn FROM t) WHERE rn > 1)
  2) For very large deletes: CTAS the distinct rows into a new table,
     recreate indexes/constraints/grants, swap names (or EXCHANGE PARTITION).
  Then add a unique constraint so it never happens again.
REAL-WORLD: For a 500M-row table deleting 30% duplicates, CTAS + rename was
faster and generated far less redo/undo than DELETE.

OQ8. Top-N per group - what are your options?
OA8. (a) ROW_NUMBER()/RANK() in an inline view, filter on rank. (b) 12c+
CROSS APPLY / LATERAL with FETCH FIRST n ROWS ONLY per group - great when
the group count is small and there is an index. (c) Aggregate KEEP
(DENSE_RANK FIRST ORDER BY ...) for top-1 values without a subquery.
REAL-WORLD: For "last 3 orders per customer" for 50K customers, LATERAL with
an index on (customer_id, order_dt DESC) avoided sorting the whole table.

OQ9. PIVOT and UNPIVOT - when and limitations?
OA9. PIVOT converts rows to columns using aggregate; UNPIVOT does the reverse.
Limitation: column list must be static in plain SQL (dynamic needs dynamic
SQL or PIVOT XML). UNPIVOT EXCLUDE/INCLUDE NULLS controls null rows.
REAL-WORLD: I generated dynamic pivot SQL in PL/SQL using LISTAGG over the
distinct month list for a reporting layer, validated with DBMS_ASSERT.

OQ10. LISTAGG limits and how do you handle them?
OA10. Result is limited to VARCHAR2 max (4000 or 32767 with extended). Error
ORA-01489 on overflow. 12.2+: LISTAGG(col, ',' ON OVERFLOW TRUNCATE '...'
WITH COUNT). Before that, use XMLAGG with CLOB or a custom aggregate.
REAL-WORLD: Used ON OVERFLOW TRUNCATE for audit descriptions so nightly jobs
stopped failing on unusually large groups.

OQ11. How does NULL behave across SQL features?
OA11. - Comparisons with NULL yield UNKNOWN; use IS NULL.
  - Aggregates ignore NULLs (except COUNT(*)); AVG ignores them in both
    numerator and denominator.
  - Oracle treats empty string as NULL (unlike PostgreSQL/SQL Server).
  - B-tree indexes do not store rows where ALL indexed columns are NULL,
    so WHERE col IS NULL cannot use a single-column index. Add a constant
    column to composite index or use a function-based index.
  - Unique constraints allow multiple rows with NULL on single column.
  - COALESCE short-circuits and accepts many args; NVL evaluates both.
REAL-WORLD: Migrating Oracle to PostgreSQL, the empty-string = NULL
difference caused logic bugs which I found with a targeted test suite.

OQ12. Outer join: condition in ON vs WHERE?
OA12. A filter on the outer-joined table in WHERE turns the LEFT JOIN into an
inner join (NULL rows get filtered out). Put it in ON to preserve outer rows.
REAL-WORLD: A report silently dropped customers with no orders after someone
added WHERE o.status='OPEN'; moving it to ON fixed the totals.

OQ13. UNION vs UNION ALL, and set operators performance?
OA13. UNION sorts/hashes to remove duplicates (extra cost). UNION ALL does
not. Default to UNION ALL unless duplicates are truly possible and unwanted.
MINUS/INTERSECT also do distinct operations. Many MINUS queries are
faster as NOT EXISTS, and INTERSECT as EXISTS, with proper indexes.
REAL-WORLD: Replacing UNION with UNION ALL where inputs were disjoint
partitions removed a large sort step in an ETL view.

OQ14. How does the WITH clause (CTE) behave? Does it materialize?
OA14. Oracle may inline it or materialize into a temp table when referenced
more than once (and the optimizer decides). Hints: /*+ MATERIALIZE */ and
/*+ INLINE */. Materialization helps when an expensive subquery is reused;
inlining helps when predicates can be pushed down.
REAL-WORLD: I forced MATERIALIZE on an expensive aggregation reused three
times in a report, cutting repeated full scans.

OQ15. What are LATERAL / CROSS APPLY / OUTER APPLY used for?
OA15. They let a right-side inline view reference columns from the left row
(12c+). Useful for top-N per row, calling table functions per row, and
JSON_TABLE per row. OUTER APPLY keeps left rows with no match.
REAL-WORLD: Used with JSON_TABLE to flatten nested JSON arrays per order row
in an API-driven integration.

OQ16. What is multi-table INSERT (INSERT ALL / INSERT FIRST)?
OA16. One scan of the source feeds several target tables, optionally with
WHEN conditions. INSERT ALL evaluates all conditions; INSERT FIRST stops at
the first true condition. Efficient for splitting a staging table into
valid / reject / history tables in one pass.
REAL-WORLD: Used INSERT FIRST to route rows into good/quarantine tables
based on validation flags without scanning staging multiple times.

OQ17. Explain Flashback Query and Flashback Table. When did you use them?
OA17. SELECT ... AS OF TIMESTAMP/SCN reads data as it was, based on undo
(limited by UNDO_RETENTION). Flashback Table restores a table (needs row
movement enabled). Flashback Version Query shows row versions between two
points; Flashback Data Archive keeps history long-term.
REAL-WORLD: After an accidental UPDATE without WHERE, I recovered rows
using AS OF TIMESTAMP and a MERGE back into the table, no restore needed.

OQ18. What is MATCH_RECOGNIZE? Give a use case.
OA18. 12c row pattern matching: regex-like patterns across ordered rows
(PARTITION BY, ORDER BY, MEASURES, PATTERN, DEFINE). Use cases: detecting
V-shaped price patterns, consecutive failed logins, session identification.
REAL-WORLD: Detected "3 or more failed payments followed by success" in
fraud analysis; it replaced a messy multi-level LAG query.

OQ19. How do you work with JSON inside Oracle SQL?
OA19. JSON_VALUE (scalar), JSON_QUERY (fragment), JSON_TABLE (relational
projection), JSON_EXISTS, JSON_OBJECT/JSON_ARRAYAGG to generate. Use IS JSON
check constraint, and a JSON search index or function-based indexes on
JSON_VALUE for performance. 21c adds native JSON type.
REAL-WORLD: Stored third-party payloads as JSON in a CLOB with IS JSON
constraint and exposed relational views via JSON_TABLE for reporting.

OQ20. How do you generate a continuous date series, and handle business days?
OA20. SELECT start_dt + LEVEL - 1 FROM dual CONNECT BY LEVEL <= end-start+1;
or recursive CTE. For business days, join to a calendar dimension table
(best practice: holiday flags, fiscal periods) instead of date arithmetic
with hard-coded weekends.
REAL-WORLD: Built a calendar dimension with fiscal periods and holiday flags
that simplified dozens of date-logic queries across reports.

OQ21. Regular expression functions in Oracle?
OA21. REGEXP_LIKE, REGEXP_SUBSTR, REGEXP_REPLACE, REGEXP_INSTR, REGEXP_COUNT.
Useful for validation and parsing but they cannot use normal indexes and are
CPU-heavy; for large tables filter first with cheaper predicates or use a
function-based index.
REAL-WORLD: Used REGEXP_SUBSTR to split delimited legacy fields into rows
(with CONNECT BY LEVEL) during a data migration.

OQ22. Virtual columns, identity columns, invisible columns - practical uses?
OA22. Virtual column: computed on read, can be indexed/partitioned on, helps
avoid function on column in WHERE. Identity (12c): GENERATED ALWAYS / BY
DEFAULT AS IDENTITY replaces sequence+trigger. Invisible columns: hidden from
SELECT * and INSERT without column list, useful for backward-compatible
schema changes.
REAL-WORLD: Added an invisible column during a rolling release so old app
versions kept working while new code populated it.

OQ23. DML error logging and RETURNING clause?
OA23. DBMS_ERRLOG.CREATE_ERROR_LOG + "LOG ERRORS INTO err$_t REJECT LIMIT
UNLIMITED" lets a bulk DML continue past bad rows, recording them. RETURNING
INTO gets values changed (e.g., generated IDs) without a second query, and
works with bulk binds (RETURNING BULK COLLECT INTO).
REAL-WORLD: Used error logging in a 10M-row load so 200 bad rows no longer
rolled back the entire batch.

OQ24. What are analytic vs aggregate functions? Give a ratio example.
OA24. Aggregates collapse rows; analytic functions return a value per row
while looking at a window. Example: percent of department total:
  salary / SUM(salary) OVER (PARTITION BY dept_id)
Also RATIO_TO_REPORT, NTILE, PERCENT_RANK, FIRST_VALUE/LAST_VALUE (watch the
default frame; use ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING).
REAL-WORLD: LAST_VALUE returned wrong results until I set the full frame; a
classic bug I now check in code reviews.

OQ25. How do you do pagination correctly?
OA25. 12c: ORDER BY id OFFSET n ROWS FETCH NEXT m ROWS ONLY. For deep pages,
OFFSET is slow (it still reads skipped rows); use keyset pagination:
WHERE (sort_col, id) > (:last_sort, :last_id) ORDER BY sort_col, id
FETCH FIRST m ROWS ONLY, backed by a composite index. ORDER BY must be
deterministic (add unique tiebreaker).
REAL-WORLD: Switched an API from OFFSET to keyset pagination; page-500
latency dropped from seconds to milliseconds.

==========================================================================
 SECTION B (Oracle SQL/PLSQL): PERFORMANCE TUNING & OPTIMIZER
==========================================================================

OQ26. How do you read an execution plan? What do you look at first?
OA26. Get the REAL plan, not just EXPLAIN PLAN:
  SELECT /*+ gather_plan_statistics */ ...;
  SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL,NULL,'ALLSTATS LAST'));
Compare E-Rows (estimated) with A-Rows (actual). Large mismatch = bad
statistics/cardinality, the root cause of most bad plans. Then check access
paths, join order/method, Starts, Buffers (logical IO), and predicate section
(access vs filter predicates).
REAL-WORLD: A query estimated 10 rows but returned 2M; extended statistics on
two correlated columns fixed the estimate and the plan flipped to hash join.

OQ27. Query was fast yesterday and slow today. How do you investigate?
OA27. 1) Same plan? Compare PLAN_HASH_VALUE in V$SQL / AWR (DBA_HIST_SQLSTAT).
2) Statistics changed/stale, new histograms? 3) Bind peeking with different
values? 4) Data volume growth, partition added? 5) Concurrency/locks/IO
waits (ASH)? 6) Parameter/patch change? Restore a good plan via SQL Plan
Baseline while root cause is fixed.
REAL-WORLD: Month-end skew made bind peeking choose a nested-loop plan for
a huge bind value; adaptive cursor sharing + histogram resolved it.

OQ28. Types of indexes and when to use each?
OA28. - B-tree: default, high-cardinality, OLTP.
  - Bitmap: low cardinality, DW/read-mostly; bad for concurrent DML (locks
    many rows).
  - Function-based: for UPPER(name), TRUNC(date), virtual column alternative.
  - Composite: column order matters (equality columns first, then range).
  - Reverse key: reduces right-hand block contention on sequences (but kills
    range scans).
  - Index-organized table: data stored in the PK index; great for lookup
    tables accessed by PK.
  - Local/global partitioned indexes.
REAL-WORLD: Replaced several single-column indexes with one composite index
matching the main access pattern, improving DML speed and plan stability.

OQ29. Composite index: how to choose column order? What is skip scan?
OA29. Put columns used with equality first, range last; consider selectivity
and whether leading columns are always present in queries. Index skip scan
lets Oracle use an index when the leading column is omitted, but only
efficient when that leading column has very few distinct values.
REAL-WORLD: Tuned (status, customer_id, created_dt) vs (customer_id,
created_dt, status) by checking actual query predicates via AWR SQL.

OQ30. Index exists but is not used. Why?
OA30. - Function/implicit conversion on the column (TO_CHAR(col), VARCHAR2
    compared to NUMBER).
  - Leading column missing; low selectivity so full scan is cheaper.
  - Stale/missing stats; NULL-only issue (IS NULL on nullable single col).
  - LIKE '%abc' leading wildcard.
  - Data type mismatch/NLS settings; different datatype in bind.
  - Index invisible/unusable; optimizer_index_cost_adj settings.
REAL-WORLD: A numeric-looking VARCHAR2 column compared to a NUMBER bind
caused implicit TO_NUMBER on the column and a full scan; fixed bind type.

OQ31. Explain nested loop, hash join and sort-merge join - when each wins.
OA31. Nested loops: small driving set + indexed lookup on inner side (OLTP).
Hash join: large unsorted sets, equi-joins; builds hash table on smaller
input (watch PGA/temp spill). Sort-merge: non-equi joins or already sorted
inputs. Wrong choice usually traces back to cardinality estimates.
REAL-WORLD: A report forced into nested loops over 5M rows took 40 minutes;
a hash join with full scans took 90 seconds after stats fix.

OQ32. Bind variables: benefits and the bind peeking problem?
OA32. Binds enable soft parse and cursor sharing, reduce shared pool pressure
and protect against SQL injection. Downsides: bind peeking creates a plan
for first value, which can be bad for skewed data. Adaptive Cursor Sharing
(11g+) can create multiple child cursors for skewed binds.
REAL-WORLD: Diagnosed using V$SQL_CS_HISTOGRAM and BIND_AWARE columns.

OQ33. How do you manage optimizer statistics in production?
OA33. Use DBMS_STATS (not ANALYZE), AUTO_SAMPLE_SIZE, METHOD_OPT with
SIZE AUTO, incremental stats for partitioned tables, extended stats for
column groups/expressions, lock stats on volatile staging tables, and
gather stats immediately after big loads. Preserve history (restore
via DBMS_STATS.RESTORE_TABLE_STATS) and test in pre-prod using pending stats.
REAL-WORLD: Made stats gathering part of the ETL job end step for the
partition just loaded rather than relying only on the nightly window.

OQ34. When do you use hints? What are the alternatives?
OA34. Hints are a last resort because they hard-code decisions that go stale.
Better: fix statistics, add indexes, rewrite SQL. If a plan must be pinned:
SQL Plan Management (baselines), SQL Profiles, or SQL Patch. Legit hints:
APPEND, PARALLEL, MATERIALIZE, LEADING/USE_HASH in well-understood batch jobs.
REAL-WORLD: I used a SQL Plan Baseline to stabilize a critical query after
an upgrade instead of embedding hints in application code.

OQ35. Hard parse vs soft parse. How do you reduce parsing?
OA35. Hard parse: syntax, semantic, optimization - expensive, takes latches
on library cache. Soft parse reuses cursor. Reduce by using bind variables,
avoid literal SQL in dynamic SQL, use PL/SQL static SQL (cached cursors),
SESSION_CACHED_CURSORS. CURSOR_SHARING=FORCE is a band-aid.
REAL-WORLD: Found a legacy module concatenating literals; AWR showed high
parse CPU. Rewriting with binds reduced CPU by ~25%.

OQ36. How does partition pruning work and how do you verify it?
OA36. Optimizer eliminates partitions based on predicates on the partition key
(static or dynamic via bind/subquery). Verify in the plan: Pstart/Pstop
columns (KEY, KEY(I) or specific numbers). Pruning fails when functions wrap
the partition key or datatypes mismatch.
REAL-WORLD: A TRUNC(txn_date) predicate prevented pruning; changing to range
predicates (>= and <) reduced scans from 60 partitions to 1.

OQ37. A batch query runs 2 hours. Walk me through your tuning method.
OA37. 1) Capture actual plan with row-source stats. 2) Find the step with
most time/buffers. 3) Check estimates vs actuals. 4) Verify stats, indexes,
partition pruning, join order. 5) Check waits (ASH/SQL Monitor): IO, temp,
locks. 6) Consider rewrites: push filters early, remove unnecessary
DISTINCT/ORDER BY, replace scalar subqueries with joins, use analytic
functions. 7) Consider parallelism/direct-path/partition-wise joins.
8) Measure after each change; keep a before/after log.
REAL-WORLD: Reduced a 2h reconciliation job to 9 minutes by eliminating a
scalar subquery executed per row and using a hash join.

OQ38. What is clustering factor and why does it matter?
OA38. It measures how well table row order matches index order. Low (close to
block count) = good, range scans touch fewer table blocks. High (close to row
count) = poor; optimizer may prefer full scan. Fix by reorganizing data
(CTAS ordered by index key), or use IOT / partitioning, rather than rebuilding
the index (rebuild doesn't change it).
REAL-WORLD: A "good" index was ignored because the clustering factor was
near the row count; reloading data ordered by key made it useful.

OQ39. Materialized views: refresh types and when to use?
OA39. Refresh methods: COMPLETE, FAST (needs MV logs), FORCE; modes ON
DEMAND / ON COMMIT. Query rewrite lets optimizer use the MV transparently.
Fast refresh requires restrictions and MV logs overhead on base tables. For
heavy aggregation reporting, MV with partition change tracking (PCT) is
very effective. Atomic_refresh=FALSE uses truncate + insert (faster).
REAL-WORLD: Built daily aggregate MVs with fast refresh for dashboards,
dropping dashboard query time from 40s to under 2s.

OQ40. What tools do you use for diagnosing performance?
OA40. SQL Trace/TKPROF (10046), DBMS_XPLAN, AWR/ASH/ADDM reports, SQL Monitor
(real-time for long-running/parallel), V$SESSION_WAIT / V$ACTIVE_SESSION_
HISTORY, DBMS_APPLICATION_INFO for tagging, SQL Tuning Advisor, PL/SQL
hierarchical profiler (DBMS_HPROF).
REAL-WORLD: Used ASH to prove a slow job was waiting on "enq: TX - row lock
contention" rather than a bad plan, saving days of misdirected tuning.

OQ41. How do you tune parallel query/DML? Risks?
OA41. Use PARALLEL hints or table DOP, ALTER SESSION ENABLE PARALLEL DML for
DML. Benefits: big scans/joins/loads. Risks: resource exhaustion, skew, uses
direct path (needs commit before reading), many parallel slaves hurting OLTP.
Check "PX Deq" waits and distribute method in plan.
REAL-WORLD: Limited DOP to 8 for nightly batch using Resource Manager so it
didn't starve online users.

OQ42. When do you use RESULT_CACHE?
OA42. For frequently executed queries/functions over slowly changing data
(lookup tables). SQL hint /*+ RESULT_CACHE */ or function RESULT_CACHE.
Invalidated on any DML to dependencies, so avoid for volatile data. Watch
latch contention under extreme concurrency.
REAL-WORLD: Cached a currency-rate lookup function; reduced repeated calls
by millions per day.

OQ43. Direct-path insert and NOLOGGING - how and trade-offs?
OA43. INSERT /*+ APPEND */ writes above the high-water mark, bypassing the
buffer cache, generating minimal undo (and minimal redo if NOLOGGING or
table in NOLOGGING mode and not in FORCE LOGGING/Data Guard). Trade-offs:
table locked exclusively until commit, space not reused from deleted
blocks, recoverability concerns with NOLOGGING (take backup after), a
direct-path-loaded table can't be queried in same transaction.
REAL-WORLD: Used APPEND + parallel for monthly 100M row loads, with a
backup after completion as per DBA policy.

OQ44. Sargability: how to write predicates that can use indexes?
OA44. Avoid functions on the indexed column. Instead of TRUNC(dt)=:d use
dt >= :d AND dt < :d + 1. Instead of col + 0 = 10, col = 10. Instead of
SUBSTR(col,1,3)='ABC', col LIKE 'ABC%'. Match datatypes. If function is
unavoidable, create a function-based index.
REAL-WORLD: Rewriting date predicates across a reporting package made
several full scans disappear.

OQ45. High water mark, row chaining/migration, PCTFREE - explain.
OA45. HWM is the boundary of used blocks; full scans read up to it, so a
table with lots of deletes still scans many empty blocks. Fix with
ALTER TABLE ... SHRINK SPACE (row movement) or MOVE. Row migration
occurs when updates grow rows beyond free space; PCTFREE reserves room.
Chaining happens when a row is too big for one block.
REAL-WORLD: Shrinking a queue table that held 1M deleted rows cut full-scan
time from seconds to milliseconds.

OQ46. Common wait events and what they imply?
OA46. db file sequential read (single-block, index lookups); db file
scattered read (multiblock, full scans); direct path read/write (parallel/
temp); enq: TX row lock contention (app locking); log file sync (too many
commits); latch/library cache (parsing); buffer busy waits (hot blocks).
REAL-WORLD: High "log file sync" was due to commit inside a loop; moving the
commit outside the loop fixed it.

OQ47. Scalar subquery in SELECT list: problem and fix?
OA47. A correlated scalar subquery can execute once per row (although
Oracle's scalar subquery caching helps for repeated inputs). Fix: join/outer
join with aggregation, or analytic function. Wrapping function calls in
(SELECT func(x) FROM dual) enables caching and reduces context switches.
REAL-WORLD: Replaced three scalar lookups with one outer join; runtime fell
from 30 minutes to 3.

==========================================================================
 SECTION C (Oracle SQL/PLSQL): PL/SQL ADVANCED
==========================================================================

OQ48. Why use packages instead of standalone procedures?
OA48. Encapsulation (public spec vs private body), modularity, overloading,
session-level state, one-time initialization, better dependency handling
(changing the body doesn't invalidate dependents; changing the spec does),
whole package loaded in memory on first call, and easy grant management.
REAL-WORLD: I structured code as layered packages (API / business logic /
data access) so UI callers depended only on stable specs.

OQ49. What is package state and what problems can it cause?
OA49. Package-level variables persist for the session. Issues: ORA-04068
("existing state of packages has been discarded") after recompilation in
connection-pooled apps; memory growth with large collections; unexpected
behavior with pooled sessions sharing state. Mitigate: avoid state, use
PRAGMA SERIALLY_REUSABLE for large temp state, or handle 04068 by retry.
REAL-WORLD: After a hot deployment, app servers threw ORA-04068; I removed
cached state from the package and moved it to a table/result cache.

OQ50. Explicit cursor vs implicit cursor vs cursor FOR loop vs REF CURSOR?
OA50. Implicit: SQL%ROWCOUNT, SQL%FOUND after DML/SELECT INTO. Explicit:
OPEN/FETCH/CLOSE for control. Cursor FOR loop: auto open/close and, since
10g, array-fetches 100 rows automatically. REF CURSOR/SYS_REFCURSOR returns
result sets to callers (Java/.NET). Strongly typed REF CURSOR checks the
shape at compile time.
REAL-WORLD: Exposed reporting data to .NET as SYS_REFCURSOR OUT params with
a stable column contract documented in the spec.

OQ51. BULK COLLECT - benefits and the LIMIT clause?
OA51. Fetches many rows with one context switch between PL/SQL and SQL engine.
Unbounded BULK COLLECT can exhaust PGA memory. Use LIMIT (100-1000):
  LOOP
    FETCH c BULK COLLECT INTO l_tab LIMIT 500;
    EXIT WHEN l_tab.COUNT = 0;   -- not c%NOTFOUND (would skip last batch)
    ...
  END LOOP;
REAL-WORLD: Fixed an out-of-memory ORA-04030 in a batch job by adding
LIMIT 1000 to an unbounded BULK COLLECT.

OQ52. FORALL: how does it work? SAVE EXCEPTIONS, INDICES OF, VALUES OF?
OA52. FORALL sends the whole DML batch to the SQL engine in one switch.
SAVE EXCEPTIONS continues past failing rows and raises ORA-24381; details
in SQL%BULK_EXCEPTIONS(i).ERROR_INDEX / ERROR_CODE. INDICES OF handles
sparse collections; VALUES OF drives from another collection of indexes.
It is not a loop - only a single DML statement is allowed in the body.
REAL-WORLD: Loaded 5M rows with FORALL + SAVE EXCEPTIONS, writing failed
rows to a reject table with error codes, 20x faster than row-by-row.

OQ53. Collection types: associative arrays, nested tables, VARRAYs?
OA53. Associative array (INDEX BY): PL/SQL only, sparse, key by number or
string, fast lookups (great as in-memory cache/map). Nested table: can be
stored in DB columns, sparse after delete, supports MULTISET operators and
TABLE(). VARRAY: bounded, ordered, dense, stored inline. Use associative
arrays for lookups, nested tables for SQL interaction.
REAL-WORLD: Replaced repeated lookup queries inside a loop with an
associative array cache keyed by code, eliminating thousands of queries.

OQ54. What are pipelined table functions?
OA54. Functions that return rows as produced (PIPE ROW) so the consumer can
start processing before the function ends, saving memory. Used in ETL
(transform stage) and with PARALLEL_ENABLE + REF CURSOR for parallel
pipelines. Query via SELECT * FROM TABLE(fn(...)).
REAL-WORLD: Built a pipelined parser for flat-file lines (external table
source) and fed it straight into INSERT ... SELECT.

OQ55. Best practices for exception handling in PL/SQL?
OA55. - Handle only what you can; let others propagate.
  - Avoid WHEN OTHERS THEN NULL. If used, log and re-raise (RAISE).
  - Use DBMS_UTILITY.FORMAT_ERROR_BACKTRACE (and FORMAT_ERROR_STACK) to
    keep the original line number; RAISE preserves it, RAISE_APPLICATION_
    ERROR(-20001..-20999) does not.
  - PRAGMA EXCEPTION_INIT to name standard ORA- errors.
  - An exception in the declaration section is not caught by the same
    block's handler.
  - Logging must use an autonomous transaction so it survives rollback.
REAL-WORLD: Created a central error-logging package (error code, stack,
backtrace, call stack, session info) used across 300+ procedures.

OQ56. What is an AUTONOMOUS_TRANSACTION? Use cases and dangers?
OA56. A PRAGMA making a subprogram run in an independent transaction that
must commit/rollback itself. Good for audit/error logging, sequence
number tables. Dangers: it doesn't see uncommitted data of parent (may
deadlock if it touches same rows), hidden commits harm atomicity, and
overuse hides design flaws.
REAL-WORLD: Used only in the logging package; code reviews rejected other
uses.

OQ57. Mutating table error (ORA-04091) - cause and fixes?
OA57. Row-level trigger reads/modifies the table that fired it. Fixes:
compound trigger (collect keys in AFTER EACH ROW, process in AFTER
STATEMENT) - best modern solution; or statement-level trigger with package
collection (older way); or redesign to avoid trigger logic (constraints,
APIs). Avoid autonomous transaction hack: gives inconsistent reads.
REAL-WORLD: Replaced a package-variable workaround with a compound trigger
to enforce a cross-row rule safely.

OQ58. Triggers - when to avoid? Compound triggers?
OA58. Triggers hide logic, hurt bulk performance, complicate debugging, and
can cascade. Use for auditing, enforcing complex integrity not expressible
declaratively, and DDL/logon events. Compound trigger has BEFORE
STATEMENT, BEFORE/AFTER EACH ROW, AFTER STATEMENT sections sharing state
in a single unit.
REAL-WORLD: Moved business rules from triggers into a PL/SQL API package;
triggers kept only for audit.

OQ59. Dynamic SQL: EXECUTE IMMEDIATE vs DBMS_SQL; SQL injection protection?
OA59. EXECUTE IMMEDIATE is simple and fast for known number of binds. DBMS_SQL
is needed when columns/binds count are unknown at compile time (describe
columns, bind dynamically). Prevent injection: always use bind variables
(USING), validate identifiers with DBMS_ASSERT.SIMPLE_SQL_NAME /
ENQUOTE_NAME / SQL_OBJECT_NAME, never concatenate user input.
REAL-WORLD: Built a generic export procedure using DBMS_SQL.DESCRIBE_COLUMNS
and DBMS_ASSERT validation for table names.

OQ60. Definer's rights vs invoker's rights?
OA60. Default is definer's rights: runs with owner's privileges (good for
controlled access via packages; roles are disabled inside). AUTHID
CURRENT_USER runs with caller's privileges (roles enabled), used for
generic utilities that should respect caller's access, or multi-schema
deployments sharing code.
REAL-WORLD: Exposed data through definer-rights packages so reporting users
had no direct table grants.

OQ61. Calling PL/SQL functions from SQL: issues and solutions?
OA61. Each call incurs context switch; functions with side effects violate
purity rules; can break read consistency if the function runs its own queries
(statement-level consistency per call). Options: PRAGMA UDF (12c) to reduce
overhead, WITH FUNCTION clause (12c), DETERMINISTIC (for same input same
output) , RESULT_CACHE, scalar subquery caching, or rewrite in pure SQL.
REAL-WORLD: Rewriting a per-row formatting function as a SQL expression cut
a report from 12 min to 1.

OQ62. What is a context switch and how do you minimize it?
OA62. Transition between PL/SQL engine and SQL engine; each costs CPU. Minimize
by using set-based SQL, BULK COLLECT, FORALL, avoiding functions in SQL
that call SQL, PRAGMA UDF, and pushing logic into a single SQL statement.
REAL-WORLD: Converted a 4-level nested cursor loop into a single INSERT ...
SELECT with joins.

OQ63. How do you implement logging and instrumentation?
OA63. Central logging package with levels (DEBUG/INFO/ERROR), autonomous
transaction inserts, correlation ID per run, DBMS_APPLICATION_INFO (module/
action/client_info, SET_SESSION_LONGOPS), and optional toggle via config
table. Keep logging overhead low in tight loops (log per batch).
REAL-WORLD: Long-running ETL steps updated V$SESSION_LONGOPS so support
could see progress without logging into the DB.

OQ64. Overloading and forward declarations?
OA64. Overloading: same name, different parameter signatures (number/types/
order), only in packages/local blocks, not by return type or by subtypes with
identical base types. Forward declaration lets a private subprogram be
referenced before its definition in the package body.
REAL-WORLD: Overloaded a LOG procedure for different message types.

OQ65. DBMS_SCHEDULER vs DBMS_JOB?
OA65. DBMS_SCHEDULER (10g+) supports calendaring syntax, job chains,
dependencies, resource consumer groups, logging history, event-based jobs,
remote/file watchers, job classes. DBMS_JOB is legacy and limited. Always use
Scheduler for new work.
REAL-WORLD: Built a job chain (load -> validate -> aggregate -> notify) with
conditional steps and automatic retry on failure.

OQ66. Reading/writing files with UTL_FILE and external tables?
OA66. UTL_FILE needs DIRECTORY objects and grants (READ/WRITE on directory);
good for generating files. For loading, external tables (ORACLE_LOADER or
ORACLE_DATAPUMP) let you query files with SQL, in parallel, with REJECT
LIMIT and bad/log files; prefer them for bulk ingestion.
REAL-WORLD: Replaced a UTL_FILE parser (slow, line-by-line) with an external
table + INSERT SELECT; load time dropped from 40 to 4 minutes.

OQ67. Conditional compilation?
OA67. $IF / $THEN / $ELSE / $END with $$PLSQL_UNIT, $$PLSQL_LINE and
PLSQL_CCFLAGS (e.g., 'debug:true'), or version checks with DBMS_DB_VERSION.
Useful for supporting multiple DB versions or removing debug code in prod.
REAL-WORLD: Used a debug flag so test builds had assertions with no cost in
production.

OQ68. Dependencies and invalidation - how do you manage them?
OA68. USER_DEPENDENCIES shows relations; DDL on a table invalidates
dependents. 11g fine-grained dependency tracking avoids invalidation when
unrelated columns change. Recompile with UTL_RECOMP/ALTER ... COMPILE.
Edition-Based Redefinition (EBR) enables online application upgrades with
editioning views and cross-edition triggers.
REAL-WORLD: Planned releases to compile packages in dependency order and
validate zero INVALID objects before go-live.

OQ69. NOCOPY hint and parameter modes?
OA69. IN passes by reference (read-only), OUT/IN OUT pass by value (copy in/
copy out) which is costly for big collections; NOCOPY requests pass by
reference. Caveat: if an exception occurs, changes are not rolled back to
the original value (partially modified).
REAL-WORLD: Used NOCOPY on collection IN OUT params of a transformation
package to cut memory copying.

OQ70. How do you handle LOBs efficiently?
OA70. Use SecureFiles, DBMS_LOB (READ, WRITE, SUBSTR, APPEND), temporary LOBs
(free them!), avoid converting CLOB to VARCHAR2 repeatedly, use chunked
reads, compression/dedup in SecureFiles, and store LOBs in separate
tablespace; avoid SELECT * when LOBs are present.
REAL-WORLD: Fixed a temp tablespace growth issue caused by unreleased
temporary LOBs (missing DBMS_LOB.FREETEMPORARY).

OQ71. Object types and member functions - have you used them?
OA71. CREATE TYPE with attributes and methods (MEMBER, STATIC, MAP/ORDER);
used for table functions returning rows, collections of objects and
APIs with structured parameters. Caution: evolving types (ALTER TYPE
CASCADE) can be painful, so keep them for interface/in-memory structures.
REAL-WORLD: Used object collection types as bulk input parameters from Java
(array binding) into PL/SQL APIs.

OQ72. Associative array indexed by VARCHAR2 - use case?
OA72. Fast in-memory dictionary: l_map(code) := value; check l_map.EXISTS
(code). Traverse with FIRST/NEXT. Great for dedupe in-memory, caching lookup
data inside a batch, and grouping.
REAL-WORLD: Built a per-run cache of reference data to avoid millions of
repeated lookups.

OQ73. Slow-by-slow processing: how do you spot and fix it?
OA73. Symptoms: loop with SQL statements inside, row-level commits, high
executions with small rows in AWR. Fix: single SQL (INSERT SELECT/MERGE),
analytic functions, bulk operations, or at least BULK COLLECT/FORALL.
Remember: the fastest PL/SQL loop is the one you don't write.
REAL-WORLD: Reviewed AWR "SQL ordered by Executions", found a statement
executed 20M times per run; collapsed to one MERGE.

OQ74. How do you profile PL/SQL code?
OA74. DBMS_PROFILER (older, line-level) and DBMS_HPROF (hierarchical,
subprogram-level with call hierarchy, 11g+), plus PL/Scope for static
analysis (finding unused variables, SQL in code). Use to find hot spots
before optimizing.
REAL-WORLD: HPROF revealed 70% time in a tiny validation function called
per row; made it SQL-expression based.

OQ75. How do you unit test and deploy PL/SQL?
OA75. utPLSQL for unit tests (annotations, test suites, code coverage),
version-controlled scripts (Git), CI pipeline (Jenkins/GitLab) with
Liquibase/Flyway or scripted migrations, repeatable deployments, post-
deploy invalid object check, rollback plan, code review checklist.
REAL-WORLD: Introduced utPLSQL tests for core calculation packages; caught
regression bugs before UAT.

OQ76. DBMS_LOCK / DBMS_PIPE / DBMS_ALERT / AQ - when used?
OA76. DBMS_LOCK.REQUEST/ALLOCATE_UNIQUE (user locks to serialize processes,
e.g., ensure only one instance of a job runs); DBMS_ALERT and AQ for
messaging; AQ (Advanced Queuing) for reliable transactional queues.
Prefer AQ over polling tables.
REAL-WORLD: Used a named lock to prevent concurrent runs of a
non-reentrant batch procedure.

OQ77. Collection methods and gotchas?
OA77. EXISTS, COUNT, LIMIT, FIRST, LAST, NEXT, PRIOR, EXTEND, TRIM, DELETE.
Gotchas: nested tables must be initialized and EXTENDed; DELETE makes
nested tables sparse so use FIRST/NEXT instead of 1..COUNT loops; COUNT
doesn't equal LAST when sparse; ORA-06533 subscript beyond count.
REAL-WORLD: Fixed an intermittent ORA-06533 caused by looping 1..COUNT on a
sparse nested table.

OQ78. What does your PL/SQL code review checklist include?
OA78. Set-based first; no WHEN OTHERS without re-raise; bind variables; no
hard-coded values; bulk ops with LIMIT; commit/transaction control only at
the outermost layer; naming standards; no SELECT *; %TYPE/%ROWTYPE usage;
meaningful logging; privileges and AUTHID; unit tests; no unnecessary
cursor loops; compile with PLSQL_WARNINGS enabled.
REAL-WORLD: Introduced a checklist and static analysis (PL/Scope) in the
pull request process.

OQ79. PLSQL_WARNINGS and optimization levels?
OA79. ALTER SESSION SET PLSQL_WARNINGS='ENABLE:ALL' flags performance and
severe issues (unreachable code, missing RETURN). PLSQL_OPTIMIZE_LEVEL:
2 default (inlining possible), 3 aggressive inlining; PRAGMA INLINE for
control. Native compilation improves compute-heavy code, not SQL-heavy code.
REAL-WORLD: Enabled warnings in CI so builds fail on severe warnings.

OQ80. How do you design a large data migration job in PL/SQL?
OA80. Stage -> validate -> transform -> load pattern. Use set-based SQL or
bulk processing with LIMIT, checkpoint/restart table (batch id, last key),
partition-wise processing and parallel execution, disable/recreate indexes
only if justified, error table with reason codes, reconciliation counts and
checksums at the end, rehearse in pre-prod with production-like volume.
REAL-WORLD: Migrated ~800M rows in a weekend window with restartable chunks
and reconciliation reports signed off by business.

==========================================================================
 SECTION D (Oracle SQL/PLSQL): TRANSACTIONS, LOCKING, CONCURRENCY
==========================================================================

OQ81. Explain Oracle read consistency, undo and ORA-01555.
OA81. Queries see a snapshot as of query start (statement-level) using undo
to rebuild old block versions; readers don't block writers. ORA-01555
"snapshot too old" occurs when needed undo was overwritten. Causes: long
queries, small UNDO_RETENTION/undo tablespace, commits inside a fetch loop
across the same table being updated (fetch across commit). Fix: tune undo,
shorten queries, commit after the loop, or use retention guarantee.
REAL-WORLD: Fixed recurring 01555 by removing commit-inside-cursor-loop and
sizing undo to hold 2 hours of changes.

OQ82. Isolation levels in Oracle?
OA82. READ COMMITTED (default, statement-level consistency) and SERIALIZABLE
(transaction-level; may throw ORA-08177 can't serialize), plus READ ONLY.
Oracle doesn't allow dirty reads. Non-repeatable reads and phantoms are
possible under READ COMMITTED.
REAL-WORLD: Used SET TRANSACTION READ ONLY so a multi-query month-end
report saw one consistent point in time.

OQ83. Types of locks in Oracle? SELECT FOR UPDATE options?
OA83. TX (row/transaction lock), TM (table lock; modes RS, RX, S, SRX, X).
Row-level locking with no escalation. SELECT FOR UPDATE variations:
NOWAIT (error immediately), WAIT n (timeout), SKIP LOCKED (skip rows locked
by others), OF column (which table's rows to lock).
REAL-WORLD: Worker processes picked queue rows with FOR UPDATE SKIP LOCKED
so many workers ran in parallel without contention.

OQ84. How do you find and resolve blocking sessions and deadlocks?
OA84. Use V$SESSION (BLOCKING_SESSION), V$LOCK, DBA_BLOCKERS/WAITERS, ASH.
Deadlock (ORA-00060): Oracle detects and rolls back one statement; trace
file shows graph. Prevent by consistent lock order, shorter transactions,
indexing foreign keys (unindexed FKs cause table-level locks / deadlocks).
REAL-WORLD: Deadlocks vanished after indexing an unindexed child FK column
in a parent-child delete scenario.

OQ85. Lost updates: pessimistic vs optimistic locking?
OA85. Pessimistic: SELECT FOR UPDATE before updating. Optimistic: version
column or ORA_ROWSCN; UPDATE ... WHERE id=:id AND version=:v; check
SQL%ROWCOUNT, raise conflict if 0. Optimistic suits web apps with
disconnected sessions.
REAL-WORLD: Implemented version-column checks in the API layer for
concurrent edits by multiple users.

OQ86. Sequences: gaps, caching, RAC?
OA86. Sequences are not gap-free (rollbacks, cache aging out, restarts);
never use them for legal gap-free numbering (use a counter table with
locking if truly required). CACHE improves performance; with RAC use
CACHE + NOORDER for scalability; ORDER only if strict ordering needed.
12c identity columns and DEFAULT seq.NEXTVAL simplify use.
REAL-WORLD: Invoice numbers required gap-free; used a dedicated counter
table with serialized access, and kept sequences for surrogate keys.

OQ87. Constraints: deferrable, ENABLE NOVALIDATE, and FK indexing?
OA87. Deferrable constraints are checked at commit (useful for circular
inserts or bulk loads). ENABLE NOVALIDATE enforces for new data without
checking existing rows (quick for legacy data). RELY/DISABLE for DW.
Index foreign key columns to avoid locking and slow parent deletes.
REAL-WORLD: Loaded parent and child in any order using INITIALLY DEFERRED
constraints during a migration.

OQ88. Commit strategy in batch processing?
OA88. Commit per batch (e.g., every 10K-100K rows) with restartable
checkpoints, never per row (log file sync) and not in the middle of a
cursor fetch on same data (ORA-01555). For all-or-nothing business logic,
commit once at end. Keep transaction control in the outermost procedure,
not in reusable lower-level code.
REAL-WORLD: Changed commit-every-row to commit-per-10K, slashing runtime
from 3 hours to 25 minutes.

OQ89. How would you build a safe queue-processing table?
OA89. Table with status, picked_by, picked_ts. Workers claim rows:
  SELECT id FROM q WHERE status='NEW' ORDER BY id
  FETCH FIRST 100 ROWS ONLY FOR UPDATE SKIP LOCKED; (12c+ syntax varies;
  alternatively use cursor with SKIP LOCKED)
then mark PROCESSING, commit, process, mark DONE/FAILED with retry count.
Index on status; purge/partition old rows. Or use Advanced Queuing.
REAL-WORLD: Scaled from 1 to 8 workers linearly using SKIP LOCKED.

OQ90. Redo and undo generation: how do you reduce it?
OA90. Use set-based ops, direct-path loads, TRUNCATE instead of DELETE all,
CTAS for big transforms, drop unneeded indexes before bulk load (and
rebuild), avoid updating indexed columns, reduce row-by-row commits, use
global temporary tables (undo only) for intermediate data.
REAL-WORLD: Archive purge via partition DROP instead of DELETE eliminated
hours of redo and archive log generation.

==========================================================================
 SECTION E (Oracle SQL/PLSQL): DESIGN, ARCHITECTURE & EXPERIENCE
==========================================================================

OQ91. Normalization vs denormalization - how do you decide?
OA91. OLTP: 3NF to reduce anomalies and write cost. Reporting/DW: star
schema, denormalized dimensions, pre-aggregated facts for read speed.
Selective denormalization is OK when measured read benefits outweigh the
maintenance cost, and kept consistent via constraints, MVs or triggers/ETL.
REAL-WORLD: Kept core transactional model in 3NF and built a star-schema
reporting layer fed by incremental loads.

OQ92. Partitioning strategies and index choices?
OA92. Range (dates), list (region), hash (even distribution), composite,
interval (auto-create partitions), reference partitioning (child follows
parent). Local indexes: easy maintenance, partition-wise operations;
global indexes: needed for non-partition-key unique constraints but need
UPDATE INDEXES during partition maintenance. EXCHANGE PARTITION loads data
instantly via a swap with a staging table.
REAL-WORLD: Converted a 2TB table to interval-partitioned by month, using
online redefinition; purge became a partition drop.

OQ93. How do you implement Slowly Changing Dimension Type 2?
OA93. Columns: surrogate key, natural key, attributes, effective_from,
effective_to, current_flag. Load: detect changed rows by comparing
hash/columns; update old row's effective_to and flag, insert new version.
Do it with one MERGE + INSERT, or a multi-step set-based approach; use a
hash (ORA_HASH / STANDARD_HASH) of attributes for fast change detection.
REAL-WORLD: Implemented SCD2 on a 30M-row customer dimension with
STANDARD_HASH change detection; incremental run took minutes.

OQ94. How do you do schema changes with zero/low downtime?
OA94. Add nullable columns (fast, metadata-only; 11g+ add column with default
is metadata-only), backward-compatible releases (expand/contract),
DBMS_REDEFINITION for online table restructuring, EBR for code versions,
create indexes ONLINE, avoid long DDL locks (DDL_LOCK_TIMEOUT), deploy in
low-traffic windows with rollback scripts.
REAL-WORLD: Changed a PK datatype on a busy table using online
redefinition with no downtime for users.

OQ95. Design an incremental ETL / change data capture approach.
OA95. Options: timestamp/watermark columns, MV logs, Oracle Streams/
GoldenGate/LogMiner (log based CDC), triggers (last resort), partition
exchange for loads. Always: idempotent steps, restart checkpoints, audit
counts, late-arriving data handling and reconciliation reports.
REAL-WORLD: Replaced full nightly reloads with watermark-based incremental
loads: 6 hours -> 35 minutes.

OQ96. Database security practices you follow as a developer?
OA96. Least privilege via roles; access through packages (definer rights);
bind variables/DBMS_ASSERT against injection; Virtual Private Database
(DBMS_RLS) or Real Application Security for row-level security; Data
Redaction/masking for non-prod; Transparent Data Encryption (DBA);
auditing (Unified Audit); no passwords in code (wallets).
REAL-WORLD: Implemented VPD policies so regional managers only saw their
region's rows without changing application queries.

OQ97. Key differences when migrating Oracle PL/SQL to PostgreSQL/SQL Server?
OA97. Empty string vs NULL; packages (absent or emulated with schemas); no
autonomous transactions natively in PG (workarounds); sequences/identity
syntax; DATE contains time in Oracle; outer join (+) syntax; CONNECT BY ->
recursive CTE; ROWNUM/ROWID differences; exception semantics; transaction
control in procedures; MERGE availability; implicit datatype conversion
rules. Automated tools (ora2pg, SCT) get ~70-80%; rest is manual + testing.
REAL-WORLD: Built a regression comparison harness running both DBs
side-by-side to verify result parity.

OQ98. Tell me about a critical production incident you resolved.
OA98. (Use STAR: Situation, Task, Action, Result.) Example structure:
  S: Month-end job suddenly ran 5x longer, blocking reports.
  T: Restore SLA within hours, find root cause.
  A: Checked ASH -> plan changed (PLAN_HASH_VALUE) after stats gather;
     skewed column histogram caused nested loops; used SQL Plan Baseline
     to restore the old plan immediately, then added extended stats and
     adjusted stats-gathering for that table.
  R: Job back to 20 minutes; added monitoring alert on plan change.
Interviewers want diagnosis method, calm approach, prevention.

OQ99. How do you mentor juniors and enforce standards?
OA99. Code review checklists, coding standards document, reusable templates
(logging, error handling), pair-tuning sessions with execution plans,
brown-bag sessions on common anti-patterns, automated checks in CI
(PL/Scope, utPLSQL), and clear naming/versioning policies.
REAL-WORLD: Reduced production defects by introducing mandatory peer
review and a SQL tuning checklist for all new queries on large tables.

OQ100. Describe the most complex database solution you designed. (Template)
OA100. Structure your answer:
  1) Business problem and scale (rows, GB, users, SLA).
  2) Architecture: schema design, partitioning, indexing strategy, APIs.
  3) Key technical decisions + trade-offs you weighed (e.g., MERGE vs
     staging swap, MV vs table, trigger vs API).
  4) Performance results with numbers (before/after).
  5) Reliability: error handling, restartability, monitoring, testing.
  6) Lessons learned and what you'd improve.

control table, and reconciliation reports. Runtime dropped from 7h to

  total, gaps and islands, MERGE, a BULK COLLECT/FORALL skeleton.
- Replace sample numbers in the REAL-WORLD lines with your own project
  facts so every answer sounds authentic.

# PART IX: POSTGRESQL SQL & PL/pgSQL QUESTIONS (PQ1-PQ100)

==========================================================================
 SECTION A (PostgreSQL SQL/PLpgSQL): ADVANCED SQL
==========================================================================

PQ1. Difference between ROW_NUMBER, RANK, DENSE_RANK? What is DISTINCT ON?
PA1. ROW_NUMBER is unique even for ties; RANK leaves gaps after ties (1,1,3);
DENSE_RANK has no gaps (1,1,2). PostgreSQL also has DISTINCT ON, a non-
standard shortcut for "first row per group":
  SELECT DISTINCT ON (customer_id) *
  FROM orders ORDER BY customer_id, created_at DESC;
It needs ORDER BY to start with the DISTINCT ON expressions and is often
faster/simpler than ROW_NUMBER()=1, but ROW_NUMBER is portable and handles
"top N" cases.
REAL-WORLD: I used DISTINCT ON with a matching composite index
(customer_id, created_at DESC) to fetch the latest record per customer from
a 150M-row table; it became an index scan instead of a big sort.

PQ2. Explain window frames: ROWS, RANGE, GROUPS. Give a running total example.
PA2. ROWS counts physical rows, RANGE groups peers by ORDER BY value, GROUPS
(PG11+) counts peer groups. EXCLUDE CURRENT ROW / TIES / GROUP is available.
Default frame with ORDER BY is RANGE UNBOUNDED PRECEDING TO CURRENT ROW, so
ties are included together and it's slower than ROWS.
  SUM(amount) OVER (PARTITION BY account_id ORDER BY txn_ts, txn_id
                    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
REAL-WORLD: A ledger report showed odd balances for same-timestamp rows until
I switched to explicit ROWS with a unique tiebreaker column.

PQ3. How do you solve "gaps and islands" problems?
PA3. Row-number-difference technique:
  SELECT min(d), max(d)
  FROM (SELECT d, d - (row_number() OVER (ORDER BY d))::int AS grp FROM t) x
  GROUP BY grp;
For dates, subtract the row number as days. LAG/LEAD can detect gaps.
generate_series + LEFT JOIN is used to find missing values.
REAL-WORLD: Used it to find missing daily batch loads and continuous coverage
periods in subscription data.

PQ4. Recursive CTEs: how do you handle cycles and ordering? Alternatives?
PA4. WITH RECURSIVE has anchor + recursive term (UNION ALL). PG14+ adds
SEARCH DEPTH/BREADTH FIRST and CYCLE clauses to order results and detect
loops. Before PG14, carry a path array and check "NOT id = ANY(path)".
For trees queried constantly, consider ltree extension (path-based, GiST
index) or materialized path/closure table.
REAL-WORLD: Exploded a bill-of-materials with a recursive CTE using a CYCLE
clause so bad data could not cause an infinite loop; switched hot category
trees to ltree for fast subtree queries.

PQ5. INSERT ... ON CONFLICT vs MERGE - when to use which?
PA5. ON CONFLICT (PG9.5+) is atomic upsert on a unique index/constraint:
  INSERT ... ON CONFLICT (key) DO UPDATE SET col = EXCLUDED.col
  [WHERE condition] / DO NOTHING.
It is safe under concurrency. MERGE (PG15+) is SQL-standard, supports
WHEN MATCHED / NOT MATCHED / NOT MATCHED BY SOURCE (PG17) with DELETE and
conditions, and PG17 adds MERGE ... RETURNING and merge_action(). But MERGE
can still raise unique violations under concurrent inserts since it doesn't
use speculative insertion.
Pitfall: "ON CONFLICT DO UPDATE command cannot affect row a second time" -
the source batch has duplicate keys; dedupe it first (DISTINCT ON).
REAL-WORLD: Used ON CONFLICT for high-concurrency event ingestion and MERGE
for batch dimension syncs with multiple actions.

PQ6. IN vs EXISTS vs JOIN; what's the NOT IN NULL trap?
PA6. PostgreSQL plans IN/EXISTS as semi-joins, NOT EXISTS as anti-joins.
NOT IN (subquery) returns no rows if the subquery yields any NULL (three-
valued logic) and often can't use a hash anti-join (slow "hashed SubPlan"
or repeated subplan). Prefer NOT EXISTS or LEFT JOIN ... IS NULL.
REAL-WORLD: A "customers without orders" job returned zero rows in
production because of one NULL; NOT EXISTS fixed it and it ran 50x faster.

PQ7. How do you delete duplicate rows from a large table safely?
PA7. Small: DELETE FROM t a USING t b WHERE a.ctid > b.ctid AND a.k = b.k;
or DELETE WHERE ctid IN (SELECT ctid FROM (SELECT ctid, row_number() OVER
(PARTITION BY k ORDER BY ctid) rn FROM t) x WHERE rn > 1). Huge: CREATE
TABLE new AS SELECT DISTINCT ON (k) ..., recreate indexes/constraints, swap
names in one transaction (DDL is transactional in PG). Then add a UNIQUE
constraint. Run VACUUM afterwards since deletes leave dead tuples.
REAL-WORLD: For 400M rows with 25% duplicates, CTAS + swap was far faster and
created less WAL/bloat than DELETE.

PQ8. Top-N per group - what are your options?
PA8. (a) row_number()/rank() in subquery, filter <= N. (b) LATERAL join with
ORDER BY ... LIMIT N per parent - excellent with an index when parent set is
small:
  SELECT c.id, o.* FROM customers c
  CROSS JOIN LATERAL (SELECT * FROM orders o WHERE o.customer_id=c.id
                      ORDER BY created_at DESC LIMIT 3) o;
(c) DISTINCT ON for top-1.
REAL-WORLD: "Last 3 orders per customer" for 40K customers with LATERAL +
index (customer_id, created_at DESC) ran in milliseconds vs seconds with
window functions over the whole table.

PQ9. Conditional aggregation, FILTER clause and crosstab?
PA9. FILTER is cleaner than CASE inside aggregates:
  count(*) FILTER (WHERE status='PAID'), sum(amt) FILTER (WHERE ...)
PostgreSQL has no PIVOT keyword. Use FILTER/CASE for known columns, or
tablefunc extension crosstab() (needs column definition list), or build
dynamic SQL with format() and EXECUTE for unknown columns.
REAL-WORLD: Built a monthly pivot report using FILTER columns generated by a
function that produced the SQL text from distinct months, validated with
format('%I').

PQ10. string_agg / array_agg: ordering and pitfalls?
PA10. Aggregate ORDER BY inside the call: string_agg(name, ',' ORDER BY name).
DISTINCT works too but ORDER BY must match the DISTINCT expression. NULLs are
skipped by string_agg but kept by array_agg. Large aggregates can use lots of
memory (max field size 1 GB). array_agg(...) is useful to return child rows
as a single column with row_to_json.
REAL-WORLD: Replaced N+1 child queries from an API with a single query using
jsonb_agg + LEFT JOIN LATERAL.

PQ11. How does NULL behave in PostgreSQL? How is it different from Oracle?
PA11. Comparisons with NULL give UNKNOWN; use IS [NOT] DISTINCT FROM for
NULL-safe comparison. Aggregates ignore NULLs (except count(*)). Empty string
is NOT NULL in PostgreSQL (in Oracle it is). UNIQUE allows multiple NULLs by
default; PG15+ supports UNIQUE NULLS NOT DISTINCT. B-tree indexes do store
NULLs so IS NULL can use an index. COALESCE is standard; no NVL.
REAL-WORLD: In an Oracle-to-PG migration, empty-string checks (col IS NULL)
broke; I wrote a test suite to find them.

PQ12. Outer join: condition in ON vs WHERE?
PA12. A WHERE filter on the nullable side of a LEFT JOIN eliminates the NULL-
extended rows and turns it into an inner join (the planner even rewrites it).
Put such filters in ON to keep unmatched left rows.
REAL-WORLD: A dashboard dropped customers with no orders after a filter was
moved to WHERE; fixed in ON clause.

PQ13. UNION vs UNION ALL and other set operations?
PA13. UNION removes duplicates (HashAggregate/Sort cost). UNION ALL just
appends; PG can use Append with parallel/partition-wise plans. Use UNION ALL
unless duplicates are possible and unwanted. EXCEPT/INTERSECT also do
distinct work and have ALL variants.
REAL-WORLD: Changing UNION to UNION ALL on disjoint partitions removed a
costly hash aggregate in a reporting view.

PQ14. CTEs: materialization behavior and data-modifying CTEs?
PA14. Before PG12, CTEs were always optimization fences (materialized). PG12+
inlines non-recursive, side-effect-free CTEs referenced once. Control with
WITH x AS MATERIALIZED (...) or NOT MATERIALIZED. Data-modifying CTEs let
you chain DML atomically:
  WITH moved AS (DELETE FROM orders WHERE created_at < now()-'1 year'::interval
                 RETURNING *)
  INSERT INTO orders_archive SELECT * FROM moved;
REAL-WORLD: Used MATERIALIZED to prevent re-evaluating an expensive
aggregation referenced thrice, and the DELETE..RETURNING pattern for
atomic archival.

PQ15. What is LATERAL? Where else do you use set-returning functions in FROM?
PA15. LATERAL lets a subquery/function in FROM reference columns from earlier
FROM items (per-row evaluation). Used for top-N per group, unnest/
jsonb_array_elements per row, and calling set-returning functions per row.
unnest(...) WITH ORDINALITY preserves array position.
REAL-WORLD: Flattened nested JSON arrays per order with CROSS JOIN LATERAL
jsonb_array_elements for a reporting view.

PQ16. Range types and exclusion constraints - practical use?
PA16. Range types (tstzrange, daterange, int4range) represent intervals with
operators (&&, @>, -|-). EXCLUDE USING gist (room_id WITH =, period WITH &&)
guarantees no overlapping bookings at the database level (needs btree_gist
for scalar equality). Also good for temporal validity in SCD tables.
REAL-WORLD: Replaced race-prone application checks for double bookings with
an exclusion constraint; zero overlaps since.

PQ17. GROUPING SETS, ROLLUP, CUBE?
PA17. Compute multiple aggregation levels in one pass:
  GROUP BY ROLLUP (year, month) -> detail, year subtotals, grand total.
CUBE gives all combinations. Use GROUPING(col) to distinguish real NULLs
from subtotal NULLs.
REAL-WORLD: One ROLLUP query replaced four UNION ALL queries in a finance
report, scanning the fact table once.

PQ18. JSON vs JSONB - operators, indexing, SQL/JSON?
PA18. JSON stores text as-is; JSONB is binary, supports indexing and faster
operators, but loses key order and duplicates. Operators: ->, ->>, #>, @>,
?, ?|, jsonb_path_query (jsonpath). Index: GIN (default for @>, ?) or
jsonb_path_ops (smaller/faster for @> only); expression indexes on
(data->>'id') for specific keys. PG16-17 add SQL/JSON constructors and
JSON_EXISTS/JSON_VALUE/JSON_QUERY/JSON_TABLE (PG17). Large JSON updates
rewrite the entire value (TOAST), so avoid frequent partial updates of big
documents.
REAL-WORLD: Stored vendor payloads in JSONB with a GIN jsonb_path_ops index
for containment search and promoted frequently filtered keys to real columns.

PQ19. Generating date series and calendar logic?
PA19. generate_series(start, end, '1 day'::interval) works for dates and
timestamps. Join to a calendar dimension (holidays, fiscal periods,
business-day flags) rather than hard-coding weekend logic. For gaps:
LEFT JOIN generate_series to fact data and COALESCE to zero.
REAL-WORLD: A calendar dimension simplified business-day SLA calculations
across dozens of queries.

PQ20. Full-text search and trigram search?
PA20. Full-text: tsvector + tsquery, to_tsvector('english', col), GIN index,
ranking with ts_rank, websearch_to_tsquery. Stored/generated tsvector column
avoids recomputation. pg_trgm + GIN/GiST supports LIKE '%abc%', ILIKE,
similarity and typo-tolerant search.
REAL-WORLD: Replaced slow ILIKE '%term%' scans with pg_trgm GIN index;
searches dropped from 3s to ~20ms.

PQ21. Generated columns, identity columns, serial?
PA21. GENERATED ALWAYS AS (expr) STORED (PG12+; virtual generated columns
arrived in PG18). Identity columns (PG10+): GENERATED ALWAYS/BY DEFAULT AS
IDENTITY are SQL-standard and preferred over serial (owned sequence,
cleaner permissions and pg_dump behavior). Gotcha: sequences are not rolled
back and may have gaps.
REAL-WORLD: Used a stored generated column for normalized email (lower())
with a unique index.

PQ22. COPY and bulk loading features?
PA22. COPY FROM/TO is the fastest path (also \copy in psql for client files).
Options: FORMAT csv/binary, FREEZE (with same-transaction table creation),
PG17 ON_ERROR ignore, LOG_VERBOSITY. Combine with unlogged/staging tables,
then INSERT ... SELECT or MERGE into final tables.
REAL-WORLD: Loaded 200M rows nightly via COPY into an unlogged staging
table, validated with SQL, then upserted into the target in batches.

PQ23. Arrays in PostgreSQL: when are they good or bad?
PA23. Good for small, bounded lists (tags, ids) and passing batches to
functions (= ANY($1::int[]), unnest). Support GIN indexes (@>, &&). Bad when
you need FK integrity, frequent element updates, or large cardinality -
normalize instead. Arrays are 1-based; NULL elements allowed; ANY(array)
behaves differently from IN (list) regarding planning.
REAL-WORLD: Passed 10K ids as one array parameter to avoid a giant IN list.

PQ24. Keyset (seek) pagination vs OFFSET?
PA24. OFFSET reads and discards rows, so deep pages are slow. Keyset:
  WHERE (created_at, id) < ($1, $2)
  ORDER BY created_at DESC, id DESC LIMIT 50
supported by a composite index on (created_at DESC, id DESC) or reverse scan.
Row-value comparison needs all columns in the same sort direction;
otherwise expand the condition with OR. ORDER BY must be deterministic.
REAL-WORLD: Moving an API to keyset pagination reduced page-1000 latency from
2.3s to 8ms.

PQ25. Time zones: timestamp vs timestamptz?
PA25. timestamptz stores UTC instants and converts to the session TimeZone on
display; timestamp has no zone semantics. Prefer timestamptz for events.
Use AT TIME ZONE carefully (it flips type). date_trunc with zone-aware
boundaries, and avoid mixing; DST bugs are common.
REAL-WORLD: Fixed daily reports that were off by an hour around DST by
grouping on date_trunc('day', ts AT TIME ZONE 'America/New_York').

==========================================================================
 SECTION B (PostgreSQL SQL/PLpgSQL): PERFORMANCE TUNING & PLANNER
==========================================================================

PQ26. How do you read an execution plan? What do you check first?
PA26. Use EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS). Compare estimated
rows vs actual rows per node; big mismatches usually mean bad statistics or
correlated columns. Check node types (Seq/Index/Bitmap scan, join type),
loops (actual time x loops), "Rows Removed by Filter", Buffers
(shared hit vs read), sort/hash spills ("Disk:"), and planning vs execution
time. Caution: EXPLAIN ANALYZE actually executes the statement - wrap DML in
BEGIN ... ROLLBACK. Use auto_explain for production captures.
REAL-WORLD: Rows estimated 10 vs 3M actual; CREATE STATISTICS on two
correlated columns changed a nested loop to a hash join.

PQ27. A query was fast yesterday and slow today. How do you investigate?
PA27. 1) pg_stat_statements: compare mean/total time, calls, shared blks read.
2) Plan change: auto_explain / re-run EXPLAIN, check generic vs custom plan
for prepared statements. 3) Stats stale: last_analyze / autovacuum status
(pg_stat_user_tables). 4) Bloat or dead tuples, long transactions holding
back vacuum. 5) Locks/waiting (pg_stat_activity wait_event). 6) Data
growth/skew, new partition, parameter changes, cache cold start after restart.
REAL-WORLD: A plan flipped after a bulk load because autovacuum hadn't
analyzed yet; I added an explicit ANALYZE as the last step of the ETL job.

PQ28. Index types in PostgreSQL and when to use each?
PA28. - B-tree: default; equality/range/sort; supports dedup (PG13+).
  - Hash: equality only; WAL-logged since PG10; rarely better than B-tree.
  - GIN: multi-valued data (jsonb, arrays, tsvector, trigram); slower
    writes (fastupdate/pending list).
  - GiST: geometric, ranges, exclusion constraints, nearest-neighbor.
  - SP-GiST: partitioned search trees (prefix, IP, quadtrees).
  - BRIN: tiny index for huge, naturally ordered tables (timestamps in
    append-only logs).
  Variants: partial, expression, covering (INCLUDE), multicolumn.
REAL-WORLD: Replaced a 40 GB B-tree on an append-only event timestamp with a
BRIN index (few MB) for time-range scans on a 1.5 TB table.

PQ29. Composite, partial, covering and expression indexes?
PA29. Composite: equality columns first, then range/sort columns; the leading
column is most important (PG18 adds B-tree skip scan, which helps when the
leading column has few distinct values, but don't rely on it). Partial:
CREATE INDEX ... WHERE status='OPEN' - small and fast for hot subsets.
Covering: INCLUDE (cols) enables index-only scans. Expression: ON
(lower(email)) to match query expression exactly.
REAL-WORLD: A partial index on unprocessed rows (status='NEW') shrank from
12 GB to 40 MB and sped up the queue poller.

PQ30. Index exists but is not used - why?
PA30. - Function/cast on column not matching an expression index.
  - Datatype mismatch (e.g. int column vs numeric/text param), collation
    mismatch (LIKE 'abc%' needs text_pattern_ops in non-C locale).
  - Low selectivity so Seq Scan is cheaper; stale stats.
  - Leading column of composite missing; OR conditions.
  - random_page_cost too high for SSD (default 4.0; try ~1.1).
  - Index not valid (failed CREATE INDEX CONCURRENTLY) - check indisvalid.
  - Planner correctly chose a bitmap scan for many rows.
REAL-WORLD: LIKE 'abc%' ignored a normal index under en_US collation; adding
varchar_pattern_ops fixed it.

PQ31. Nested loop, hash join, merge join - when does each win?
PA31. Nested loop: small outer set + indexed inner lookup (OLTP). Hash join:
large equi-joins; builds hash on smaller side; spills to disk if exceeding
work_mem x hash_mem_multiplier (batches > 1 in EXPLAIN). Merge join: both
inputs sorted/indexed or large sorted joins. Wrong choices trace back to
estimates; parallel hash joins appear for big scans.
REAL-WORLD: A nested loop over 5M outer rows ran 40 minutes; after fixing
stats and raising work_mem for that job, a hash join finished in 70s.

PQ32. Prepared statements: generic vs custom plans?
PA32. For the first 5 executions PG builds custom plans using the bind values;
after that it may switch to a cached generic plan if its estimated cost is not
much worse than custom plans' average. With skewed data the generic plan can
be terrible. Control with plan_cache_mode (PG12+): auto /
force_custom_plan / force_generic_plan. Poolers (PgBouncer transaction mode)
complicate server-side prepared statements.
REAL-WORLD: After moving to a pooled driver, a skewed-key query turned slow
on the 6th execution; set plan_cache_mode=force_custom_plan for that role.

PQ33. How do statistics work and how do you manage them?
PA33. ANALYZE samples tables into pg_statistic (most common values,
histograms, n_distinct, correlation). Tune default_statistics_target (100)
or per column ALTER TABLE ... ALTER COLUMN SET STATISTICS. Extended statistics
(CREATE STATISTICS: dependencies, ndistinct, mcv) fix correlated column and
multi-column estimates. Autovacuum runs auto-analyze on thresholds; for
big tables lower the scale factor per table or call ANALYZE after loads.
REAL-WORLD: Raised statistics target to 1000 for a skewed tenant_id column,
which fixed estimates for large tenants.

PQ34. Does PostgreSQL support hints? What do you use instead?
PA34. Not in core by design. Options: fix statistics, indexes, rewrite SQL
(CTE MATERIALIZED, OFFSET 0 trick, LATERAL), session-level planner GUCs
(enable_nestloop=off etc.) for diagnosis only, SET LOCAL for a specific
transaction, and extension pg_hint_plan when really needed. There are no
built-in plan baselines.
REAL-WORLD: Used SET LOCAL work_mem and enable_nestloop in a nightly report
transaction instead of changing global settings.

PQ35. Planning time, JIT and many-partition overhead?
PA35. Planning can be significant with many partitions/joins (join_collapse_
limit, from_collapse_limit, geqo_threshold for >12 tables). JIT compilation
(enabled by default since PG12) helps long analytical queries but can add
hundreds of ms to short ones - often disabled for OLTP. Prepared statements
amortize planning cost.
REAL-WORLD: Turning JIT off for the OLTP role removed random 200 ms
latency spikes.

PQ36. Partition pruning - how it works, how to verify?
PA36. Static pruning at plan time with constants; dynamic pruning at
execution time for parameters/subqueries/nested loops ("Subplans Removed" in
EXPLAIN). Requires predicates directly on the partition key without non-
immutable function wrapping. Check enable_partition_pruning. Too many
partitions (thousands) hurt planning time and memory.
REAL-WORLD: date_trunc('day', ts) = ... blocked pruning; rewriting as range
predicate pruned 59 of 60 partitions.

PQ37. A query runs 2 hours. Walk me through your tuning method.
PA37. 1) Capture actual plan with EXPLAIN (ANALYZE, BUFFERS). 2) Find the
node consuming most time/buffers. 3) Estimates vs actuals, stats, indexes,
join order. 4) Check spills (sort/hash disk), work_mem, parallel workers.
5) Rewrite: pre-filter earlier, replace correlated subqueries with joins,
window functions, avoid DISTINCT/ORDER BY where unnecessary, batch big
updates. 6) Consider partitioning, materialized/summary tables. 7) Measure
each change; keep a before/after record.
REAL-WORLD: Cut a 2-hour reconciliation to 8 minutes by replacing a
correlated subquery with a hash join and adding a partial index.

PQ38. Index-only scans, visibility map, and correlation?
PA38. Index-only scans avoid heap visits only for pages marked all-visible in
the visibility map, so VACUUM frequency matters ("Heap Fetches" in EXPLAIN).
Column correlation (pg_stats.correlation) near +-1 means the heap order
matches index order, making index range scans cheap; low correlation favors
bitmap scans. CLUSTER or pg_repack can reorder a table (one-time, not
maintained).
REAL-WORLD: An index-only scan did 2M heap fetches until autovacuum was
tuned; fetches dropped to near zero.

PQ39. Materialized views - refresh and limitations?
PA39. REFRESH MATERIALIZED VIEW locks reads; REFRESH ... CONCURRENTLY allows
reads but needs a UNIQUE index and is slower (diff-based). No native
incremental refresh in core (pg_ivm extension or custom summary tables with
triggers / jobs). Index materialized views like tables. Schedule with pg_cron
or external scheduler.
REAL-WORLD: Dashboard aggregates in a materialized view refreshed
CONCURRENTLY every 10 minutes: query time from 40s to under 1s.

PQ40. What tools do you use to diagnose performance?
PA40. pg_stat_statements (top SQL by time/calls/IO), pg_stat_activity (wait
events, state, query age), auto_explain, log_min_duration_statement,
log_lock_waits, pg_stat_user_tables/indexes (seq scans, unused indexes),
pg_stat_io (PG16+), pg_stat_progress_* views, pgBadger for log analysis,
EXPLAIN visualizers, perf/OS metrics, and monitoring (Prometheus
postgres_exporter, pgwatch).
REAL-WORLD: pg_stat_statements showed one query using 38% of total DB time;
a missing composite index fixed it.

PQ41. Parallel query: when does it help and what are the limits?
PA41. Parallel seq scan, index scan, hash join, aggregate, append. Controlled
by max_parallel_workers_per_gather, parallel_setup_cost, table size
thresholds. Not used inside functions marked PARALLEL UNSAFE, with writable
CTEs, cursors, or SERIALIZABLE (in older versions). Big queries benefit; OLTP
can be hurt by worker overhead and CPU saturation.
REAL-WORLD: Set max_parallel_workers_per_gather=4 for the reporting role
only, leaving OLTP at 0-2.

PQ42. Key memory parameters and how do you reason about them?
PA42. shared_buffers (~25% RAM start point), effective_cache_size (planner
hint about OS+PG cache), work_mem (per sort/hash node per query - can
multiply across nodes and connections!), hash_mem_multiplier,
maintenance_work_mem (VACUUM/CREATE INDEX), wal_buffers, max_connections.
Raise work_mem per session/role for heavy jobs rather than globally.
REAL-WORLD: A global work_mem increase caused OOM kills under concurrency;
I reverted it and used SET LOCAL for the batch role.

PQ43. Fastest way to bulk load data?
PA43. COPY; load into an UNLOGGED or fresh table; create indexes/constraints
after loading; larger maintenance_work_mem; increase max_wal_size to avoid
frequent checkpoints; synchronous_commit=off for the load session (only if
loss of last few commits is acceptable); COPY FREEZE where applicable;
batch inserts of multi-row VALUES if COPY unavailable; ANALYZE afterwards.
There is no Oracle-style direct-path INSERT hint.
REAL-WORLD: Rebuilt a 300M-row table via COPY into an unlogged table, built
indexes in parallel, then swapped; 5h -> 50 min.

PQ44. Sargability: writing index-friendly predicates?
PA44. Avoid wrapping indexed columns in functions/casts: use
created_at >= '2026-01-01' AND created_at < '2026-01-02' instead of
created_at::date = '2026-01-01'; match datatypes; use text_pattern_ops for
prefix LIKE; create expression indexes if function is unavoidable.
REAL-WORLD: Fixing cast-on-column predicates removed several seq scans.

PQ45. Bloat, HOT updates, fillfactor, and vacuum tuning?
PA45. UPDATE/DELETE leave dead tuples; VACUUM reclaims space for reuse (not
returned to the OS, except trailing pages); VACUUM FULL rewrites the table
with ACCESS EXCLUSIVE lock; pg_repack does it online. HOT updates (no
indexed column changed + free space in same page) avoid index churn; lower
fillfactor (e.g. 80-90) on update-heavy tables to enable them. Tune
autovacuum per table (autovacuum_vacuum_scale_factor=0.01-0.05 for big
tables, cost limits). Long-running transactions and abandoned replication
slots prevent cleanup.
REAL-WORLD: An 800 GB table was 60% bloat from a stuck replication slot and
long transaction; fixed both, then pg_repack reclaimed space online.

PQ46. Common wait events and what they imply?
PA46. Lock (relation/transactionid/tuple): app-level blocking. IO:DataFileRead:
cache misses/seq scans. LWLock:BufferMapping/WALInsert: contention. IO:
WALWrite / WALSync: commit rate or slow disks. Client:ClientRead: app is
slow reading, idle in transaction. Activity: background.
REAL-WORLD: Many sessions in "idle in transaction" with ClientRead led me to
find an app bug holding transactions open during HTTP calls.

PQ47. Correlated subqueries, SQL function inlining and set-returning functions?
PA47. Correlated subqueries can run per outer row (SubPlan); the planner often
converts EXISTS/IN to semi-joins but not scalar subqueries in SELECT lists.
Rewrite as joins/LATERAL/window. Simple LANGUAGE sql functions (single SELECT,
non-volatile, no side effects) can be inlined, allowing index usage; PL/pgSQL
functions are opaque to the planner (default COST 100, ROWS 1000 estimates -
set realistic COST/ROWS).
REAL-WORLD: Converting a PL/pgSQL scalar helper to a SQL function allowed
inlining and cut report time from 12 min to 90 s.

==========================================================================
 SECTION C (PostgreSQL SQL/PLpgSQL): PL/pgSQL & EXTENSIBILITY
==========================================================================

PQ48. Functions vs procedures in PostgreSQL?
PA48. Functions (CREATE FUNCTION) return values, are called in SQL, and run
inside the caller's transaction (no COMMIT/ROLLBACK). Procedures (PG11+)
are invoked with CALL, can COMMIT/ROLLBACK inside (when not called inside an
explicit transaction block/other function), and can have INOUT params
(OUT since PG14). Use procedures for batch/ETL orchestration; functions for
reusable logic and SQL integration.
REAL-WORLD: Rewrote a batch-load routine as a procedure that committed per
50K-row chunk, which was impossible in a function.

PQ49. PostgreSQL has no packages. How do you organize code?
PA49. Use schemas as namespaces (billing.calc_tax), naming prefixes,
extensions to package and version groups of objects, and migration tooling
for deployments. For "package state": session-level variables via
set_config('app.key', val, false)/current_setting(), temp tables, or
tables. There's no package initialization block; functions are stateless
between calls (plan caching aside).
REAL-WORLD: Used one schema per domain (api, core, util) with api functions
as the only exposed interface, granting EXECUTE only on api.

PQ50. Cursors in PL/pgSQL?
PA50. FOR rec IN SELECT ... LOOP uses an implicit cursor and fetches in
batches - simplest option. Explicit: DECLARE c CURSOR FOR ...; OPEN/FETCH/
CLOSE. REFCURSOR returns cursors to clients (valid only inside transaction
unless WITH HOLD). Server-side cursors in drivers (named cursors/fetch size)
avoid loading huge result sets in client memory.
REAL-WORLD: Streamed a 50M-row export via a named cursor with fetch size
10K instead of loading everything into app memory.

PQ51. How do you return result sets from functions?
PA51. RETURNS TABLE(...) or SETOF type with RETURN QUERY (adds all rows) or
RETURN NEXT (row by row). PL/pgSQL materializes the entire result before
returning (tuplestore) - not streaming like Oracle pipelined functions;
for huge sets prefer LANGUAGE sql functions (can be inlined/streamed) or
cursors.
REAL-WORLD: A PL/pgSQL set-returning function over 20M rows consumed GBs of
memory/temp; rewriting as a SQL function/view fixed it.

PQ52. Bulk operations: there is no BULK COLLECT/FORALL. What do you do?
PA52. Use set-based SQL (INSERT ... SELECT, UPDATE ... FROM, MERGE), pass
arrays/JSON and unnest() into a single statement, use COPY from the app,
batch multi-row inserts, and process in chunks with keys/ctid ranges plus
COMMIT in procedures. PL/pgSQL loops with SQL inside are slower but there
is less engine-switch cost than Oracle; still avoid row-by-row.
REAL-WORLD: Replaced a 3M-iteration FOR loop with one UPDATE ... FROM
(unnest) statement: 2 hours -> 40 seconds.

PQ53. Composite types, domains, enums - when to use?
PA53. Composite types model structured values and table row types (%ROWTYPE,
table%ROWTYPE). Domains add reusable constraints on a base type (e.g.
email, positive_int) - great for consistency. Enums are ordered label sets;
adding values is easy (ALTER TYPE ADD VALUE) but removing is not, so use
lookup tables for volatile lists.
REAL-WORLD: Introduced domains for email/phone/postal code so validation
lived in one place across 60+ tables.

PQ54. Function volatility, strictness, parallel safety, cost?
PA54. VOLATILE (default; may change data/results), STABLE (same results
within a statement; can use index scans), IMMUTABLE (always same output;
required for expression indexes). Mislabeling causes wrong results or
index corruption. STRICT/RETURNS NULL ON NULL INPUT short-circuits.
PARALLEL SAFE/RESTRICTED/UNSAFE controls parallel plans. COST and ROWS
inform planner. LEAKPROOF matters with row-level security.
REAL-WORLD: Marked a pure formatting function IMMUTABLE and PARALLEL SAFE,
enabling an expression index and parallel scans.

PQ55. Exception handling best practices in PL/pgSQL?
PA55. BEGIN ... EXCEPTION WHEN unique_violation THEN ... END. Each block
with an EXCEPTION clause creates a subtransaction (savepoint) - costly in
tight loops, and many subtransactions per transaction (>64) can cause
performance problems with snapshots (subxid overflow). Use GET STACKED
DIAGNOSTICS (message, detail, hint, context, sqlstate), RAISE with ERRCODE,
re-raise with plain RAISE, avoid blanket WHEN OTHERS THEN NULL, and ASSERT
for internal checks.
REAL-WORLD: Removed a per-row EXCEPTION block from a loop (used ON CONFLICT
instead): throughput increased 5x and replica snapshot stalls disappeared.

PQ56. No autonomous transactions - how do you handle audit/error logging?
PA56. Options: (1) dblink/postgres_fdw loopback connection to insert logs in
a separate transaction; (2) pg_background extension; (3) log via RAISE
LOG/NOTICE to server logs and ship them; (4) LISTEN/NOTIFY to an external
worker; (5) write logs after the failure at the application layer.
Note: ordinary INSERT-based logging inside a transaction is rolled back with
it.
REAL-WORLD: Implemented error logging through a dblink loopback function
for failed batch rows, with a fallback to RAISE LOG.

PQ57. Triggers: types, transition tables, event triggers?
PA57. BEFORE/AFTER/INSTEAD OF (views), row-level or statement-level, WHEN
clause for conditional firing, and transition tables (REFERENCING NEW TABLE
AS n) in statement-level AFTER triggers for efficient set-based auditing.
No "mutating table" error like Oracle, but you can still see
inconsistent results if reading the table being modified. Event triggers
fire on DDL (audit, enforce naming). Triggers hide logic and add overhead;
disable with session_replication_role for bulk loads (superuser) carefully.
REAL-WORLD: Replaced a row-level audit trigger with a statement-level one
using transition tables: bulk updates ran 6x faster.

PQ58. Dynamic SQL and SQL injection prevention?
PA58. EXECUTE 'SELECT ... WHERE id = $1' USING p_id; build identifiers with
format('%I', name) or quote_ident, literals with %L or quote_literal -
never concatenate raw input. Use USING for values. For arbitrary-column
queries, validate against catalog tables (information_schema). Dynamic
SQL isn't cached the same way as static PL/pgSQL statements, so prefer
static SQL where possible.
REAL-WORLD: Built a generic export function with format('%I.%I') and an
allow-list lookup of table names.

PQ59. SECURITY DEFINER vs INVOKER, and the search_path risk?
PA59. INVOKER (default) runs with the caller's rights; DEFINER runs with the
owner's privileges (like Oracle definer rights). Always add
SET search_path = pg_catalog, myschema (or fully qualify) to DEFINER
functions to prevent hijacking via malicious objects in the caller's
search_path. REVOKE EXECUTE FROM PUBLIC and grant explicitly (functions
are executable by PUBLIC by default).
REAL-WORLD: Audited all SECURITY DEFINER functions, pinned search_path,
and revoked PUBLIC execute as part of a security review.

PQ60. How does LISTEN/NOTIFY work and what are its limits?
PA60. NOTIFY channel, 'payload' (default max 8000 bytes) delivers events to
listening sessions after the sending transaction commits. Not durable: if
no one is listening, messages are lost; listeners need persistent
connections (not transaction-mode pooling). Use for cache invalidation or
wake-ups, with data stored in tables and the notification carrying ids.
REAL-WORLD: Used NOTIFY to wake queue workers immediately rather than
polling every second.

PQ61. Polymorphism, VARIADIC, default arguments, overloading?
PA61. Overloading by argument types is supported (ambiguity errors can occur
with unknown literals). Polymorphic types anyelement/anyarray/anycompatible
allow generic functions. Named notation (name => value) and defaults make
APIs backward compatible. VARIADIC accepts variable argument lists as arrays.
Changing a function's signature creates a new function; CREATE OR REPLACE
cannot change argument types or return type.
REAL-WORLD: Added new parameters with defaults to keep older callers working
during a phased release.

PQ62. Logging, instrumentation and progress reporting?
PA62. RAISE NOTICE/LOG for debugging; log table via autonomous workaround;
set application_name per job; track_functions = pl for pg_stat_user_functions;
auto_explain.log_nested_statements for statements inside functions;
pg_stat_progress_* for VACUUM/CREATE INDEX/COPY; custom progress via
set_config or a progress table updated outside the long transaction.
REAL-WORLD: ETL steps set application_name to job/step so support could see
progress in pg_stat_activity.

PQ63. Scheduling jobs in PostgreSQL?
PA63. No built-in scheduler. Options: pg_cron extension (cron syntax, runs
SQL inside DB), OS cron/systemd timers, Kubernetes CronJobs, pgAgent,
orchestration tools (Airflow). Ensure single-run semantics with advisory
locks (pg_try_advisory_lock) and idempotent jobs with retries and alerting.
REAL-WORLD: Scheduled materialized view refreshes via pg_cron guarded by
an advisory lock to avoid overlapping runs.

PQ64. Advisory locks - what are they for?
PA64. Application-defined locks on arbitrary bigint keys: session-level
(pg_advisory_lock) or transaction-level (pg_advisory_xact_lock, released
automatically). Use to serialize jobs, protect critical sections, or
implement per-customer mutual exclusion. Danger: session locks persist
through pooled connections; prefer xact-level locks.
REAL-WORLD: Used pg_try_advisory_xact_lock(hashtext('nightly_close')) so
only one instance of the close process ran across app nodes.

PQ65. Working with files and external data: COPY, file_fdw, postgres_fdw?
PA65. COPY (server-side needs privileges pg_read_server_files; client-side via
\copy). file_fdw exposes files as foreign tables for SQL access.
postgres_fdw queries remote PostgreSQL (push down WHERE/joins/aggregates
where possible). Other FDWs: oracle_fdw, mysql_fdw, mongo_fdw. FDW
performance depends on pushdown; check EXPLAIN VERBOSE for "Remote SQL".
REAL-WORLD: Migrated data from legacy Oracle using oracle_fdw into staging
tables with parallel jobs per partition range.

PQ66. Which extensions have you used and why?
PA66. pg_stat_statements (query stats), pg_trgm (fuzzy search), btree_gist
(exclusion constraints), pgcrypto (hashing/encryption), uuid-ossp or
built-in gen_random_uuid() (uuidv7() in PG18 for time-ordered ids), ltree
(hierarchies), hstore, citext, postgis (geospatial), pg_partman (partition
management), pg_cron, pg_repack, pgaudit, timescaledb (time series),
pg_hint_plan, plpgsql_check.
REAL-WORLD: Adopted pg_partman to automate monthly partition creation and
retention, removing a manual runbook step.

PQ67. Other procedural languages: PL/Python, PL/Perl, PL/v8?
PA67. Useful for logic hard to write in SQL (regex, parsing, ML scoring,
calling libraries). Untrusted variants (plpython3u, plperlu) need superuser
and can access the OS - restrict tightly. Overhead of language switching;
keep out of hot paths. Often better done in the application layer unless
data-local processing is needed.
REAL-WORLD: Used PL/Python sparingly to validate complex file formats close
to the data; all else stayed in SQL/PLpgSQL.

PQ68. Dependency management and DDL behavior?
PA68. DDL is transactional (rollback a failed migration). PL/pgSQL function
bodies are not validated against objects at creation (late binding), so
errors appear at runtime; use plpgsql_check for static analysis. Views
depend on columns (can't drop/alter type used by a view without
CASCADE). pg_depend tracks dependencies. CREATE OR REPLACE VIEW can add
columns at the end only.
REAL-WORLD: Added plpgsql_check to CI and caught missing columns and
type mismatches before release.

PQ69. Parameter modes, RETURNS TABLE vs OUT parameters?
PA69. IN, OUT, INOUT, VARIADIC. RETURNS TABLE(col type, ...) is shorthand for
OUT parameters + SETOF. Beware name collisions between OUT column names and
table columns in the function body (use qualified names or
#variable_conflict). Large arrays passed by value are copied; prefer
tables/temp tables for huge inputs.
REAL-WORLD: Fixed an ambiguous column reference bug in a RETURNS TABLE
function by prefixing aliases.

PQ70. Large objects, bytea, TOAST?
PA70. bytea stores binary in-row/TOAST (up to 1 GB); large objects (lo_*) use
pg_largeobject with streaming APIs and OID references (extra cleanup via
vacuumlo/triggers). TOAST automatically compresses/out-of-lines large
values (>~2KB) - SELECT * on wide TOAST columns costs I/O; select only
needed columns. For big files, store in object storage and keep metadata/
URLs in DB.
REAL-WORLD: Moved PDFs from bytea to S3 with a reference table, shrinking
the DB by 400 GB and speeding backups.

PQ71. Constraints and safe validation on live tables?
PA71. CHECK, UNIQUE, FK, NOT NULL, EXCLUDE. On large tables add as NOT VALID
(skips scanning existing rows, enforces for new rows) then VALIDATE
CONSTRAINT later (takes weaker lock). PG: SET NOT NULL scans the table
unless a validated CHECK (col IS NOT NULL) exists (PG12+ uses it). FK
columns on child should be indexed.
REAL-WORLD: Added FK constraints on a 600M-row table with NOT VALID +
VALIDATE during low traffic: no outage.

PQ72. Connection pooling and PgBouncer - what should developers know?
PA72. PostgreSQL uses a process per connection (memory + context switch
cost), so thousands of direct connections hurt. PgBouncer modes: session,
transaction (best scaling, but session state such as SET, advisory session
locks, LISTEN, temp tables and, historically, prepared statements don't
work reliably), statement. Size pools to cores (roughly 2-4x cores of
active connections), set timeouts, and avoid long idle-in-transaction.
REAL-WORLD: Introduced PgBouncer in transaction mode and fixed code that
relied on session-level SET; max connections dropped from 2000 to 200.

PQ73. Slow-by-slow processing - how do you spot and fix it?
PA73. Symptoms: loop with a SQL statement per iteration, huge "calls" count in
pg_stat_statements with tiny rows, per-row exceptions/commits. Fix with
single set-based statements, joins in UPDATE ... FROM, window functions,
batching with arrays, or chunked processing. The fastest loop is the one
you don't write.
REAL-WORLD: pg_stat_statements showed a statement with 30M calls per run;
replaced with one INSERT ... SELECT.

PQ74. How do you profile PL/pgSQL?
PA74. track_functions='pl' (pg_stat_user_functions), auto_explain with
log_nested_statements, plpgsql_check profiler and plprofiler extension
(line-level), pg_stat_statements with pg_stat_statements.track=all for
nested statements, plus manual clock_timestamp() timing.
REAL-WORLD: plprofiler showed 70% of time in a tiny validation function; I
moved it into a SQL expression.

PQ75. How do you unit test and deploy database code?
PA75. pgTAP for unit tests (is(), results_eq(), throws_ok()), migration tools
(Flyway, Liquibase, sqitch, Alembic) with versioned repeatable scripts,
CI using Docker/testcontainers, test data fixtures, rollback/forward
plan, idempotent scripts, checks for lock timeouts, and plpgsql_check in
pipeline.
REAL-WORLD: Introduced pgTAP for core pricing functions and a CI pipeline
that spins up PostgreSQL, applies migrations, runs tests.

PQ76. Array/JSON helper pitfalls inside functions?
PA76. Arrays are 1-based; array_append on NULL array returns array with the
element; unnest of empty array returns zero rows (affects joins - use LEFT
JOIN/COALESCE); jsonb functions return NULL for missing keys (->>) which
may be mistaken for JSON null; jsonb_set requires create_missing awareness;
use jsonb_strip_nulls when needed.
REAL-WORLD: A report lost rows because unnest(empty array) removed the parent
row; fixed with LEFT JOIN LATERAL ... ON true.

PQ77. Row-Level Security (RLS) from a developer's view?
PA77. ALTER TABLE ... ENABLE ROW LEVEL SECURITY; CREATE POLICY ... USING
(tenant_id = current_setting('app.tenant')::int) WITH CHECK (...). Policies
apply to non-owner roles unless FORCE ROW LEVEL SECURITY. Performance:
policy predicates are added to every query, so index them and keep
functions LEAKPROOF/simple. Great for multi-tenant isolation.
REAL-WORLD: Implemented tenant isolation with RLS + set_config at connection
checkout; eliminated tenant-filter bugs in application code.

PQ78. Code review checklist for PL/pgSQL?
PA78. Set-based first; explicit column lists; no SELECT *; parameterized
dynamic SQL; correct volatility/security labels; search_path pinned for
SECURITY DEFINER; EXCEPTION blocks only when needed; chunking + commit in
procedures; indexes for new access paths; lock impact of DDL (lock_timeout);
logging; tests (pgTAP); idempotent migrations.
REAL-WORLD: Introduced this checklist in PR templates, reducing production
rollbacks.

PQ79. Common PL/pgSQL gotchas?
PA79. - Variable name vs column name conflict (use qualified names or
  #variable_conflict).
  - SELECT INTO with multiple rows: takes first row silently unless STRICT.
  - FOUND / ROW_COUNT semantics; IF NOT FOUND after SELECT INTO.
  - NULL in IF/CASE conditions evaluates as not true.
  - Cached plans inside functions can go stale with changing table shapes
    or skewed values.
  - Temp tables inside functions can bloat catalogs when created per call.
REAL-WORLD: A silent SELECT INTO (non-STRICT) picked an arbitrary row; I
changed it to STRICT and fixed the duplicate-data root cause.

PQ80. How do you design a large data migration job?
PA80. Stage -> validate -> transform -> load. Use COPY and set-based SQL,
process in key-range chunks with a control table (batch id, status, last
key) for restartability, parallel workers per partition, disable
non-essential indexes only if justified, error/reject tables with reason
codes, reconciliation (row counts, checksums, sums), rehearsal with
production-sized data, and cutover plan (logical replication or CDC for
minimal downtime).
REAL-WORLD: Migrated ~700M rows in a weekend window with restartable chunks
and signed-off reconciliation reports.

==========================================================================
 SECTION D (PostgreSQL SQL/PLpgSQL): MVCC, TRANSACTIONS, LOCKING, CONCURRENCY
==========================================================================

PQ81. Explain MVCC in PostgreSQL. How is it different from Oracle?
PA81. Each row version (tuple) lives in the heap with xmin (creator xid) and
xmax (deleter/locker xid). An UPDATE writes a new tuple version and marks the
old one dead; snapshots decide which versions a transaction can see. Readers
never block writers. Old versions are cleaned by VACUUM. Oracle instead keeps
the current version in the block and rebuilds old versions from undo
(so no table bloat, but ORA-01555). PostgreSQL has no snapshot-too-old
for normal queries, but bloat and vacuum dependencies instead.
REAL-WORLD: Explained high update cost on a wide table to the team: every
update copied the full row; narrowing the table and enabling HOT updates
cut write amplification.

PQ82. Isolation levels in PostgreSQL?
PA82. READ COMMITTED (default; each statement sees a fresh snapshot),
REPEATABLE READ (transaction-level snapshot; prevents non-repeatable reads
and phantoms; can fail with "could not serialize access", SQLSTATE 40001),
SERIALIZABLE (SSI; detects dangerous dependency patterns, may abort with
40001 - applications must retry). READ UNCOMMITTED behaves as READ COMMITTED
(no dirty reads).
REAL-WORLD: Used REPEATABLE READ READ ONLY for multi-query month-end exports
and SERIALIZABLE with retry logic for a financial allocation routine.

PQ83. Row locks and table locks - what should I know?
PA83. Row lock modes: FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE, FOR KEY SHARE
(FK checks use KEY SHARE), with NOWAIT and SKIP LOCKED options. Table lock
modes range from ACCESS SHARE (SELECT) to ACCESS EXCLUSIVE (ALTER TABLE,
VACUUM FULL, DROP). A queued ACCESS EXCLUSIVE request blocks all later
queries behind it - a common cause of outages during migrations. Always set
lock_timeout (e.g. 3s) and retry DDL.
REAL-WORLD: An ALTER TABLE waiting behind a long query froze the app; I
introduced lock_timeout + retry wrappers for all migrations.

PQ84. How do you find blocking sessions and deadlocks?
PA84. pg_stat_activity (wait_event_type = 'Lock'), pg_blocking_pids(pid),
pg_locks joined to activity. Enable log_lock_waits and deadlock_timeout
(default 1s). Deadlocks raise SQLSTATE 40P01 and one transaction is aborted;
the log shows both statements. Prevent with consistent lock ordering,
short transactions, and indexed foreign keys.
REAL-WORLD: Deadlocks in an order-update flow disappeared after sorting row
ids before locking (SELECT ... ORDER BY id FOR UPDATE).

PQ85. Lost updates: pessimistic vs optimistic locking?
PA85. Under READ COMMITTED, two read-modify-write cycles can overwrite each
other. Pessimistic: SELECT ... FOR UPDATE. Optimistic: version column
(UPDATE ... WHERE id=$1 AND version=$2; check row count) or compare
xmin::text::bigint cautiously. Atomic SQL (SET qty = qty - 1 WHERE qty > 0)
avoids read-modify-write entirely.
REAL-WORLD: Replaced read-then-update inventory logic with a single atomic
UPDATE ... RETURNING, removing oversells.

PQ86. Sequences: gaps, caching, and gap-free numbering?
PA86. Sequences are non-transactional: rollbacks and crashes create gaps;
CACHE causes per-session ranges and out-of-order values across sessions.
nextval is never rolled back. Gap-free numbering (invoices) needs a counter
table updated in the same transaction (serializes writers), accepting the
concurrency cost. Prefer identity columns; consider uuid (v7 in PG18 or
application-generated) for distributed ids and index locality.
REAL-WORLD: Used sequences for surrogate keys and a locked counter table
only for legally gap-free invoice numbers.

PQ87. DEFERRABLE constraints, FK indexing and exclusion constraints?
PA87. DEFERRABLE INITIALLY DEFERRED checks constraints at commit - good for
circular inserts and bulk loads (only UNIQUE/PK/FK/EXCLUDE can be
deferrable; NOT NULL/CHECK cannot). PostgreSQL does not auto-index FK
columns; unindexed child FKs make parent deletes/updates scan the child
table and lock heavily. Exclusion constraints enforce non-overlap.
REAL-WORLD: Added missing FK indexes found with a catalog query; slow parent
deletes dropped from minutes to seconds.

PQ88. Transaction ID wraparound and freezing?
PA88. XIDs are 32-bit; after ~2 billion transactions old rows could appear
"in the future". VACUUM freezes old tuples; autovacuum forces anti-
wraparound vacuum when age(relfrozenxid) exceeds autovacuum_freeze_max_age
(200M default). Monitor age(datfrozenxid). Causes of danger: blocked
vacuum (long transactions, replication slots, prepared transactions),
disabled autovacuum. At the extreme the DB stops accepting writes.
REAL-WORLD: Alerted on datfrozenxid age > 1B and found an orphaned
prepared transaction blocking freezing.

PQ89. Build a safe queue-processing table.
PA89. Table: id, payload, status, attempts, locked_at, run_after. Workers:
  WITH next AS (SELECT id FROM jobs WHERE status='NEW' AND run_after<=now()
                ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED)
  UPDATE jobs j SET status='RUNNING', locked_at=now()
  FROM next WHERE j.id=next.id RETURNING j.*;
Partial index on status='NEW'; handle retries with attempts and dead-letter
status; reap stuck jobs by locked_at; frequently VACUUM (high churn);
consider partitions or deleting finished rows. Alternatives: pgmq, LISTEN/
NOTIFY wakeups, or dedicated brokers at large scale.
REAL-WORLD: Scaled from 1 to 12 workers linearly with SKIP LOCKED, 4M jobs/day.

PQ90. WAL, checkpoints, durability settings, and PITR?
PA90. Every change is written to WAL before data files. Checkpoints flush
dirty pages; tune max_wal_size/checkpoint_timeout/checkpoint_completion_
target to smooth I/O. synchronous_commit=off trades up to a few hundred ms of
commits for speed without corruption risk; fsync=off is dangerous.
Reduce WAL: batch commits, UNLOGGED tables (not crash-safe, not replicated),
fewer indexes, wal_compression. PITR: base backup (pg_basebackup/pgBackRest)
+ continuous WAL archiving, restore to any timestamp. Developers should know
PostgreSQL has no Flashback - recover mistakes via PITR to a side instance.
REAL-WORLD: Recovered an accidentally deleted table by restoring a PITR
clone to just before the DELETE and exporting the rows.

==========================================================================
 SECTION E (PostgreSQL SQL/PLpgSQL): DESIGN, ARCHITECTURE & EXPERIENCE
==========================================================================

PQ91. Normalization vs denormalization; relational vs JSONB hybrid?
PA91. OLTP: 3NF to protect integrity. Reporting: star schema or summary
tables. A hybrid works well: core attributes as typed columns with
constraints, flexible/sparse attributes in JSONB with GIN or expression
indexes. Over-using JSONB loses FK integrity, statistics (planner can't
estimate inside JSONB well), and ease of updates.
REAL-WORLD: Modeled product catalogs with typed core columns and a JSONB
attributes column for category-specific fields; promoted hot keys to columns
as usage grew.

PQ92. Declarative partitioning: strategies and limitations?
PA92. RANGE (time), LIST (tenant/region), HASH (even spread), multi-level.
Unique/PK constraints must include the partition key; no global indexes;
FKs referencing partitioned tables supported (PG12+). Maintenance:
ATTACH PARTITION (after matching CHECK constraint to avoid scan),
DETACH PARTITION CONCURRENTLY (PG14+), default partition, pg_partman for
automation. Benefits: pruning, fast purge (DROP), parallel maintenance.
Don't over-partition (thousands hurt planning).
REAL-WORLD: Converted a 3 TB events table to monthly range partitions;
retention became a DROP PARTITION job and vacuum times fell dramatically.

PQ93. How do you implement Slowly Changing Dimension Type 2?
PA93. Columns: surrogate key, business key, attributes, valid_from, valid_to
(or tstzrange valid_period), is_current. Detect changes with a hash
(md5/sha256 of concatenated attributes) or IS DISTINCT FROM. Load in one
transaction: close current rows (UPDATE ... SET valid_to=now()) for
changed keys, insert new versions (or MERGE on PG15+). An exclusion
constraint (business_key WITH =, valid_period WITH &&) prevents overlapping
versions.
REAL-WORLD: Loaded a 30M-row customer dimension daily using hash-based
change detection and exclusion constraint for integrity; ran in minutes.

PQ94. Zero/low-downtime schema changes?
PA94. - ADD COLUMN with constant/non-volatile DEFAULT is metadata-only (PG11+).
  - CREATE INDEX CONCURRENTLY (and REINDEX CONCURRENTLY, PG12+); check for
    invalid indexes afterwards.
  - Constraints: NOT VALID then VALIDATE.
  - Changing types often rewrites the table: use expand/contract (new
    column, dual write/trigger, backfill in batches, swap, drop).
  - Always set lock_timeout and retry; keep migrations small.
  - Large rewrites: pg_repack or logical replication to a new instance.
REAL-WORLD: Changed an int PK to bigint on a 1B-row table via expand/
contract with batched backfill and no outage.

PQ95. Replication, HA, and read replicas - what should a developer know?
PA95. Streaming (physical) replication: byte-level replica, read-only hot
standby, async or synchronous; failover via Patroni/repmgr/cloud managed
services. Logical replication: table-level publish/subscribe (cross-version
migration, selective data), but DDL and sequences aren't replicated
automatically and needs replica identity. Developer concerns: replication
lag (read-your-writes issues), query conflicts on standby (max_standby_
streaming_delay, hot_standby_feedback trade-offs), route reads carefully,
idempotent retries after failover.
REAL-WORLD: Moved reporting to a replica and solved stale reads by routing
post-write reads to the primary for a short window.

PQ96. Security practices as a developer?
PA96. Least privilege roles (group roles, no app as superuser), GRANT on
schema/function level, REVOKE CREATE on public schema (default in PG15+),
default privileges, SCRAM-SHA-256 auth, TLS, RLS for multi-tenancy, column-
level privileges, pgcrypto for hashing, pgaudit for auditing, SECURITY
DEFINER with pinned search_path, secrets in vaults, masked data in non-
prod (pg_anonymizer).
REAL-WORLD: Introduced separate roles (app_rw, app_ro, migrator) with
default privileges, ending use of the owner account by applications.

PQ97. Oracle (or SQL Server) to PostgreSQL migration - key differences?
PA97. Empty string vs NULL; no packages (schemas/extensions); no autonomous
transactions; no ROWNUM (use LIMIT/row_number); (+) outer joins -> ANSI;
CONNECT BY -> recursive CTE; sequences/NEXTVAL syntax; DATE type has no time
in PG; implicit conversions stricter; no hierarchical hints; MERGE since PG15;
PL/SQL -> PL/pgSQL syntax (BULK COLLECT, %ROWTYPE, exception names);
transaction control inside procedures only; case-folding of identifiers
(unquoted names lower-case). Tools: ora2pg, AWS SCT/DMS handle most DDL;
code needs manual review + side-by-side result comparison.
REAL-WORLD: Built a comparison harness executing identical queries on both
engines and diffing results to certify parity before cutover.

PQ98. Tell me about a critical production incident you resolved.
PA98. (Use STAR: Situation, Task, Action, Result.) Example:
  S: API latency jumped from 50 ms to 5 s at peak; connections maxed out.
  T: Restore service quickly, find root cause.
  A: pg_stat_activity showed many sessions waiting on a lock held by an
     "idle in transaction" session from a stuck migration job; terminated

  R: Service restored in 10 minutes. Prevention: lock_timeout + retry in
     migrations, idle_in_transaction_session_timeout, statement_timeout for
     report roles, alert on lock waits > 30s.
Interviewers want a calm method, correct tools, and prevention steps.

------------------------ X. TOOLBOX INTERVIEW QUESTIONS ------------------

X1. How do you move a 3 TB schema from one Oracle DB to another with minimal
downtime?
A.  Options by constraint: Data Pump with PARALLEL + NETWORK_LINK/ consistent
FLASHBACK_SCN for logical copy; transportable tablespaces/RMAN
(cross-platform with conversion) for physical speed; GoldenGate or Data Guard
for near-zero downtime cutover (initial load + CDC, then switch). Validate
with row counts/checksums, rebuild statistics, compile invalid objects,
compare privileges, run performance baselines.
REAL-WORLD: Used transportable tablespaces + incremental backups to cut
cutover downtime from 18 hours to 40 minutes.

X2. Data Pump vs SQL*Loader vs external tables - when each?
A.  Data Pump: Oracle-to-Oracle with metadata. SQL*Loader: flat files with
complex parsing/rejects, direct path for speed. External tables: SQL-
friendly ETL, parallel, no staging load, ideal for repeated file feeds.

X3. How do you update 200M rows in a controlled way?
A.  DBMS_PARALLEL_EXECUTE (chunk by ROWID or key, parallel jobs, restartable,
commit per chunk), or partition-wise CTAS/exchange partition, or INSERT
APPEND into new table and swap. Avoid single giant UPDATE (undo, redo,
rollback time).

X4. Explain tracing a slow session end to end.
A.  Enable 10046 level 12 (or DBMS_MONITOR with binds/waits) for the session,
reproduce, disable, TKPROF with sort=exeela,fchela, look at parse/exec/
fetch CPU vs elapsed, waits, row counts, plans. For multi-session
apps use client identifier + TRCSESS.

X5. How do you ensure you don't use a feature that requires a license?
A.  Check DBA_FEATURE_USAGE_STATISTICS, CONTROL_MANAGEMENT_PACK_ACCESS (turn
off diagnostics/tuning pack use if unlicensed), avoid AWR/ASH views in
unlicensed environments, review options in Oracle LMS guidance, use
Standard Edition feature set in dev if SE2 in prod.

X6. What is an invisible index and why use it?
A.  Index maintained by DML but ignored by optimizer unless
OPTIMIZER_USE_INVISIBLE_INDEXES=TRUE. Use to test the effect of dropping an
index safely or to introduce indexes gradually.

X7. Explain DB links and distributed query tuning.
A.  The optimizer chooses a driving site; large remote tables moved over the
network are costly. Use DRIVING_SITE hint, filter remotely, create remote
views, MVs (replication) or ETL. Secure with fixed-user links via wallet/
proxy, avoid public links.

X8. What is Edition-Based Redefinition used for?
A.  Zero-downtime application releases: new code version lives in a new
edition while old sessions use the old one; editioning views map tables;
cross-edition triggers sync data during transition. Not widely adopted
due to complexity, but powerful for 24x7 systems.

X9. How do you handle LOB-heavy workloads?
A.  SecureFiles with compression/dedup, separate LOB tablespace, chunk size,
CACHE/NOCACHE, DBMS_LOB piecewise IO, avoid SELECT * with LOBs,
free temporary LOBs, move giant files to object storage with a pointer.

X10. How do you use AWR/ASH to diagnose an intermittent 5-minute slowdown?
A.  ASH report for that window (top events, top SQL, blockers, objects), AWR
diff against a good period, SQL Monitor if captured, check OS metrics and
alert log. Hourly AWR averages hide short spikes; ASH samples are key.

------------------------ XI. TOOLBOX INTERVIEW QUESTIONS ------------------

Y1. How do you take and restore a consistent logical backup quickly?
A.  pg_dump -Fd -j 8 for parallel directory-format dump (consistent snapshot);
restore with pg_restore -j 8 into a new database; restore pre-data, data,
then post-data (indexes/constraints) which pg_restore handles; analyze
afterwards. For TB-scale or low RPO use physical backups with WAL archive.
REAL-WORLD: Parallel dump/restore of a 900 GB DB took 55 minutes vs 4 hours
single-threaded.

Y2. How do you design backup for 5-minute RPO and 30-minute RTO?
A.  Base backups (pgBackRest full weekly + incrementals), continuous WAL
archiving (archive_timeout ~60 s or streaming to a repo), a hot standby for
fast failover, periodic restore tests, monitoring of archive lag, backups
stored off-region/encrypted. RTO validated by timing restores/promotions.

Y3. How do you perform a major version upgrade with minimal downtime?
A.  Option 1: pg_upgrade --link (minutes of downtime; rehearse, check
extensions, run analyze). Option 2: logical replication to a new-version
cluster, sync, switch writes. Pre-checks: deprecated features, extension
versions, collation/glibc versions, application compatibility, rollback
plan (keep old cluster).

Y4. How do you find and fix duplicate/unused/missing indexes?
A.  Unused: pg_stat_user_indexes with idx_scan = 0 over a full business
cycle (and not enforcing constraints). Duplicates: compare indkey/indpred in
pg_index. Missing FK indexes: compare pg_constraint with pg_index. Use
hypopg to test hypothetical indexes. Drop with caution (CONCURRENTLY).

Y5. How do you detect and measure table/index bloat?
A.  pgstattuple / pgstattuple_approx for exact/approx, estimation queries
from community scripts, n_dead_tup and autovacuum stats, comparing table size
to expected size. Fix by vacuum tuning, REINDEX CONCURRENTLY, pg_repack.

Y6. What do you check before installing a new extension in production?
A.  Compatibility with PG major version, maintenance status, shared_preload_
libraries restart requirement, security implications (untrusted languages,
file/OS access), resource usage, upgrade path (ALTER EXTENSION UPDATE), support
on managed services, backups/restores includes extension.

Y7. How does pgbench help and what are its limits?
A.  Quick synthetic OLTP benchmark (TPC-B-like) or custom scripts (-f) to test
config changes, hardware, pooler settings. Limits: doesn't mirror your
workload; use captured production queries/replay (pgreplay) for realism.

Y8. How do you migrate from Oracle to PostgreSQL step by step?
A.  Assess (ora2pg report, SCT), convert schema/code, fix incompatibilities
(see VII C23), migrate data (ora2pg/oracle_fdw/DMS + CDC), build test
harness (result comparison, performance baselines), tune stats/indexes,
rehearse cutover, run dual write/parallel run if needed, cutover with
rollback plan, post-migration monitoring.

Y9. psql tricks you use daily?
A.  \x auto, \timing, \watch, \gexec to generate and run DDL, \copy for client
files, \sf to view function definitions, \d+ for table details with
sizes/storage, \set ON_ERROR_STOP on for scripts, -v variables, -1 single
transaction runs.

Y10. What differs when running PostgreSQL on a managed service?
A.  Limited privileges and extensions, parameter groups, vendor-specific
backup/failover/replica semantics, I/O credit models, maintenance windows
forcing restarts, no direct WAL access, performance insights tools in place
of OS tools. Design for those limits and test failover.

-- Active sessions with waits
SELECT sid, serial#, username, status, sql_id, event, wait_class,
       seconds_in_wait, blocking_session
FROM   v$session
WHERE  type = 'USER' AND status = 'ACTIVE';

SELECT sid, serial#, blocking_session, event, seconds_in_wait, sql_id
FROM   v$session
WHERE  blocking_session IS NOT NULL;

-- Top SQL by elapsed time (current shared pool)
SELECT sql_id, executions, ROUND(elapsed_time/1e6,1) elapsed_s,
       buffer_gets, disk_reads, rows_processed
FROM   v$sql
ORDER  BY elapsed_time DESC FETCH FIRST 10 ROWS ONLY;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR('&sql_id', NULL, 'ALLSTATS LAST'));

-- Plans from AWR history
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_AWR('&sql_id'));

-- Long running operations
SELECT sid, opname, target, sofar, totalwork,
       ROUND(sofar/totalwork*100,1) pct, time_remaining
FROM   v$session_longops WHERE sofar < totalwork;

-- Tablespace usage
SELECT tablespace_name, ROUND(used_percent,1) used_pct
FROM   dba_tablespace_usage_metrics ORDER BY used_percent DESC;

-- Undo / temp usage
SELECT begin_time, undoblks, txncount, maxquerylen, ssolderrcnt, nospaceerrcnt
FROM   v$undostat ORDER BY begin_time DESC FETCH FIRST 12 ROWS ONLY;
SELECT username, sql_id, tablespace, segtype, blocks
FROM   v$tempseg_usage;

-- Invalid objects
SELECT owner, object_type, object_name FROM dba_objects WHERE status = 'INVALID';

-- Stale statistics
SELECT owner, table_name, last_analyzed, stale_stats
FROM   dba_tab_statistics WHERE stale_stats = 'YES';

-- Redo log switch frequency (per hour)
SELECT TO_CHAR(first_time,'YYYY-MM-DD HH24') hr, COUNT(*) switches
FROM   v$log_history GROUP BY TO_CHAR(first_time,'YYYY-MM-DD HH24') ORDER BY 1 DESC;

-- Flash recovery area usage
SELECT * FROM v$recovery_file_dest;
SELECT * FROM v$flash_recovery_area_usage;

SELECT event, COUNT(*) samples
FROM   v$active_session_history
WHERE  sample_time > SYSDATE - 30/1440 AND session_state = 'WAITING'
GROUP  BY event ORDER BY samples DESC;

-- Session kill (after identifying the right one)
ALTER SYSTEM KILL SESSION 'sid,serial#' IMMEDIATE;

 XII.2 POSTGRESQL DIAGNOSTIC QUERIES
==========================================================================
-- Active queries (longest first)
SELECT pid, usename, state, wait_event_type, wait_event,
       now() - query_start AS runtime, left(query,120) AS query
FROM   pg_stat_activity
WHERE  state <> 'idle' AND pid <> pg_backend_pid()
ORDER  BY runtime DESC;

-- Idle in transaction (vacuum blockers)
SELECT pid, usename, now() - xact_start AS xact_age, left(query,100) q
FROM   pg_stat_activity WHERE state LIKE 'idle in transaction%'
ORDER  BY xact_age DESC;

-- Blocking chains
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, left(query,100)
FROM   pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- Top SQL (pg_stat_statements; PG13+ column names)
SELECT queryid, calls, round(total_exec_time) AS total_ms,
       round(mean_exec_time::numeric,2) AS mean_ms, rows,
       shared_blks_read, left(query,100) AS query
FROM   pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

-- Biggest tables
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS total
FROM   pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 20;

-- Dead tuples and autovacuum health
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze,
       n_tup_hot_upd, n_tup_upd
FROM   pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 20;

-- Unused indexes (check across a full business cycle; skip constraint indexes)
SELECT s.schemaname, s.relname, s.indexrelname, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM   pg_stat_user_indexes s JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE  s.idx_scan = 0 AND NOT i.indisunique AND NOT i.indisprimary
ORDER  BY pg_relation_size(s.indexrelid) DESC;

-- Foreign keys without a leading-column index (simplified)
SELECT c.conrelid::regclass AS tbl, c.conname
FROM   pg_constraint c
WHERE  c.contype = 'f'
AND    NOT EXISTS (SELECT 1 FROM pg_index i
                   WHERE i.indrelid = c.conrelid AND i.indkey[0] = c.conkey[1]);

-- Cache hit ratio (database level)
SELECT datname, round(blks_hit*100.0/nullif(blks_hit+blks_read,0),2) AS hit_pct
FROM   pg_stat_database ORDER BY hit_pct;

-- Transaction ID age (wraparound watch)
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
SELECT c.oid::regclass, age(c.relfrozenxid)
FROM   pg_class c WHERE c.relkind IN ('r','m') ORDER BY 2 DESC LIMIT 10;

-- Replication lag and slots
SELECT application_name, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes, replay_lag
FROM   pg_stat_replication;
SELECT slot_name, slot_type, active, restart_lsn, wal_status
FROM   pg_replication_slots;

-- Checkpoint behavior (PG17+: pg_stat_checkpointer; older: pg_stat_bgwriter)
SELECT * FROM pg_stat_bgwriter;

-- Locks overview
SELECT locktype, mode, granted, count(*) FROM pg_locks GROUP BY 1,2,3 ORDER BY 4 DESC;

-- Settings and where they came from
SELECT name, setting, unit, context, source FROM pg_settings WHERE name IN
 ('shared_buffers','work_mem','max_connections','random_page_cost');

-- Cancel / terminate
SELECT pg_cancel_backend(<pid>);      -- cancels current query
SELECT pg_terminate_backend(<pid>);   -- ends the session

##########################################################################
# PART XIII: DATA MODELLING, DW/ETL, MIGRATION & CLOUD (D1-D20)
##########################################################################

D1. How do you approach designing a new OLTP schema?
A.  Gather entities/access patterns, model in 3NF with clear keys, define
constraints (PK/FK/CHECK/UNIQUE), choose data types carefully, plan
indexes from query patterns, consider partitioning for growth/retention,
define naming standards, audit columns (created/updated), soft vs hard
delete policy, security (roles/RLS/VPD), and review with DBAs/app teams.
Validate with load tests on realistic volume.

D2. Star schema vs snowflake vs data vault?
A.  Star: central fact table with denormalized dimensions - simplest, fastest
for BI. Snowflake: normalized dimensions - saves space, more joins. Data
Vault (hubs/links/satellites): auditability and agility for enterprise
integration layers, then marts for reporting.

D3. Fact table types and grain.
A.  Transaction, periodic snapshot, accumulating snapshot, factless. Always
declare the grain first (one row per what?). Additive vs semi-additive vs
non-additive measures. Degenerate dimensions, conformed dimensions.

D4. Slowly Changing Dimensions types.
A.  Type 0 fixed, 1 overwrite, 2 new row with validity dates, 3 previous-
value column, 4 mini-dimension/history table, 6 hybrid (1+2+3). Implementation
patterns: Oracle MERGE/INSERT ALL; PostgreSQL MERGE (PG15+)/ON CONFLICT plus
range types/exclusion constraints; hash of attributes for change detection.

D5. ETL vs ELT and orchestration.
A.  ETL transforms before load; ELT loads raw then transforms in the DB
(favoured with powerful warehouses and SQL). Use staging/raw/curated layers,
idempotent jobs, restartability, lineage, data quality checks, orchestration
(Airflow, Oracle Scheduler chains, pg_cron + external orchestrator).

D6. Change Data Capture options.
A.  Oracle: GoldenGate, LogMiner, Streams (legacy), MV logs, timestamps,
triggers. PostgreSQL: logical decoding (pgoutput, wal2json) with Debezium,
pglogical, triggers/outbox, timestamp watermarks. Choose by latency,
volume, schema-change tolerance, DB overhead.

D7. Designing idempotent, restartable batch jobs.
A.  Batch control table (run id, step, status, high-water mark), deterministic
chunking, upserts (MERGE/ON CONFLICT) instead of blind inserts, error/reject
tables, retry with backoff, locking to avoid concurrent runs (DBMS_LOCK/
advisory locks), reconciliation counts and checksums, alerting.

D8. Data quality and reconciliation approach.
A.  Row counts per source/target, sum checks on key measures, hash totals,
null/duplicate/orphan checks, referential checks, sampling compare, rule
tables with thresholds, quarantine invalid rows with reasons, dashboard of
quality KPIs.

D9. Partitioning for data warehouses and retention.
A.  Range/interval by date; partition-wise joins; local indexes; exchange
partition loads (Oracle EXCHANGE PARTITION; PG ATTACH PARTITION with matching
constraints); archive/purge by drop/detach; compress cold partitions; keep
statistics incremental per partition.

D10. Handling slowly growing JSON/semi-structured data.
A.  Land raw JSON (JSON/JSONB/CLOB with IS JSON), extract stable attributes
to columns/virtual or generated columns, index hot paths (GIN/JSON search
index/function-based), keep schema registry; avoid unbounded sparse columns.

D11. Multi-tenant design options.
A.  Database/PDB per tenant (strong isolation), schema per tenant (balanced),
shared schema with tenant_id (+ VPD/RLS) (scales best, noisy neighbors,
needs strict indexing with tenant_id leading). Consider backup/restore per
tenant, upgrades, and data residency.

D12. Time-series and large append-only data.
A.  Time partitioning, BRIN (PG) / partition pruning + compression (Oracle),
rollups/continuous aggregates (TimescaleDB), retention by partition drop,
write path batching (COPY / direct path), avoid secondary index overload.

D13. Soft delete vs hard delete vs temporal tables.
A.  Soft delete (flag/timestamp) complicates uniqueness and indexes (use
partial/filtered unique indexes). History via audit triggers, Flashback Data
Archive (Oracle), temporal/system-versioned patterns (PG range types,
extensions), or event logs.

D14. Caching and read scaling patterns.
A.  Oracle: result cache, Active Data Guard read replicas, In-Memory,
materialized views. PostgreSQL: read replicas, materialized views, summary
tables, external cache (Redis) with invalidation by NOTIFY/CDC.

D15. Capacity planning method.
A.  Baseline growth (rows/day, GB/month, WAL/redo per hour, IOPS, CPU,
connections, peak TPS), project with growth curves and retention, plan for
indexes/temp/undo/WAL, backup storage, replicas, headroom (30-50%), test
with production-sized data, review quarterly.

D16. RPO/RTO and DR design.
A.  RPO = tolerable data loss, RTO = tolerable downtime. Oracle: Data
Guard (sync/async), RMAN backups, flashback; PostgreSQL: sync/async
replicas, WAL archive/PITR, automated failover, cross-region copies. Test
failover regularly; document runbooks; monitor lag.

D17. Cloud migration considerations for databases.
A.  Lift-and-shift (IaaS) vs managed service (RDS/Aurora/OCI/Autonomous).
Check version support, extensions/options, licensing (BYOL vs included),
network latency, data transfer time (DMS/Data Pump/snapshot), IOPS/
throughput limits, backup/HA model, security (KMS, private networking),
cost model, exit strategy.

D18. How do you evaluate Oracle -> PostgreSQL feasibility?
A.  Inventory objects and PL/SQL volume, features used (RAC, Partitioning,
Advanced Queuing, VPD, Text, Spatial, DB links, autonomous txns, packages),
SQL dialect usage (CONNECT BY, hints, (+)), data volume and downtime
window, performance requirements, team skills, tooling readiness
(ora2pg/SCT reports give effort estimates), and cost/benefit including
licensing savings vs conversion/testing effort.

D19. Zero-downtime migration strategy outline.
A.  Initial bulk copy + continuous CDC; validation (row counts/checksums);
read-only verification; application dual-read/dual-write if needed; cutover
with short write freeze; fallback plan (reverse replication); monitor and
decommission after stabilization.

D20. Governance: schema change management.
A.  Version-controlled migrations (Liquibase/Flyway/Alembic/sqitch), peer
review, automated tests, environments parity, rollback/forward strategy,
change windows, lock/timeout guards, post-deploy validation (invalid objects,
plpgsql_check), audit of DDL via event triggers/auditing.

##########################################################################
# PART XIV: TROUBLESHOOTING RUNBOOKS
##########################################################################
Method for every incident: (1) Define symptom and impact, (2) Check what
changed, (3) Get facts before acting (waits, plans, logs), (4) Mitigate
safely, (5) Root cause, (6) Prevent (alert/test/automation).

RB1. SLOW QUERY (both)
  1. Get actual plan (DBMS_XPLAN ALLSTATS LAST / EXPLAIN ANALYZE BUFFERS).
  2. Estimated vs actual rows; biggest time/buffer node.
  3. Stats fresh? Histogram/extended stats? Indexes usable (sargability)?
  4. Binds/params skew (peeking, generic plan)? Plan changed recently?
  5. Spills (TEMP/work_mem), parallelism, partition pruning.
  6. Fix: stats, index, rewrite, partition, baseline/hint (Oracle) or
     setting/SET LOCAL (PG). Re-measure. Document.

RB2. BLOCKING / LOCK CONTENTION
  Oracle: V$SESSION blocking_session, DBA_WAITERS, ASH; PG: pg_blocking_pids,
  pg_locks. Identify root blocker (often idle in transaction / forgotten
  session / long batch). Decide: wait, contact owner, cancel/kill. Fix app:
  shorter transactions, consistent lock order, FK indexes, NOWAIT/SKIP LOCKED.

RB3. HIGH CPU
  Oracle: top SQL by CPU (ASH/AWR), hard parse rates, PL/SQL loops,
  latch/mutex contention. PG: pg_stat_statements by total time, seq scans,
  parallel workers, JIT, connection storms, autovacuum workers, regex/JSON
  functions. OS: run queue, steal time. Mitigate: pooling, cap parallelism,
  tune top queries.

RB4. HIGH I/O OR SLOW COMMITS
  Oracle: db file sequential/scattered read, direct path, log file sync/
  parallel write, checkpoint incomplete. PG: IO:DataFileRead, WALSync/WALWrite,
  checkpoint spikes (log_checkpoints), backend writes, temp file spills.
  Actions: reduce commits per second, batch writes, tune checkpoint/redo
  sizing, move WAL/redo to faster storage, add memory, fix full scans.

RB5. DISK FULL
  Oracle: archive destination/FRA (ORA-00257), tablespace autoextend limit,
  TEMP/UNDO growth, trace/audit files. Use RMAN delete backed-up archives,
  add datafile, shrink, purge logs.
  PG: pg_wal (replication slot, archive failure), base/ (bloat), temp files,
  logs. Fix slot/archive_command first, never delete WAL files manually;
  VACUUM/repack; clean logs.

RB6. REPLICATION LAG / STANDBY ISSUES
  Oracle Data Guard: V$DATAGUARD_STATS, apply lag/transport lag, network,
  MRP status, archive gaps. PG: pg_stat_replication write/flush/replay lag,
  long queries on standby (conflicts), replica I/O, large transactions,
  WAL receiver errors, slots. Mitigate: throttle bulk jobs, tune standby
  delay/feedback, resize replica, rebuild if gap unrecoverable.

RB7. BACKUP FAILURE
  Verify error (RMAN logs / pgBackRest logs), storage space, permissions,
  archive continuity, network, locks. Fix then run an immediate backup and a
  validation/test restore. Alert on backup age.

RB8. CORRUPTION SUSPECTED
  Oracle: ORA-01578, DBVERIFY, RMAN VALIDATE, block media recovery.
  PG: checksum failures, amcheck, pg_dump errors, restore from replica/
  backup/PITR. Stop writes if needed, find scope, recover from clean copy,
  investigate storage/hardware, never ignore.

RB9. CONNECTION STORM / MAX CONNECTIONS
  Identify source (module/application_name), enforce pooling, set timeouts,
  limit per role, increase only after pooling. Oracle: PROCESSES/SESSIONS,
  listener logs, DRCP. PG: max_connections, PgBouncer pools, idle sessions.

RB10. PERFORMANCE REGRESSION AFTER RELEASE/UPGRADE
  Compare before/after (AWR diff / pg_stat_statements snapshots), changed
  plans, new SQL, stats gathered, parameter changes, collation/NLS changes.
  Mitigate with plan baseline / config rollback; test upgrades with
  production-like workload replay.

RB11. LONG-RUNNING ROLLBACK / HUGE TRANSACTION
  Oracle: rollback time proportional to work done; monitor V$TRANSACTION
  used_ublk; do not bounce (restart continues rollback). PG: rollback is
  instant, but bloat/vacuum follow; watch WAL volume and replica lag.

RB12. DEADLOCK STORM
  Capture deadlock traces/logs, find the SQL pair, fix lock ordering,
  index FKs, shorten transactions, add retry.

# PART XV: RAPID-FIRE REVISION (R1-R90) & SCENARIO QUESTIONS (S1-S12)
##########################################################################
One- or two-line answers for last-day revision. [O]=Oracle [P]=PostgreSQL.

--------------------------- A. ARCHITECTURE ------------------------------
R1.  [O] Instance vs database? Instance = SGA + processes; database = files.
R2.  [O] Which process writes redo? LGWR (flush on commit, 1/3 full, 3 s).
R3.  [O] Which writes dirty blocks? DBWn (checkpoints, free buffers).
R4.  [O] What does SMON do? Instance recovery, temp cleanup, coalescing.
R5.  [O] What does PMON do? Cleans failed sessions/locks, registers services (LREG).
R6.  [O] Smallest I/O unit? Data block (commonly 8 KB).
R7.  [O] What is SCN? System Change Number - logical clock for consistency.
R8.  [O] Undo purposes? Rollback, read consistency, flashback.
R9.  [O] Cause of ORA-01555? Needed undo overwritten (long query/small undo).
R10. [O] What is ITL? Per-block transaction slots; ITL waits when exhausted.
R11. [O] Shared pool holds? Library cache, dictionary cache, result cache.
R12. [O] PGA holds? Private work areas (sort/hash), session state.
R13. [O] Startup stages? NOMOUNT -> MOUNT -> OPEN.
R14. [O] Best shutdown mode? IMMEDIATE (ABORT only if hung).
R15. [O] Crash recovery steps? Roll forward with redo, roll back with undo.
R16. [O] RAC data transfer? Cache Fusion over the private interconnect.
R17. [P] Process model? postmaster forks a backend per connection.
R18. [P] Main memory areas? shared_buffers, WAL buffers, work_mem (per node).
R19. [P] What does the checkpointer do? Flushes dirty pages, writes checkpoint record.
R20. [P] bgwriter's job? Trickle-writes dirty buffers ahead of need.
R21. [P] WAL segment default size? 16 MB.
R22. [P] Page size? 8 KB.
R23. [P] What's in a tuple header? xmin, xmax, cmin/cmax, ctid, infomask, nulls.
R24. [P] Does UPDATE overwrite in place? No - new tuple version (HOT if possible).
R25. [P] What does VACUUM do? Removes dead tuples, updates FSM/VM, freezes xids.
R26. [P] Crash recovery steps? WAL replay only (no undo).
R27. [P] What is TOAST? Out-of-line compressed storage for large values.
R28. [P] What are hint bits? Cached commit-status flags in tuple headers.
R29. [P] XID wraparound protection? Freezing; anti-wraparound autovacuum.
R30. [P] Default isolation level? READ COMMITTED.

------------------------- B. SQL AND PROGRAMMING -------------------------
R31. RANK vs DENSE_RANK? RANK leaves gaps after ties; DENSE_RANK does not.
R32. UNION vs UNION ALL? UNION dedups (sort/hash); UNION ALL doesn't.
R33. NOT IN pitfall? Any NULL in subquery returns no rows; use NOT EXISTS.
R34. WHERE vs HAVING? Row filter before grouping vs group filter after.
R35. Top-N per group in PG? LATERAL ... LIMIT N, DISTINCT ON, row_number().
R36. Top-N per group in Oracle? row_number() or CROSS APPLY/FETCH FIRST (12c+).
R37. Upsert in Oracle? MERGE. In PG? INSERT ... ON CONFLICT (or MERGE 15+).
R38. Pagination best practice? Keyset seek, not deep OFFSET.
R39. '' vs NULL? Oracle: same; PostgreSQL: different.
R40. Oracle DATE vs PG date? Oracle DATE has time; PG date doesn't.
R41. LISTAGG equivalent in PG? string_agg().
R42. NVL/DECODE equivalents? COALESCE / CASE (Oracle supports both too).
R43. ROWNUM equivalent? LIMIT/FETCH FIRST or row_number().
R44. Hierarchical queries? Oracle CONNECT BY; PG WITH RECURSIVE (ltree).
R45. PL/SQL BULK COLLECT limit? Use LIMIT 100-1000 to cap PGA memory.
R46. FORALL purpose? One context switch for a DML batch; SAVE EXCEPTIONS.
R47. PG equivalent of FORALL? Set-based SQL, unnest arrays, COPY.
R48. Autonomous transaction in PG? None; use dblink/pg_background workarounds.
R49. Package in PG? Schemas + extensions; no package state.
R50. SECURITY DEFINER hardening? SET search_path and revoke PUBLIC execute.
R51. Mutating table (Oracle)? Row trigger reading its own table; use compound trigger.
R52. Dynamic SQL safety? Bind variables + DBMS_ASSERT / format('%I','%L').
R53. EXCEPTION cost in PG? Each block creates a subtransaction; avoid in loops.
R54. Function volatility in PG? VOLATILE, STABLE, IMMUTABLE; mislabeling is dangerous.
R55. Result cache? Oracle RESULT_CACHE; PG no built-in (use MVs/app cache).

------------------------- C. PERFORMANCE TUNING --------------------------
R56. First tuning step? Get actual plan with row counts, compare E-rows vs A-rows.
R57. Why index not used? Function on column, type mismatch, low selectivity, stale stats.
R58. Composite index order? Equality columns first, then range/sort.
R59. Bitmap index use? Oracle DW low cardinality; avoid in OLTP (locks).
R60. BRIN use? PG huge append-only tables with correlated order.
R61. GIN use? PG jsonb, arrays, full-text, trigram.
R62. Partition pruning check? Pstart/Pstop (Oracle) / "Subplans Removed"/partition list (PG).
R63. Bind peeking issue? First value fixes plan; ACS (Oracle) / generic plan (PG).
R64. Stats gathering Oracle? DBMS_STATS; PG? ANALYZE / autovacuum.
R65. Extended statistics? Column-group/expressions stats (both: DBMS_STATS ext / CREATE STATISTICS).
R66. Direct-path load? Oracle INSERT /*+ APPEND */; PG COPY + UNLOGGED/FREEZE.
R67. Fast bulk delete? Partition drop/truncate or CTAS + swap.
R68. Parallel risks? Resource exhaustion, skew; limit DOP / workers per role.
R69. HWM fix? Oracle SHRINK/MOVE; PG VACUUM (+ repack for bloat).
R70. Pooling PG? PgBouncer transaction mode; Oracle UCP/DRCP.

------------------------- D. CONCURRENCY, HA, OPS ------------------------
R71. Queue pattern? SELECT ... FOR UPDATE SKIP LOCKED in both.
R72. Deadlock error codes? Oracle ORA-00060; PG SQLSTATE 40P01.
R73. Serialization failure PG? SQLSTATE 40001 - retry transaction.
R74. Unindexed FK effect? Parent delete scans child, locks/deadlocks.
R75. DDL lock danger PG? ACCESS EXCLUSIVE queue; use lock_timeout.
R76. Gap-free numbers? Counter table with lock; sequences have gaps.
R77. Oracle backup tool? RMAN. PG? pgBackRest/pg_basebackup + WAL.
R78. PITR in PG? Base backup + archived WAL + recovery target.
R79. Flashback in PG? None - use PITR clone or temporal design.
R80. Standby types Oracle? Physical, logical, snapshot standby (Data Guard).
R81. Streaming vs logical replication? Physical byte-level vs row changes per table.
R82. Replication slot danger? Retains WAL/xmin; abandoned slot fills disk.
R83. Oracle HA clustering? RAC + Data Guard. PG HA? Patroni/repmgr + replicas.
R84. VPD vs RLS? Oracle DBMS_RLS policies vs PG CREATE POLICY.
R85. TDE availability? Oracle TDE (ASO); PG community: use disk/volume encryption.
R86. Audit tools? Oracle Unified Audit; PG pgaudit.
R87. Monitoring history? Oracle AWR; PG pg_stat_statements snapshots + Prometheus.
R88. Upgrade tools? Oracle AutoUpgrade/DBUA; PG pg_upgrade/logical replication.
R89. Scheduler? Oracle DBMS_SCHEDULER; PG pg_cron.
R90. One-line difference summary? Oracle: undo-based in-place updates; PG: heap versions + VACUUM.

------------------------- SCENARIO QUESTIONS (S1-S12) --------------------

S1. A nightly job that took 1 hour now takes 5 hours. What do you do?
A.  Compare to baseline: same plan? data volume change? stats? locks/
waits? Use AWR diff or pg_stat_statements snapshots, actual plans,
check concurrent workloads and storage latency. Mitigate (restore plan,
add index, adjust parallelism), then root-cause and add a monitor.

S2. Users report the application is "freezing" intermittently. 
A.  Catch it live: active sessions and waits, blocking chains, connection
counts, checkpoints/redo switches, OS metrics. Intermittent pauses often
come from lock queues (DDL), checkpoint spikes, connection storms,
long transactions, or GC/pool issues in the app. Add instrumentation
(application_name/module, log_lock_waits, ASH).

S3. You must delete 80% of a 1 TB table (retention). Plan?
A.  Don't DELETE. Option: partition and drop old; or CTAS the 20% to keep,
build indexes/constraints, swap names in a short window; validate counts;
gather stats; keep the old table briefly for rollback. PG: remember dead
tuple/vacuum implications; Oracle: undo/redo and HWM.

S4. A report must be consistent across multiple queries. How?
A.  Oracle: SET TRANSACTION READ ONLY or SERIALIZABLE; flashback query AS OF
SCN. PG: BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY (or pg_dump-like
snapshot export/import). Mind long-snapshot effects (undo / vacuum).

S5. How do you safely add a NOT NULL column with default to a 2B-row table?
A.  Oracle 11g+: ADD column DEFAULT value NOT NULL is metadata-only. PG11+:
non-volatile default is metadata-only; NOT NULL on existing column uses
CHECK NOT VALID + VALIDATE then SET NOT NULL (fast). Avoid volatile
defaults that rewrite the table; backfill in batches if values vary.

S6. The primary DB is down. Walk through failover.
A.  Confirm failure (not a network blip), protect against split-brain
(fencing), choose most advanced standby (lowest lag), promote (Data Guard
failover / pg_ctl promote or Patroni), repoint apps (SCAN/VIP/DNS/
proxy), verify data/lag, reintegrate old primary (flashback+convert / pg_rewind
or rebuild), post-mortem and update runbook.

S7. Design a high-throughput audit/log table.
A.  Append-only, time-partitioned (interval/pg_partman), minimal indexes
(BRIN/time), batch inserts (APPEND / COPY), compress or archive old
partitions, avoid triggers for each row where possible, separate tablespace,
retention via partition drop, monitor growth.

S8. A developer wants to use SELECT FOR UPDATE on 5M rows. Response?
A.  Explain cost: locks/undo/WAL writes (PG dirties heap pages), blocking
others, long transactions. Prefer set-based update with a status column,
chunked batches with SKIP LOCKED, or optimistic approaches.

S9. How do you make a multi-step ETL restartable?
A.  Control table with step status and high-water mark, deterministic chunks,
idempotent upserts, commit per chunk, error table, resume from last
successful step, locks to prevent concurrent runs, metrics and alerts.

S10. You inherit a database with no documentation. First week plan?
A.  Inventory (versions, sizes, objects, jobs, dependencies), backup/restore
verification, monitoring baseline (top SQL/waits), security review
(privileges, passwords, encryption), parameter review, schema/ERD
reverse-engineering, interview app owners, quick wins (missing indexes,
stale stats, unused objects), written runbook and risk register.

S11. How do you convince the team to adopt PostgreSQL (or stay on Oracle)?
A.  Frame with requirements and TCO: licensing, features needed (RAC,
partitioning, vendor support), skills, ecosystem, migration risk, cloud
strategy. Propose a pilot with measurable criteria (performance, ops cost,
defect rate) rather than ideology.

S12. A critical query is fast in test but slow in production. Why?
A.  Different data volume/skew/statistics, missing indexes or partitions,
configuration (work_mem, optimizer params), concurrency, cache state,
bind values, NLS/collation differences, parallelism/hardware, and
version/patch differences. Reproduce with production stats export/import
(Oracle DBMS_STATS.EXPORT_TABLE_STATS; PG restore pg_statistic via tools) or
a recent clone.

# PART XVI: HOW TO PRESENT ANSWERS IN A SENIOR INTERVIEW
##########################################################################
 1. START WITH THE FLOW, THEN DRILL DOWN.
    "A statement arrives, is parsed/planned, touches buffers, writes
    redo/WAL, commits via a log flush; data pages are written later."
 2. TIE EVERY CONCEPT TO A SYMPTOM AND A FIX.
    log file sync -> commit rate or slow redo disk -> batch commits.
    idle in transaction -> vacuum blocked -> timeouts + fix app.
 3. USE NUMBERS FROM YOUR WORK.
    Size of DB, TPS, connections, WAL/redo per hour, recovery time,
    replica lag, bloat percentage, before/after runtime.
 4. KNOW THE FAILURE MODES.
    Oracle: ORA-01555, ORA-04031, ORA-00257, ITL waits, hot blocks,
            RAC gc waits.
    PostgreSQL: bloat, xid wraparound, replication slot WAL growth,
            lock queue on DDL, OOM from work_mem, subtransaction overflow.
 5. BE VERSION-AWARE.
    Oracle 12c multitenant, 19c LTS, 23ai; PostgreSQL 12 CTE inlining,
    13 dedup, 14 subxact/partition improvements, 15 MERGE + shared stats,
    16 pg_stat_io, 17 incremental backup/JSON_TABLE, 18 async I/O.
 6. DRAW IT.
    Practice sketching: client -> process -> memory -> log -> datafiles;
    UPDATE/COMMIT flow; MVCC versions; checkpoint; replication topology.
 7. FINISH WITH A TRADE-OFF.
    "Oracle pays for old versions at read/rollback time with undo; PostgreSQL
    pays at cleanup time with vacuum. Which cost hurts depends on workload:
    long-running readers and huge rollbacks vs high-churn updates."

 PRACTICE PROMPTS (self-test):
   - Explain what happens from COMMIT to disk in both databases.
   - Why can a long transaction hurt PG vacuum but hurt Oracle via undo?
   - How would you design DR for 15 min RPO in each?
   - Walk me through diagnosing a sudden slowdown in each.
   - How would you migrate a 2 TB Oracle schema with PL/SQL packages to PG?

   - Walk through any two Part XV scenarios aloud.
